## 1. 第一个要义是轻

> 软件的第一个要义是轻

### 1.1 「使用轻的技术栈」

> 使用轻的技术栈,功能上做减法

**在代码里的落点**

- 运行时直接依赖 **13 个第三方包**（`pubspec.yaml`）：`drift` / `sqlite3` / `path_provider` / `path` /
  `uuid` / `provider` / `dio` / `flutter_secure_storage` / `flutter_markdown` / `cupertino_icons` /
  `archive` / `file_selector` / `crypto`。dev 依赖 6 个，其中 `path_provider_platform_interface` /
  `plugin_platform_interface` 本来只是传递依赖，显式列出只为满足 `depend_on_referenced_packages`。
- `pubspec.lock` 里总共 **118 个包**（含 Flutter SDK 自带与全部传递依赖）。
- **只有一套代码生成器**：`drift_dev` + `build_runner`。`lib/core/db/tables.dart` 是全项目唯一
  需要跑 `build_runner` 的文件。
- 刻意拒绝的依赖——**逐条在 `pubspec.lock` 里查证过确实不存在**（不是"没写进 `pubspec.yaml`"）：

| 被拒绝的包 | 本项目用什么替代 |
|---|---|
| `shared_preferences` | 数据库里的 `app_kv` 表（`PreferencesService`）；偏好随笔记进同一个备份包 |
| `riverpod` / `riverpod_generator` | `provider` + `ChangeNotifier` |
| `freezed` / `json_serializable` | 模型与 JSON 全手写，不引入第二套生成器 |
| `sqflite` / `sqlite3_flutter_libs` | drift ≥ 2.32 起由 `sqlite3` 的 build hooks 自动打包原生库 |
| `hive` / `get_it` / `bloc` | 不需要第二套存储或依赖注入 |
| `file_picker` | Flutter 官方的 `file_selector`（Windows 走 IFileDialog、Android 走 SAF，且不需要存储权限） |
| `url_launcher` / `share_plus` / `permission_handler` | 用不到 |

- 选型理由与**代价（放弃了什么）不在这里重复**，见 [技术栈设计](技术栈设计.md) 第 3、4、5、7、8、9 节。

**尚未落地 / 反例**

- `lib/core/util/ai_limits.dart:212` 的注释写着"避免为一个扩展引入 characters 包"，于是手写了一个
  最小的 `characters` 扩展（`:215-229`）。但 **`characters` 本来就在 `pubspec.lock` 里**
  （`dependency: transitive`，由 flutter 带进来的 1.4.1）。省下的只是"直接依赖声明"这一行，
  实际解析出的依赖集合一个没少——这条注释给出的理由在事实层面不成立。

## 2. 「笔记库平铺而不是模仿文件系统」

> 笔记库平铺而不是模仿文件系统

**在代码里的落点**

- `lib/core/db/tables.dart:36-51` 的 `Notebooks` 表全部字段只有：
  `id` / `name` / `sortOrder` / `createdAt` / `updatedAt` / `deletedAt`。
  **没有 `parentId`，也没有任何自引用外键**——表结构层面就不可能嵌套。
- `sortOrder` 的注释已经把口径改掉：`用于列表展示排序。**不再是"同层内"排序**——没有层了。`
  （`tables.dart:40`）
- 层级是被**迁移主动删掉**的，不是"从没写过"：v2→v3 执行
  `ALTER TABLE notebooks DROP COLUMN parent_id`，并 `DROP INDEX IF EXISTS idx_folders_parent`；
  SQLite < 3.35 的退路是把 `parent_id` 全部置 NULL（[数据库设计](数据库设计.md):562-582）。
- 改名与去层级是同一次动作：`folders` → `notebooks`、`folder_id` → `notebook_id`、
  `workspace_folder_id` → `workspace_notebook_id`。文件头写明：
  **全项目没有任何 `folder_*` 列，也没有任何 `@JsonKey` 列名映射**（`tables.dart:19-23`）。
- 理由就写在表定义里（`tables.dart:28-31`）：当初采用 SQLite 而非文件系统，本来就是为了
  不模仿目录树；再长出子目录等于把文件系统的复杂性又搬回来。
- 界面对齐：笔记库页没有层级展示，**刻意没有「新建子笔记库」**（[界面设计](界面设计.md):176、:455）。
- 顺带把层级最容易出错的边界也一并去掉了：删笔记库不再需要"子目录上浮"
  （[界面设计](界面设计.md):468），改成**不删笔记**——一个事务里把库内笔记
  `notebook_id → NULL` 且 `is_inbox → true`（回到「我的轻笔记」），再逻辑删除笔记库本身
  （[数据库设计](数据库设计.md):78-81）。直接级联删笔记会是数据丢失事故。

**尚未落地 / 反例**

- 有一处**形似层级、但不是库结构**：切片的 `note_chunks.heading` 存的是
  `工作 / 项目A / 风险` 这种标题路径（`tables.dart:358-362`）。它描述的是"这一片落在**这一篇笔记的**
  哪个标题下"，是文档内部的 Markdown 标题层次，不影响笔记库的平铺语义。算张力，不算违反。
- 兼容层会让人误以为"层级还在"：v2→v3 迁移里仍然出现 `folders` 这个名字，备份校验也同时接受
  新旧两个表名（`tables.dart:33-35`）。那是给老库 / 老备份准备的，不是残留的层级字段。

## 3. 「笔记的大小有限制,各个字段的上限有限制」

> 笔记的大小有限制,各个字段的上限有限制

**在代码里的落点**

上限数值集中在一个文件：`lib/core/util/ai_limits.dart`。它的写法本身就是落点——文件头写明
「**对 AI 消费的内容要狠，对用户生产的内容要软**」，并要求所有数值集中在此，
避免"prompt 里写 300、代码里截 500"。

| 对象 | 上限 | 超限会发生什么 |
|---|---|---|
| 笔记正文 | 软 80 KB（`ai_limits.dart:44`） | **只提示**：横幅「笔记较长（x KB）」+「继续变长可能影响编辑流畅度」 |
| 笔记正文 | 强警告 90 KB（`:47`） | **只提示**：「笔记偏长（x KB）」+「建议拆成多篇。还能继续编辑，超过 100 KB 就无法保存了」 |
| 笔记正文 | 硬 100 KB（`:50`） | **拒绝保存**：`_flush()` 直接 return、保存状态显示为失败，内容仍留在编辑器里（`note_editor_page.dart:336-346`）；横幅给「裁剪到 80 KB」按钮，先弹确认「**这个操作不能撤销**」（`:216-248`、`:562-565`）。**这一档绝不静默截断用户写的东西** |
| 笔记标题 | 200 字（`:53`） | **截断**：落盘前 `safeTruncate`。理由是标题会进 prompt，一个几万字的"标题"能直接把一次请求撑爆（`note_editor_page.dart:250-256`） |
| AI 摘要 | 目标 150–250 字（`:19-20`） | 提示词里要求 |
| AI 摘要 | 硬 300 字（`:27`） | **强制截断**。注释里给了实测证据：要求 60 字模型会返回 160 字，**不能只靠提示词** |
| 卡片标签 | 2–6 个（`:32-33`） | 超量截断；**不足 2 个也照存**——"宁可存少，也不要为了凑数塞进没意义的词"（`:199-209`） |
| 单个标签 | ≤5 个汉字 / ≤12 个英文字母（`:36-39`） | 按配额逐字符截断，并剥掉 `#`、引号、`「」『』【】` 这类包装字符（`:157-187`） |
| 列表预览 `notes.excerpt` | 前 200 字（[数据库设计](数据库设计.md):93） | 截断后加 `…`；目的是列表页不读全文 |
| 切片 `note_chunks` | 片 700 字 / 不可拆散单元硬顶 1500 字（`note_chunker.dart:58`、`:72`） | 前者切，后者硬顶。1500 的来源是 `readChunk` 的单次预算：一片超过 1500，AI 根本读不进来，作为"片"就没意义 |
| 搜索历史 | 20 条（`preferences_service.dart:20`） | 超量删除 |
| AI 聊天历史 | 单条 500 字 / 只带最近 5 轮（`ai_chat_repository.dart:61`、`:67`） | 截断处显式标「…（已截断）」 |
| 进 prompt 的单条笔记正文 | AI 助手 6000 字（`ai_chat_repository.dart:54`） | 截断 |
| AI 确认弹层里"改前 / 改后" | 600 字（`agent_dialogs.dart:143`） | 截断并标注 |

两处判据用**字节**而不是字符，理由写在代码里（`ai_limits.dart:55-59`、
`note_editor_page.dart:200-204`）：中文一个字 3 字节，按字符算会**低估三倍**，而数据库与 token
成本都跟字节数更相关。分档边界是**闭区间下界**（正好 80 KB 算"较长"、正好 100 KB 就拒绝保存），
免得出现"显示 100.0 KB 却还能保存"的矛盾（`ai_limits.dart:265-275`）。

**尚未落地 / 反例**（这一节问题最集中）

1. **上限只长在编辑页 UI 上，AI 写路径不受约束。** `tool_executor.dart` 的 `_writeNote()`
   （`:305-326`）与 `_createNote()`（`:596-633`）直接 `upsertNote`，**既不检查
   `AiLimits.noteHardBytes`，也不对标题做 `safeTruncate`**。用户手敲到 100 KB 会被拒绝保存，
   但 AI 的 `createNote` / `updateNote` / `replaceInNote` 可以把笔记写得任意长、标题任意长。
   同一张表两条写入路径，一条有上限一条没有。
2. **同一个字段有两种上限。** `notes.excerpt` 在 `note_repository.dart:240` 是 `max = 200`
   （并先做 Markdown → 纯文本去噪，这正是 [数据库设计](数据库设计.md):93 记录的那个 200）；
   而 `tool_executor.dart:331-334` 的 `_excerptOf()` 是 **80 字**，且不做 Markdown 去噪。
   谁的写入方最后跑，列表预览的长度和形态就不一样。
3. **同一个字段有两种算法。** `notes.wordCount` 在 `note_repository.dart:248-262` 是
   "中文按字 + 英文按词"；`tool_executor.dart:319` 写的是 `content.length`（UTF-16 码元数）。
   AI 写过的笔记，字数统计口径与用户手写的不是一套。
4. **数据库层面没有任何长度约束。** `tables.dart` 里所有 TEXT 列都是不带长度参数的 `text()`
   （`title` / `content` / `name` / `summary` …全都没有）。100 KB、300 字、200 字全靠写入路径
   的代码兜底；绕过这层代码直接写库（导入备份、迁移、将来任何新的写入方）就没有上限。
   DDL 层唯一存在的约束是布尔列的 `CHECK (col IN (0, 1))`（[数据库设计](数据库设计.md):54）。
5. **有些字段根本没有上限。** 笔记库名（`notebooks.name`，`tables.dart:38`）、
   `ai_conversations.title`（`:149`）、`feed_reserve.title` / `body`（`:239-242`）都没有任何
   长度限制，代码里也搜不到对应常量。
6. **有一条上限是死代码。** `AiPrompts.maxBodyChars = 200000`（`prompts.dart:102`）只被
   **已无调用方**的 `organizeUser` 使用（[AI接入设计](AI接入设计.md):282）——"字段上限"清单里
   混着一条已经不生效的。
7. **正文的 100 KB 只管"保存"，不管"入库后的派生"**：切片、搜索、AI 读取都不看这个上限。
   影响有限，因为 `saveContent` 是切片唯一的漏斗（`note_chunk_repository.dart` 的 `onNoteSaved`），
   但"上限"的适用范围要说清是"经过编辑页的保存"，不是"库里的所有正文"。

## 4. 「不做语音输入」

> 不做语言输入的功能,因为这不是一款轻笔记想要的,这是输入法做的事情

（原话里的"语言输入"就是下文代码与文档一致称呼的**语音输入**；原话逐字保留，不改写。）

**在代码里的落点**

- `pubspec.yaml` 与 `pubspec.lock` 里**没有任何语音或音频相关包**：`speech_to_text`、`record`、
  `flutter_sound`、`just_audio`、`audio_session` 等全部不存在（在 118 个锁定包里逐条查过）。
  注意 `record_use` 是 Dart SDK 的构建工具包，与录音无关。
- `lib/` 下 68 个 dart 文件里，`speech` / `voice` / `audio` / `SpeechToText` / `microphone`
  **零命中**。
- 输入只有一条路：`note_editor_page.dart` 的原生 `TextField` + Markdown 文本，输入的事交给系统
  输入法。[界面设计](界面设计.md) 的 15 个页面清单里也没有任何录音入口。
- 用户的理由（"这是输入法做的事情"）与代码的实际分工一致：**文字输入与语音识别都是系统输入法的
  职责，本项目不重复实现**。

**尚未落地 / 反例**

- ⚠️ **`android/app/src/main/AndroidManifest.xml:14-15` 声明了
  `android.permission.RECORD_AUDIO`，注释写着「录音」。** 代码里既没有录音实现，也没有任何
  语音依赖——这是一条**申请了却完全用不到的麦克风权限**。对一份明确说不做语音的 App，
  这既是权限最小化上的越界（应用商店与系统权限页会把它显示给用户），也和这条原则直接冲突。
- **同一份清单里还有同类问题**：`CAMERA`（`:5-6`，注释「拍照（用户想拍照插入笔记时）」）与
  `READ_MEDIA_IMAGES` / `READ_EXTERNAL_STORAGE`（`:8-12`，注释「相册选图」）。
  而界面设计明确写着「**图片：不支持插图**」（[界面设计](界面设计.md):221），
  代码里也没有 `image_picker` / `camera` 任何依赖。**这三组权限是模板式声明，与产品决定相反。**

## 5. 「第二要义得省钱,想办法节省token使用」

> 第二要义得省钱,想办法节省token使用

**费用模型与完整的省钱机制不在这里展开，见 [AI接入设计](AI接入设计.md) 第 3 节。**
本节只记录：这条原则**约束了哪些设计决策**（每条一句话，细节去那份文档）。

| 由此产生的设计决定 | 一句话 | 落点 |
|---|---|---|
| 切片只存偏移、不存正文 | 库里只留一份可喂给 AI 的正文，切片不复制文本，也就不存在"片正文过期" | `tables.dart:308-320`、[数据库设计](数据库设计.md) 第 9 节 |
| 会话历史只带最近 5 轮 | 历史每轮都要重发，钉死上限把总成本从 `O(N²)` 拉回 `O(N)` | `ai_chat_repository.dart:61` |
| 更早的历史压成一段摘要，且**只生成一次** | 之后每轮直接读，不再每轮重复支付"压缩"那次调用 | `ai_chat_repository.dart:544`（`ai_history_summary_<会话id>`，存 `app_kv`） |
| 工具分层下发（19 个 = 核心 7 / 常用 8 / 按需 4） | 核心层带完整 schema、常用层省掉 schema、按需层只在目录里给一行 | `tool_specs.dart`、[AI接入设计](AI接入设计.md) §3.2(3) |
| 读笔记按需：目录先行、正文按片取 | `listNotes` 只取 id + 标题；`listChunks` 不含正文；`readChunk` 每轮 ≤3 片 ≤1500 字 | `tool_executor.dart:122-125` |
| 默认 `deepseek-flash`，`modelPro` 与模型选择表**一并删掉** | 少一个"改了没反应的开关"，也少一条通向 3–4 倍价格的路 | `deepseek_config.dart:16`、[AI接入设计](AI接入设计.md) §3.2 |
| 每个入口显式 `thinking: disabled` | 官方默认开思考且 effort 默认 high，不管它连"加个标签"都走完整推理链 | `deepseek_client.dart:70`、`:126`、`:364` |
| 摘要持久化成资产，只在源正文变化 >20% 时重生成 | 用户改个错别字不会作废摘要、白烧一次调用；判据用字节数而不是 `updatedAt` | `ai_note_summaries.sourceBytes`、`staleRatio = 0.20` |
| 卡片流一次批量出 9 张，素材窗口 400 字 | 一次请求拿 9 张，比分三次各拿 3 张省两次往返，素材 prompt 只发一次 | `feed_repository.dart:35`、`feed_window.dart:20` |
| system prompt 前缀稳定 | 时间戳、随机 ID、笔记 ID 一律不进 prompt 开头，变化的东西 append 在末尾——缓存命中后输入价降到 1/50 | `prompts.dart`、[AI接入设计](AI接入设计.md) §3.2(1) |
| 护栏：轮数、提问数、批量条数、重试次数都有上限 | `maxRounds = 6`、`maxAsksPerTurn = 3`、批量 ≤10、生成类最多重试 1 次 | `agent_loop.dart:139`、[AI接入设计](AI接入设计.md) §3.2(5) |
| `ai_calls` 审计表**不存 prompt / 响应全文** | 成本可见性只留 token 与金额，不留内容 | `tables.dart:90-91` |

**尚未落地 / 反例**

[AI接入设计](AI接入设计.md) §3.3 已经认下三条，这里按"理念—现状"再点一遍：

1. **取消在途请求只是能力，不是行为。** `CancelToken` 贯穿 `DeepSeekClient` 的三个入口，
   但**没有任何调用方传它**——"用户切页/关页时中断请求，不白烧 token"目前不成立。
2. **"空闲时段执行"只有一句静态文案。** 官方价格空闲时段是高峰的一半，但代码里除了用量页那句
   「批量整理放周末或晚上更便宜」，**没有调度、没有提示交互**。
3. **用户无法覆盖价格。** config 注释写着"如需精确对账请在设置页允许用户覆盖"，
   **设置页没有这个入口**。

本次核对另外发现两条：

4. **换来了"秒出"，代价是每次进入轻笔记页都会多跑一批预生成。**
   `FeedRepository.warmUpIfNeeded()` 命中 `feed_reserve` 的预留后，仍然会执行
   `unawaited(_fillPoolForNextTime(source))` → `refill()` → `_doRefill()`，一次生成
   **9 张**（`feed_repository.dart:693`、`:759-766`、`:535-549`）；只要池子小于
   `kFeedPoolTarget = 12`（`:25`）就会真的发请求，而用户这一屏只取 `kFeedBatchSize = 3`
   （`:19`）。也就是说：**"进入轻笔记页"这个动作本身就会触发一次生成**，用户并没有要求过它。
   这与 [界面设计](界面设计.md):440「卡片流不自动调 AI（翻卡片不烧 token）」不矛盾
   （那句说的是翻卡），但确实放宽了"不主动烧 token"的口径。
5. **同一段注释与常量已经对不上。** `feed_repository.dart:646-653` 写的是"预留 **3** 条 /
   申请新的 **6** 张 / 后 3 张入库"，而真实常量是 `kFeedReserveSize = 6`（`:41`）、
   `kFeedGenerateCount = 9`（`:35`）、`kFeedPoolTarget = 12`（`:25`）；
   `tables.dart:215-223` 的说法（"生成 9 张、后 6 张存表"）与常量一致。
   **注释比常量旧**——这类不一致会让人调参数时改错地方。
