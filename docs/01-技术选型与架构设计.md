# 智能笔记 App —— 技术选型与架构设计

> 目标平台：Android 手机（首版），Windows 桌面用于开发调试
> 技术底座：Flutter + Dart + SQLite + DeepSeek API
> 核心能力：笔记记录 → AI 整理 → 记忆卡片（间隔重复）→ 沉浸阅读

---

## 0. 结论速览

| 维度 | 决定 | 一句话理由 |
|---|---|---|
| UI 框架 | Flutter (Material 3) | 一套代码出 Android + Windows 调试版 |
| 数据库方案 | **Drift + NativeDatabase**（不是裸 sqflite） | 类型安全、编译期校验 SQL、响应式 Stream 查询；同一份代码跑 Android 和 Windows |
| SQLite 运行库 | **不依赖 `sqlite3_flutter_libs`** | drift ≥ 2.32 起通过 sqlite3 build hooks 自动打包 SQLite |
| 状态管理 | Provider + ChangeNotifier | 骨架只用一套生成器（drift 的 build_runner），不引入第二套 codegen |
| AI 接口 | DeepSeek OpenAI 兼容协议 + Dio | 流式输出、JSON Output、Tool Calls 全覆盖 |
| 默认模型 | `deepseek-flash` | 支持 JSON Output 与思考模式；1M 上下文够整本笔记投喂 |
| 需思考的任务 | `deepseek-v4-pro` | 只在"整理笔记/生成卡片"这类高价值调用上升级 |
| 记忆卡片算法 | 自实现 SM-2（4 档评分） | 纯 Dart，无依赖，可单测；后续可平滑换 FSRS |
| API Key 存储 | `flutter_secure_storage` | 绝不打进安装包 |
| 最低 Dart SDK | `>=3.10.0` | 被 drift 2.33+ 的约束抬起来的 |

## 1. 为什么是 Flutter + Dart

| 候选 | 优势 | 在你这个场景的劣势 |
|---|---|---|
| **Flutter** | 一套代码覆盖 Android/iOS/桌面；本地 SQLite 生态成熟；Markdown、图表、手势组件齐全 | 包体积比原生大（release APK 约 15–25 MB 起） |
| React Native | JS 生态大，AI SDK 现成 | SQLite 走 bridge，离线重查询性能与类型安全弱一档 |
| 原生 Kotlin | 性能与系统集成最好 | 只有 Android；后续上 iOS 等于重写 |
| Jetpack Compose Multiplatform | Kotlin 一套代码 | 桌面/移动稳定性和第三方库丰富度不如 Flutter |

**决定性因素**：你已经选定 Flutter，且本项目的技术难点集中在「本地数据模型 + 流式 AI + 复习调度」，这三块 Flutter 都有成熟方案，不需要碰平台原生代码。

## 2. 数据库选型：sqflite 还是 Drift

你原话是「sqllite」，这里有一个必须做的决策：**用裸 `sqflite` 还是在上层加 Drift**。

| 维度 | 裸 `sqflite` | **Drift（推荐）** |
|---|---|---|
| 查询写法 | 手写 SQL 字符串 | Dart DSL + 可选自定义 SQL |
| 类型安全 | 无，靠运行时 `Map<String, dynamic>` | 编译期生成行类型 |
| 改表结构 | 手写 `onUpgrade` + 容易漏字段 | 迁移有步骤助手 + 可导出 schema 做回归测试 |
| UI 刷新 | 自己通知、自己重查 | `watch()` 返回 Stream，数据一变 UI 自动重建 |
| 复杂查询 | 手写 JOIN | 类型安全 JOIN |
| 桌面调试 | 需要 `sqflite_common_ffi` 另配 | `NativeDatabase` 原生支持 Windows |
| 编译开销 | 无 | 需要跑一次 `build_runner` |
| 学习成本 | 低 | 中 |

**结论：用 Drift。** 本项目的核心复杂度是「笔记 ↔ 标签 ↔ 卡片 ↔ 复习记录」的多表关系，以及「今日待复习」这种带 JOIN + 排序 + 计数的查询——手写 SQL 字符串在这个量级会迅速变成维护负担。

### 2.1 一个必须避开的过时做法

网上大量 Flutter + SQLite 教程（以及 2025 年前的 Drift 文档）会让你在 `pubspec.yaml` 里加：

```yaml
# ❌ 过时写法
sqlite3_flutter_libs: ^0.5.24
```

Drift 官方平台文档现在明确写着：

> Starting from drift version 2.32.0 ... an up-to-date copy of SQLite will automatically be bundled with your app. **It is no longer necessary to depend on `sqlite3_flutter_libs` or `sqlcipher_flutter_libs`, you can remove these dependencies.**

也就是说，依赖 `sqlite3` 3.x 后由 **build hooks** 机制自动完成打包。**照抄老教程加这个依赖，在新版工具链下会引入不必要的冲突。**

参考：[Drift 支持的平台](https://drift.simonbinder.eu/platforms/)

### 2.2 Android 上的一个坑（官方文档点名）

`NativeDatabase` 在部分 Android 设备上，遇到非常复杂的查询会因临时目录不可用而 OOM。需要在打开数据库前告诉 sqlite3 临时目录位置：

```dart
// main.dart 里，runApp 之前
if (Platform.isAndroid) {
  sqlite3.tempDirectory = (await getTemporaryDirectory()).path;
}
```

这条不是可选优化，建议首版就加上。

### 2.3 数据加密（暂不做，但要知道成本）

笔记是隐私数据。若后续要加密，Drift 支持 `sqlcipher_flutter_libs` + `NativeDatabase(..., setup: (db) => db.execute("PRAGMA key = '...'"))`。代价：密钥管理（放 `flutter_secure_storage`）、换库时的一次性迁移、包体积上涨。**建议首版不做，把它列进 v1.2 的路线图**，但表结构设计上不要依赖明文全文索引。

## 3. 状态管理与项目分层

首版采用**最低生成器数量**原则：

- Drift 必须跑 `build_runner`（生成表结构代码）
- 除此之外**不再引入 freezed / json_serializable / riverpod_generator**，手写 `fromJson`/`toJson` 与状态类

所以状态管理用 `provider` + `ChangeNotifier`，而不是 Riverpod。理由：

1. Riverpod 3.x 当前最新版要求 Dart `^3.12.0`，会进一步抬高 SDK 门槛，且 3.x 的 API 与 2.x 差异较大，网上示例混杂容易踩坑。
2. Provider 在这个规模（十来个页面、单用户本地库）完全够用。
3. 只有一套 codegen，`flutter pub run build_runner build` 出错面小很多。

> 若你偏好 Riverpod：等骨架跑通后再迁移，届时只需替换 `ChangeNotifier` 为 `AsyncNotifier`，数据层（Drift）完全不动。

分层：

```
lib/
├─ core/            基础设施：数据库、主题、安全存储、工具
│  ├─ db/           Drift 表定义与 AppDatabase
│  ├─ secure/       API Key 读写
│  ├─ theme/        Material 3 主题 + 阅读器主题
│  └─ util/         文本统计、时间格式化
├─ features/
│  ├─ notes/        笔记 CRUD + 列表 + 编辑
│  ├─ ai/           DeepSeek 客户端、提示词、AI 面板
│  ├─ cards/        SM-2 调度器、卡片生成、复习页
│  ├─ reader/       沉浸阅读模式
│  └─ settings/     API Key、模型、偏好
└─ main.dart
```

依赖方向严格单向：`ui → domain → data → core`。**UI 不直接 import `dio`，也不直接写 SQL。**

## 4. DeepSeek 接入设计

### 4.1 接口事实（已核对官方文档）

| 项 | 值 |
|---|---|
| Base URL（OpenAI 格式） | `https://api.deepseek.com` |
| Base URL（Anthropic 格式） | `https://api.deepseek.com/anthropic` |
| 对话端点 | `POST /chat/completions` |
| 模型 | `deepseek-flash`、`deepseek-v4-pro` |
| 上下文长度 | 1M |
| 最大输出 | 384K |
| JSON Output | 两个模型都支持 |
| Tool Calls | 两个模型都支持 |
| 思考模式开关 | `{"thinking": {"type": "enabled" \| "disabled"}}` |
| 思考强度 | `reasoning_effort: "low" \| "high" \| "max"` |
| 思维链返回字段 | `reasoning_content`（与 `content` 同级） |

**⚠️ 最重要的过时信息**：网上绝大多数中文教程仍在用 `deepseek-chat` 和 `deepseek-reasoner` 这两个模型名。按当前官方文档，模型名应使用 **`deepseek-flash`** 与 **`deepseek-v4-pro`**；文档特别说明模型名请使用 `deepseek-flash`。

### 4.2 三个容易踩的坑

**坑 1：思考模式默认是开的。**
官方原文：思考模式**默认打开，且 effort 默认为 `high`**。这意味着如果你不显式关闭，每一次"帮我加个标签"的轻量请求都会走完整推理链——**又慢又贵**。所以：

- 轻量任务（自动打标签、摘要一句话）→ 显式 `thinking: {"type": "disabled"}`
- 重任务（整理笔记结构、生成卡片、深度问答）→ `thinking: {"type": "enabled"}` + 合适的 `reasoning_effort`

**坑 2：思考模式下 `temperature` 失效。**
官方原文：思考模式不支持 `temperature`、`presence_penalty`、`frequency_penalty`，**设置了不报错但也不生效**。所以不要指望"调低 temperature 让输出更稳定"，稳定性要靠 prompt 约束 + JSON Output。

**坑 3：JSON Output 有概率返回空 content。**
官方原文承认：使用 JSON Output 时 **API 有概率返回空的 content**。因此解析层必须做：

```
尝试解析 → 失败则重试 1 次（可带更强约束的提示词）→ 仍失败则降级到正则提取 ```json 代码块 → 最后抛业务异常并保留原文给用户手动确认
```

### 4.3 费用模型与省钱策略

价格为每百万 tokens、人民币（[官方价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)）：

| 时段 | 模型 | 输入(缓存命中) | 输入(未命中) | 输出 |
|---|---|---|---|---|
| 空闲 | deepseek-flash | 0.02 元 | 1 元 | 4 元 |
| 高峰 | deepseek-flash | 0.04 元 | 2 元 | 8 元 |
| 空闲 | deepseek-v4-pro | 0.15 元 | 4.5 元 | 13.5 元 |
| 高峰 | deepseek-v4-pro | 0.30 元 | 9.0 元 | 27 元 |

**空闲时段价格是高峰的一半。** 高峰 = 北京时间周一至周五（非法定节假日）9:00–12:00、14:00–18:00，其余（含周末、节假日全天）都是空闲时段。

可落地的三条省钱策略：

1. **默认用 flash**，只在用户显式点"深度整理"时才用 pro。
2. **批量而非零散**：卡片生成一次处理整篇笔记，而不是每段一次请求——省掉重复的系统提示词输入。
3. **缓存命中要靠前缀稳定**：系统提示词与笔记正文的前缀保持一致，命中缓存后输入成本降到 1/50。所以**不要把时间戳、随机 ID 放在 prompt 开头**。
4. 可选：非紧急的批量任务（如给全部旧笔记补标签）提示用户"建议在空闲时段执行"。

### 4.4 调用分层

```dart
// features/ai/data/deepseek_client.dart   负责 HTTP + 流式 + 错误映射
// features/ai/domain/prompts.dart         负责提示词与 JSON schema 约定
// features/ai/domain/ai_repository.dart   负责业务：摘要/标签/卡片/问答 + 落库
```

UI 只与 `AiRepository` 打交道，拿到的是 `Stream<AiEvent>`：`AiChunk`（增量文本）、`AiReasoning`（思维链，可折叠展示）、`AiDone`、`AiError`。

## 5. 记忆卡片：算法先讲清楚

### 5.1 卡片从哪来

两条来源，都要做：

1. **AI 生成**：笔记正文 → 模型输出结构化的 `{question, answer, tags}` 数组 → 用户逐条确认/编辑后入库。**必须有人工确认环节**，AI 直接入库会产生大量劣质卡片，污染复习队列。
2. **手动标记**：阅读时选中一段 → "做成卡片"。

### 5.2 调度算法：SM-2（首版）

选择 SM-2 而不是 Anki 的 FSRS：

- SM-2 逻辑只有 20 行，纯 Dart 可单测，无参数依赖
- FSRS 需要 4 个模型参数，通常要靠大量个人复习历史拟合才有收益
- 数据模型预留了 `stability`/`difficulty` 字段（见数据模型文档），未来迁移 FSRS 不用改表

评分简化为 4 档，映射到 SM-2 的 quality：

| 按钮 | quality | 行为 |
|---|---|---|
| 忘记了 | 1 | 重置 `repetitions=0`，间隔回到 1 天，EF 减 0.20 |
| 有点难 | 3 | 间隔按 EF 增长，EF 减 0.14 |
| 记得 | 4 | 间隔按 EF 增长，EF 不变 |
| 太简单 | 5 | 间隔按 EF 增长，EF 加 0.10 |

公式：

```
EF' = clamp(EF + (0.1 - (5-q) * (0.08 + (5-q) * 0.02)), 1.3, 2.8)

第 1 次答对: interval = 1 天
第 2 次答对: interval = 6 天
第 n 次答对: interval = round(interval_prev * EF')
```

**EF 下限 1.3 是 SM-2 的经典值；上限我加到了 2.8**，否则长期记忆好的用户会拿到离谱的长间隔（比如 3 年后），在笔记类应用里没有意义。

### 5.3 复习队列的选取

"今日待复习"的定义：`due_at <= 今天 23:59:59`，按 `due_at ASC` 排序，**新卡（`repetitions = 0`）混入但要限量**（比如每天最多 15 张新卡），避免积压时一次性砸给用户。

更完整的 SQL 与索引设计见 [02-数据模型设计.md](02-数据模型设计.md)。

## 6. 阅读模式设计

「提供阅读」有三种可能的理解，我按可叠加的三层来做：

| 层 | 内容 | 实现要点 |
|---|---|---|
| L1 沉浸阅读 | 隐藏所有 chrome，纯正文，可调字号/行距/主题（日/夜/护眼） | 全屏路由 + `SystemChrome.setEnabledSystemUIMode` |
| L2 结构化速读 | 顶部固定 AI 摘要卡（要点 + 标签），支持"只看要点 / 看全文"切换 | 摘要存 `note_summaries` 表，离线可看 |
| L3 朗读 | `flutter_tts` 把正文或摘要读出来 | 首版可延后；作为后台听读入口 |

首版做 L1 + L2，L3 列入 v1.1。

阅读进度要持久化（`note.readingProgress` + `readingSeconds`），这样「继续阅读」才有意义，也为后续统计"我在哪篇笔记上花了多少时间"打基础。

## 7. 架构总览

```
┌─────────────────────────────────────────────────────────┐
│                     Flutter UI (Material 3)             │

                │ Watch (Stream)          │ 用户动作
                ▼                         ▼
┌───────────────────────────┐  ┌─────────────────────────┐
│  AppDatabase (Drift)      │  │  AiRepository           │
│  ─────────────────────    │  │  ─────────────────────  │

## 8. 关键风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Dart/Flutter SDK 版本太旧 | 装不上 drift 2.33+ | 项目已固定 `sdk: ^3.10.0`；用 `flutter --version` 先确认 |
| build_runner 与生成器版本不匹配 | `drift_dev` 编译失败 | pubspec 里已 `dependency_overrides` 固定 `analyzer` / `build_runner_core`（见骨架文件注释） |
| Drift 3.x 迁移到 build hooks | 依赖声明方式变化 | 首版锁 `drift: ^2.35.2`；升级时按官方 `sqlite3` build hooks 文档调整 |
| DeepSeek 返回空 JSON content | 卡片生成失败 | 三级降级：重试 → 正则抽代码块 → 抛业务异常保留原文 |
| 思考模式默认开启导致费用超预期 | 成本 | 默认 `disabled`，仅重任务显式开启；`ai_calls` 表记录每次 token 用量，设置页展示累计成本 |
| API Key 泄漏 | 资金损失 | 仅存设备 `flutter_secure_storage`；不写日志；`ai_calls` 表不存 prompt 全文（可选开关） |
| Android 复杂查询 OOM | 崩溃 | `sqlite3.tempDirectory` 指向应用临时目录 |
| 中文分词与全文检索 | 搜索体验差 | 首版用 `LIKE`；v1.1 引入 FTS5（中文需配 trigram 或 jieba 分词） |
