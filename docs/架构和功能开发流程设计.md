## 一、分层总览

```
lib/
├─ main.dart        进程入口：依赖装配 + 启动前自检 + 换库
├─ app/             应用级 UI 骨架（不是入口）
│  ├─ app_shell.dart        底部导航外壳（轻笔记 / 笔记库 / 设置）
│  ├─ seed_bootstrap.dart   启动时写示例数据
│  └─ api_key_file.dart     从文件读 API Key（开发/调试用）
├─ core/            与具体功能无关的基础设施
│  ├─ app_info.dart         产品名 / 版本 / 包名（唯一来源）
│  ├─ backup/               整库 .zip 备份与恢复（5 个文件）
│  ├─ db/                   Drift 连接、查询、表定义、数据库位置
│  ├─ prefs/                轻量偏好（主题、字号、搜索历史）
│  ├─ secure/               系统钥匙串（API Key）
│  ├─ seed/                 首次启动的示例数据
│  ├─ theme/                Material 3 主题与尺寸常量
│  ├─ util/                 纯函数（文本统计、AI 限额）
│  └─ widgets/              跨功能复用组件（log_bar.dart）
└─ features/        业务功能，一功能一目录
   ├─ ai/          data(2) / domain(10) / ui(3)
   ├─ note/        data(6) / domain(5) / ui(11)
   └─ settings/    ui(8)
```

注意两件容易被旧印象带偏的事：

- `core/` 下**没有 `export/`**。Markdown 导出功能已取消，整库与单篇的搬家用的是 `core/backup/` 的 `.zip` 备份包。
- `features/` 下**只有三个目录**。早先的 `notebooks/` `reader/` `card/` `review/` 都已不存在（前两个并入或删除，后两个随记忆卡片功能整体移除）。

### 四个位置的判断标准

| 位置 | 放什么 | 判断标准 |
|---|---|---|
| `main.dart` | 进程入口：`runApp` 之前要做的事 | 只有启动相关代码能进来 |
| `app/` | 应用整体的 UI 骨架 | 「换掉某个 feature 它也不用改」的 UI |
| `core/` | 被多个 feature 依赖的基础设施 | **删掉任何一个 feature，它依然要存在** |
| `features/` | 业务功能 | 删掉它，App 少一块能力 |

最容易搞错的是 `core/` 和 `features/` 的边界。一条判据：

> 这个文件**只服务于某一个功能**吗？
> 是 → `features/<那个功能>/`；否 → `core/`。

例：`backup_service` 只被设置页调用，但它处理的是整库导出与恢复、不隶属任何单个功能，所以进 `core/backup/`。

## 二、features/ 内部：data / domain / ui

| 目录 | 放什么 | 本项目的实例 |
|---|---|---|
| `data/` | 与外部打交道：数据库、网络、文件 | `note_repository.dart`、`notebook_repository.dart`、`search_service.dart`、`deepseek_client.dart` |
| `domain/` | 业务规则与业务编排，产出可被 UI 直接调用的接口 | `note_chunker.dart`（纯切分算法）、`prompts.dart`、`agent_loop.dart`、`ai_repository.dart`、`ai_chat_repository.dart` |
| `ui/` | 页面与组件 | `inbox_page.dart`、`library_page.dart`、`note_editor_page.dart` |

**不是每个 feature 都要三层。** `settings/` 只有 `ui/`（`ui/pages/` 各子页 + `ui/widgets/` 共用骨架）——它没有自己的表，也没有自己的业务算法。空目录不要建：`analyze` 不报错，只会让人困惑。

### 一条容易搞错的边界：仓储不一定在 `data/`

`ai/` 把仓储分在了两处：

- `ai/data/deepseek_client.dart` —— 只管 HTTP、流式、错误映射；`ai/data/deepseek_config.dart` 只管模型名、定价、用量类型
- `ai/domain/ai_repository.dart` —— 业务封装（整理、生成卡片、问答）+ 用量落库
- `ai/domain/ai_chat_repository.dart` —— 多轮会话、工作区、Agent 驱动与历史落库

所以「repository 一律放 `data/`」是错的。判据是它**碰什么**：

- 只碰 HTTP / DB / 文件 → `data/`
- 带业务编排、要串多个 IO 步骤、要维护业务不变量 → `domain/`

## 三、依赖方向：实际规则

按 import 实测，成立的是下面五条：

| # | 规则 | 实测 |
|---|---|---|
| 1 | `data/` 与 `domain/` 都不 import `ui/` | 0 处 |
| 2 | `core/` 不反向依赖 `features/` | 1 处例外，见下 |
| 3 | `ui/` **可以**直接 import 本功能（及跨功能）的 `data/` 仓储 | 11 个 ui 文件这么做 |
| 4 | `ui/` **不** import `package:dio`，**不** import `package:drift` | 0 处 |
| 5 | 跨 feature import 允许，但要能说清方向 | `note/data/feed_repository.dart` → `ai/domain/ai_repository.dart`；`ai/domain/tool_executor.dart` → `note/data/*_repository.dart` |

**一句话记法：允许 UI 直连仓储，不允许 UI 直连 IO。**

规则 4 是真正被守住的那条边界。UI 拿到的是仓储方法，以及 Drift 的行类型（`Note`、`Notebook`、`AiCall`…，经 `core/db/app_database.dart` 与 `core/db/models.dart` 导出）——所以 ui 文件会 import `core/db/app_database.dart`，但那是为了**类型**，不是为了自己拼 SQL。

规则 2 的唯一例外是 `core/seed/seed_data.dart`：它直接 import `features/note/data/` 的两个仓储来写示例数据。这条约束 `core/db/app_database.dart` 的注释里明确写着（切片器与 `NoteChunk` 类型因此留在 `features/note/`），seed 是已知的破例。

## 四、状态管理与数据流

### 4.1 provider 只做依赖装配

`lib/` 全目录**没有任何 `ChangeNotifier` / `ChangeNotifierProvider` / `notifyListeners`**。`package:provider` 的用法只有两种：

1. `main.dart` 里注册：`Provider` / `ProxyProvider` / `ProxyProvider2`
2. 页面里取用：`context.read<T>()`

`main.dart` 的 `MultiProvider` 注册清单（顺序即依赖顺序）：

| 注册类型 | 依赖 |
|---|---|
| `AppDatabase` | 无（`dispose` 时 `close()`） |
| `DeepSeekClient` | 无 |
| `FileDialogs` | 无 |
| `NotebookRepository` / `NoteRepository` / `SearchService` / `PreferencesService` / `BackupService` | `AppDatabase` |
| `AiRepository` | `AppDatabase` + `DeepSeekClient` |
| `FeedRepository` | `AppDatabase` + `AiRepository` |
| `AiChatRepository` | `AppDatabase` + `AiRepository` |

两条硬约束，都是代码注释里记着实测踩过的：

1. **顺序即依赖顺序。** `FeedRepository` 依赖 `AiRepository`，必须写在它后面。Provider 是惰性解析的，写反了第一次读取就抛 `Could not find the correct Provider<AiRepository>`。
2. **注册了才能读。** `context.read<X>()` 在 `X` 未注册时**不报编译错**，只在运行时抛 `ProviderNotFoundException`。没有静态检查能抓住它，所以每次改完 `MultiProvider` 清单都要人工核对一遍：页面里读到的每个 `X` 都注册过。

### 4.2 界面刷新靠 Drift 的 watch 流

```
写：UI 调仓储方法 → 仓储写 Drift → Drift 通知订阅者
读：UI 在 StreamBuilder 里订阅仓储的 watchXxx() → 数据一变自动重建
```

- `core/db/app_database.dart` 定义 `watchNotes()` / `watchInboxNotes()` / `watchUnfiledNotes()` / `watchLibraryNotes()` / `watchNote(id)` / `watchNotebooks()` 等，返回 `Stream<...>`
- `features/*/data/*_repository.dart` 把它们转出去（`note_repository.dart` 5 个、`notebook_repository.dart` 1 个、`ai_chat_repository.dart` 2 个）
- 页面用 `StreamBuilder` 消费：11 个文件用到 `StreamBuilder`（`main.dart`、`inbox_page`、`library_page`、`notebook_detail_page`、`search_page`、`ai_page`、`workspace_sheet`、`notebook_picker`、`settings_page`、`appearance_settings_page`、`usage_settings_page`）

结论：**刷新列表不需要手工通知**，当前也没有这类代码。页面自身的临时状态（输入框、选中项、加载中）用 `StatefulWidget` + `setState`；启动期自检用 `FutureBuilder`。

### 4.3 启动顺序（`main.dart` 实际做的事）

1. `applyPendingImportIfAny()` —— 换库必须发生在**任何数据库连接建立之前**。这一步只做纯文件操作，不碰 drift，所以不会有文件被占用的问题。
2. `unawaited(_publishDbLocation())` —— 把数据库位置写到 App 工作目录的 `.lightnote-storage.txt`，方便在「编译 + 启动」之后直接查看这次用的是哪个库文件。
3. `runApp` → `LightNoteApp` 的 `MultiProvider` → `_AppShell`。
4. 首帧之后（`addPostFrameCallback`）：`AiRepository.init()` 读已保存的 API Key，并播报本次启动的导入结果。**不阻塞启动，也不在 `main` 里 await。**
5. `_StartupGate`：先一次 `SELECT 1` 探活（真正触发建库与迁移，失败在这里被抓住而不是在某个页面的 `StreamBuilder` 里炸开）→ 再 `SeedBootstrap.run(...)` 写示例数据 → 通过才进 `HomeShell`。

## 五、日常开发循环

一句话版：**改代码 → 保存 → `flutter run -d windows`**（进程还开着时按 `r` 热重载）。数据不会丢（理由见第六节）。

```
1. 在工程根目录打开终端
2. 改 lib\ 里的 .dart 文件
3. 保存
4. flutter run -d windows
5. 终端出现 Flutter run key commands、App 窗口弹出来 = 成功
```

热重载（`r`）只重建 Dart 代码：改了 `pubspec.yaml` 的依赖、原生插件或 `windows\` 下的东西，要按 `R` 重启，或者重新 `flutter run`。

### 怎么看数据落在哪

启动后 App 会把这次的数据库位置摘要写进**它自己工作目录**（exe 所在目录）下的 `.lightnote-storage.txt`，内容是 `path=` / `private=` / `degradedProgramDir=` 这样的键值行；App 内「设置 → 存储位置」显示的是同一个值。**`path=` 那行就是「我的数据在哪」的答案。**

其中一行需要格外注意：`degradedProgramDir=true` 表示常规位置都不可写、数据临时退到了程序目录里 —— 这种情况下**删 `build\` 会连数据一起删**，第一件事就是去「设置 → 存储位置」把它换到安全目录。

由环境变量指定位置时会多一行 `envOverride=true`（即「由环境变量 LIGHTNOTE_DB_DIR 指定」）。

### 编译要多久

以下是原《开发流程》的**经验值，本次未逐项计时复测**，只当量级参考（随机器、缓存状态差异很大）：

| 改了什么 | 大约耗时 |
|---|---|
| 只改文案 / 界面 | 8–20 秒 |
| 改了多处逻辑 | 15–30 秒 |
| 加了新依赖 | 1–3 分钟（要下载） |
| `flutter clean` 之后第一次 | 约 50 秒 |

不用背这张表：第一次编译和改动范围大的时候自然会慢，以实际输出的耗时为准。

## 六、数据会不会丢

**不会。** 因为数据根本不在工程目录里。

| 东西 | 在哪 | 重新编译会怎样 |
|---|---|---|
| **笔记数据库** | App 私有目录（「设置 → 存储位置」显示的那个；路径以启动时写下的 `.lightnote-storage.txt` 为准） | **完全不受影响** |
| 编译产物 | `build\` | 被覆盖 / 可随时删 |
| Dart 中间状态 | `.dart_tool\` | 被覆盖 / 可随时删 |
| 源码 | `lib\` `test\` `docs\` | 你不动它就不动 |

编译只碰 `build\` 和 `.dart_tool\`。数据库在 App 私有目录里，两者毫不相干。

### 唯一例外

如果位置报告里是 `degradedProgramDir=true`，说明常规位置都写不进去、数据退到了 `build\` 下面——那种情况下**删 `build\` 就会连数据一起删**。
第一件事是去「设置 → 存储位置 → 更换工作目录」把它搬到安全的地方。

### 这些操作都不会丢数据

- 改代码、重新编译
- `flutter clean`
- 删 `build\` 目录
- 删 `.dart_tool\` 目录
- 关掉 App 再打开
- 电脑重启

### 这些操作会丢数据

| 操作 | 后果 | 怎么避免 |
|---|---|---|
| 删 App 私有目录（「设置 → 存储位置」显示的那个） | 笔记全没 | 先导出备份包 |
| 卸载 / 重装 App（Android 上卸载会清私有目录） | 笔记全没 | 先导出备份包 |
| 手工改 `lightnote.sqlite` | 库损坏 | 别用别的工具去写它 |
| 删掉 App 工作目录里的 `lightnote.sqlite` | 笔记全没 | 同上 |

### 保险做法：定期导出备份

「设置 → 导出备份包（.zip）」→ 选个位置（比如 D 盘或网盘同步目录）。换电脑、换手机、重装系统都能恢复。

备份的实际实现（已对着 `lib/core/backup/` 核实）：

- 导出用 SQLite 的 **`VACUUM INTO`** 做一致性快照，**不是 `File.copy`** —— 直接拷正在使用的库文件可能得到「少了最后一次提交」甚至撕裂的库
- 快照再打成一个普通 zip，内含 `data/lightnote.sqlite` 与清单 `backup.json`（`kBackupFormatVersion = 1`）
- 导出**只在用户选定的位置生成一份**，不再往私有目录另留（`autoBackupFolder` / `listAutoBackups` 已一并删除），默认文件名形如 `LightNote-20260213-1045.zip`
- 导入**只读不写**地先校验：zip 能否解开、清单是否存在且合法、库的 schemaVersion 是否兼容、再对解出来的库做一次真实的完整性检查。**损坏的包会被拒绝，而不是把现有库弄坏**
- 换工作目录走的也是快照（`snapshotToNewFile`），不是文件拷贝

## 七、什么时候需要多做一步

### 情况 1：改了数据库表结构

改 `lib/core/db/tables.dart` 之后要跑 `build_runner` 并处理老库。**完整步骤与完成标志见第八节第 2 步**（不在这里重复一遍，免得两处维护）。

### 情况 2：加了新依赖

改 `pubspec.yaml` 之后：

```powershell
flutter pub get
```

然后正常编译。第一次会因为下载依赖慢一点（1–3 分钟）。

### 情况 3：想跑测试 / 看静态分析

```powershell
flutter test              # 跑测试
flutter analyze           # 静态分析
flutter build windows     # 编译，确认真的能过
```

> ⚠️ `flutter analyze` 对刚保存的改动**有缓存延迟**，偶尔会说
> `No issues found` 而实际编译报错。**以 `build` 的结果为准。**

三件事都干净（analyze 无 issue、test 全绿、build 成功）才算这一步过了。

### 情况 4：想在手机上看效果

```powershell
flutter build apk --release
```

约 **6 分钟**（首次更久，Gradle 要下依赖）。产物在 `build\app\outputs\flutter-apk\`：

```
build\app\outputs\flutter-apk\
└── app-release.apk    可直接安装的 release 包
```

**装到手机**（任选）：

- 把 apk 拷到手机（数据线 / 微信文件传输 / 网盘），点开安装
- 手机开 USB 调试，连上电脑后：`adb install -r build\app\outputs\flutter-apk\app-release.apk`

几点已核实的事实：

- **可以只出 arm64-v8a**：`flutter build apk --release --target-platform android-arm64`；不加这个参数就按 Flutter 默认输出该版本包含的 ABI
- 签名分两种：**配了 `android/key.properties` 就用你自己的发布密钥；没配就回退 debug 签名**（`android/app/build.gradle.kts`）。回退是给本地调试留的方便 —— 这样的包能直接装、能覆盖升级，但**不能上架**，而且一旦装过 debug 签名的包，将来换正式签名必须先卸载（用户数据会丢）。正式发布前先生成密钥并建 `key.properties`（两个文件都已被 `.gitignore` 挡住）：
  ```
  keytool -genkey -v -keystore android\lightnote.jks -keyalg RSA -keysize 2048 -validity 10000 -alias lightnote
  ```
  `android/key.properties` 里写 `storePassword` / `keyPassword` / `keyAlias` / `storeFile=../lightnote.jks`。**这个 `.jks` 与两个密码丢了就再也无法更新已发布的 App**，必须离线备份
- 包名 / applicationId 实测为 `com.lightnote.app`（`android/app/build.gradle.kts` 的 `namespace` 与 `applicationId`，与 `core/app_info.dart` 的 `kAppPackageId` 一致）
- 手机上数据库在 App 私有目录里，和桌面版是**两套独立数据**——手机上的笔记不会同步到电脑。要搬数据用「设置 → 导出备份包」，在另一端「从备份包导入」。**具体路径以 App 内「设置 → 存储位置」显示的为准**，不要在文档里写死

### 情况 5：改了版本号

**只改两个地方**（没有任何机制会自动同步，但只有这两处需要动）：

| 文件 | 改什么 |
|---|---|
| `pubspec.yaml` | `version: 1.0.0+2` ← **源头**。Android 的 `versionName` / `versionCode` 与 Windows 的 exe 版本资源都由它派生 |
| `lib/core/app_info.dart` | `kAppVersion` ← Dart 运行时读不到 pubspec，所以复制一份（关于页显示、写进备份清单） |

> `windows/runner/Runner.rc` 里也有个 `"1.0.0"`，那是**模板兜底值**（Flutter 没把版本传进去时才用），
> 正常**不用动** —— 实际的 exe 版本资源来自 `pubspec.yaml`，这一点可以用
> `windows/flutter/ephemeral/generated_config.cmake` 里的 `FLUTTER_VERSION` 验证。

**`+2` 是构建号**，和 `1.0.0` 是两回事：同一个版本号可以发多次，每次构建号 +1
（应用商店要求它只增不减）。

漏改 `app_info.dart` 就会出现「任务栏/exe 叫一个版本、关于页叫另一个版本」。

## 八、加一个新功能的完整流程

### 第 1 步：把要做什么写进对应的设计文档

**没有单独的规格书目录了**（曾经有过 `docs/specs/`，已撤销）。现在改动**直接写进对应的设计文档**：
界面改动写进 [界面设计](界面设计.md)，表改动写进 [数据库设计](数据库设计.md)，
AI 行为写进 [AI接入设计](AI接入设计.md)，依此类推。

写之前先想清两件事：**新增哪些文件**、**要不要新建 feature**。

第 6 节要顺手回答两件事：**新增哪些文件**、**要不要新建 feature**。

判断该不该新建 feature：

- 它有自己的数据表吗？有 → 新 feature
- 它会出现在底部导航或设置首页吗？会 → 新 feature
- 只是现有功能的一个新页面？→ **不新建**，放进现有 feature

**做完的标志**

- 九节没有空节；没想清楚的地方标 `TODO` 而不是留空
- 「明确不做」写了（范围蔓延时这就是依据）
- 验收标准每条都能判定，不出现「体验流畅」这类没法判的词
- 第 6 节的文件清单里，每个文件都能按 `<名词>_<角色>.dart` 起个名

### 第 2 步：建表 / 改表

没碰表就跳过这步。

1. `lib/core/db/tables.dart` 加表或改字段（表名用复数，feature 目录名用单数）
2. 升版本号：`kCurrentSchemaVersion`（在 `lib/core/db/database_location.dart`，当前 = **11**）
3. 迁移写进 `lib/core/db/app_database.dart` 的 `MigrationStrategy.onUpgrade`，按 `if (from < 12) { ... }` 追加。**不要修改已有的 `from < N` 分支** —— 老库升级路径已经被 `test/migration_test.dart` 锁住了。
4. 跑 `dart run build_runner build`（不跑会报 `app_database.g.dart` 相关的错）

5. 同步改 [数据库设计](数据库设计.md)

开发期最省事的做法是让 App 重建库：导出备份 → 删掉 `lightnote.sqlite` → 重开 App（建新结构空库 + 种子数据）→ 需要老数据就导入备份。**一旦对外发布过就不能这么干，必须写迁移。**

**做完的标志**

- `dart run build_runner build` 无错，`app_database.g.dart` 已更新
- `test/migration_test.dart` 覆盖了这条新迁移
- 删库重建后功能正常，且**同时**验证过从老版本库升级上来（`from < 12` 分支真的跑过）
- 表结构改动没有只改 `tables.dart` 而漏掉文档

### 第 3 步：数据层

1. 在 `features/<功能>/data/` 建 `xxx_repository.dart`，构造函数**收** `AppDatabase`——不要自己 new 数据库，不要收 `BuildContext`
2. 读：转出 `watchXxx()` 的 `Stream`，让 UI 能 `StreamBuilder` 订阅
3. 写：给出语义化方法（如 `createInNotebook` / `moveToNotebook`），派生字段（`updatedAt` / `excerpt` / `wordCount` / 切片）在仓储里统一维护，**别让页面自己填**——页面漏填一次就是一处数据不一致
4. 需要访问已有数据时，**走现有仓储**，不要新建直连数据库的类
5. 在 `lib/main.dart` 的 `MultiProvider` 里注册，**排在它依赖的 Provider 之后**。`ProxyProvider` / `ProxyProvider2` 的写法照抄相邻那几行即可

**做完的标志**

- 页面里读到的每个 `X` 都在 `main.dart` 的 `MultiProvider` 里注册过（`flutter analyze` 抓不到这个问题，只能人工核对）
- 全工程搜不到第二个自己开 SQLite 连接的地方
- 仓储里没有 `BuildContext` 参数，测试可以不经 widget 树直接调用它
- 派生字段只有一个写入点

### 第 4 步：UI

1. 整屏页面进 `features/<功能>/ui/`，复用组件进 `ui/widgets/`（有 `Scaffold` 的才叫 `_page`）
2. 数据只从 `context.read<XxxRepository>()` 拿；列表用 `StreamBuilder` 订阅 `watch` 流
3. 不 import `package:dio`、不 import `package:drift`、不写 SQL 字符串
4. 提示统一走 `core/widgets/log_bar.dart`。级别规则：挡住操作 → `error`；结果不合预期 → `warn`；做成了 → `success`；纯告知 → `info`。用了 `SnackBarAction` 必须显式 `persist`，用了 `LogBar.busy` 必须 `try/finally` 收起
5. 资源配对：`TextEditingController` / `StreamSubscription` / `Timer` / `ScrollController` 都在 `dispose` 里释放
6. `await` 之后用 `context` 前检查 `mounted`；`Navigator.pop` 前先取好 `ScaffoldMessenger.of(context)`
7. 破坏性操作（删数据、换库）要二次确认

**做完的标志**

- 首帧就有数据或明确的空状态，不出现「先空一下再刷新」
- `lib/features/**/ui/` 下搜不到 `package:dio` 与 `package:drift` 的 import
- 退出页面时控制台没有「`setState` after dispose」或「stream 还在推数据」的报错
- 提示不会永久驻留（除非有意 `persist`），也不会一闪而过看不到

### 第 5 步：测试

1. 测试放 `test/`，一文件一主题，不建子目录（现有 31 个测试文件）
2. 纯算法测纯函数（如 `note_chunker_test.dart`）；数据层可直接用 `AppDatabase.forTesting(...)`；界面用 `testWidgets`
3. 跑：

```powershell
flutter test              # 全部测试
flutter analyze           # 静态分析
flutter build windows     # 编译，确认真的能过
```

**做完的标志**

- analyze / test / build 三项都干净 —— 注意不是只有 `test` 绿
- 新增的失败分支（没网、磁盘满、数据为空、重复点击）至少各有一条测试或一条明确的手工验证记录
- 测试的组织方式与 [测试设计](测试设计.md) 一致

### 第 6 步：文档同步

按「一个文档只记录一个事情」落到对应文件：

| 改了什么 | 改哪份 |
|---|---|
| 表、字段、索引、迁移 | [数据库设计](数据库设计.md) |
| 页面、交互、视觉规范 | [界面设计](界面设计.md) |
| 新目录、新的命名角色 | [目录设计](目录设计.md) |
| 依赖、构建方式、平台支持 | [技术栈设计](技术栈设计.md) |
| 产品行为与边界 | [核心功能设计](核心功能设计.md) |
| 分层规则或本文流程变了 | 本文 |
| 功能本身 | 对应的设计文档（[界面设计](界面设计.md) / [数据库设计](数据库设计.md) / [AI接入设计](AI接入设计.md) 等） |

**做完的标志**

- 规格书第 7 节的验收标准逐条勾掉
- 上表里受影响的文档都改了；没有受影响的就是「无」
- 没有新建带数字前缀的文档（用户定的规则：文件名直接命名）
- 没有把字段清单、页面清单抄进本文

## 九、出问题了怎么办

### 1.「打不开本地数据库」

App 会进入一张诊断页（`main.dart` 的 `_StartupErrorScreen`，标题原文就是「打不开本地数据库」），上面列了每个候选位置**各自的失败原因**。

**首先那不是数据丢了** —— 原来的文件还在磁盘上，只是这次没访问到。页面里也写了常见原因：磁盘已满或为只读 / 安全软件或企业策略拦了 AppData 与文档目录 / 以受限账户运行。

临时办法：设一个环境变量指定位置，然后重新打开 App。

```powershell
setx LIGHTNOTE_DB_DIR "D:\我的笔记数据"
```

重开终端后生效。想撤销：`setx LIGHTNOTE_DB_DIR ""`。
（这个变量名就是 `DatabaseLocation.envOverride` 的值；由它生效时位置报告里会多一行 `envOverride=true`。）

### 2. App 里笔记看起来「没了」

先看这次启动写下的 `.lightnote-storage.txt` 里 `path=` 那一行。如果它显示的位置和你以为的不一样，说明 App 换了位置去找库（降级了）。按上一条的办法固定位置。

### 3. 报 `CMakeCache.txt directory ... is different`

`build\` 里的 CMake 缓存写死了旧的源码路径（工程目录被搬过家）。删掉重来：

```powershell
Remove-Item -Recurse -Force build\windows
flutter run -d windows
```

### 上传前想确认一切正常

```powershell
flutter analyze
flutter test
flutter build windows --release
```

三件事都干净就可以放心，release 产物在 `build\windows\x64\runner\Release\`。

## 十、不要做的事

| ❌ 别做 | ✅ 改成 |
|---|---|
| 把工程目录搬到别处后直接编译 | 先删 `build\windows` 让 CMake 重新生成缓存（原因见第九节第 3 条） |
| 手工改 `build\` 里的东西 | 那些是生成物，改了下次编译就被覆盖 |
| 手工改 `*.g.dart` | 同上；改 `tables.dart` 后跑 `build_runner` |
| 用别的工具（DB Browser 等）**写** `lightnote.sqlite` | 可以只读查看；要改数据请用 App 或导入备份包 |
| 在代码或文档里写死数据库路径 | 以启动时写下的 `.lightnote-storage.txt` / 「设置 → 存储位置」为准 |

## 十一、完整命令速查

以下命令都在工程根目录执行。

```powershell
# 日常
flutter run -d windows                     # 编译 + 启动；终端里按 r 热重载、R 重启

# 分开做
flutter analyze                            # 静态分析
flutter test                               # 跑测试
flutter pub get                            # 拉依赖
flutter build windows --debug              # 只编译 debug
flutter build windows --release            # 编译 release，产物在 build\windows\x64\runner\Release\
flutter build apk --release                # 打 APK，产物在 build\app\outputs\flutter-apk\
flutter build apk --release --target-platform android-arm64   # 只出 arm64-v8a
flutter doctor                             # 环境自检
flutter doctor --android-licenses          # 接受 Android SDK 许可（首次装 SDK 时用一次）

# 深度排查
dart run tool\inspect_db.dart               # 直接看数据库内容（表/索引/行数）
dart run tool\inspect_db.dart <库文件>       # 看指定文件

# 改了表结构之后
dart run build_runner build
```

几点说明：

- `flutter analyze` 有缓存延迟，刚保存的改动偶尔漏报，**以 `flutter build` 的结果为准**
- `dart run tool\inspect_db.dart` 不带参数时用的是代码里写的一个**猜测**路径，未必就是真实位置。最稳的是把「设置 → 存储位置」显示的路径当参数传进去
