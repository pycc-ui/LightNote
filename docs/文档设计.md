# 文档设计

这份文档管 `docs/` 的规则：文档放哪、拆几份、怎么互相引用、叫什么名字。
具体某块的设计（数据库有几个字段之类）不在这里。

---

## 1. 所有文档都放在 `docs/` 里

**要求**：除了仓库首页，其它 Markdown 文档都放在 `docs/` 下。不允许散落在 `tool/`、`lib/`、
根目录（首页除外）或新增的其它位置。

**为什么**：

- **只有一个地方要找**。想知道"这个仓库有哪些文档"，看一个目录就够了。
- **搬迁只发生在一个目录内**。文档改名、拆分、合并都落在 `docs/` 里，代码目录的树不会被文档搅乱。
- **索引能管住**。`README.md` 的两张表能覆盖全部文档，前提是它们都在同一层。

**现状**：`docs/` 顶层有 11 个 `.md`（10 份设计文档 + `README.md` 索引）。全仓库的 `.md` 一共 12 个，
`docs/` 之外只有一个：根目录的 `README.md`。

**怎么查**：

```powershell
# 应只输出 README.md（仓库首页）
Get-ChildItem -Recurse -File -Filter *.md |
  Where-Object { $_.FullName -notmatch '\\(build|\.dart_tool|\.git|\.idea|windows|android|__pycache__)\\' -and
                 $_.FullName -notmatch '\\docs\\' }
```

输出里出现除 `README.md` 以外的任何路径 = 违规。

**边界情况**：

唯一例外是根目录 `README.md`，这是定案。它的定位是仓库首页——GitHub / 编辑器打开仓库第一眼看到的就是它，
面向"第一次打开这个仓库的人"：环境状态、目录结构、构建方式、常见问题。所以第 1 条的准确读法是
**除仓库首页 `README.md` 外，所有文档都在 `docs/` 里**。

判断一个文件该不该搬：它讲的是"仓库首页"还是"设计与规范"？后者一律进 `docs/`。搬运后同步所有引用
（见第 3 节）。

其它边界：

- 说明性内容写在文档里，不要写在脚本 / 代码目录里（不要在那里建 `README`）。
- 文档里引用代码用相对路径（`lib/core/theme/dimens.dart`），但不要把代码贴成一节文档放进 `docs/`。
- 根目录 `README.md` 只写"仓库首页"该有的东西（环境、结构、构建、常见问题），具体设计一律链到 `docs/`。

## 2. 一个文档只讲一件事

**要求**：一份文档 = 一个主题。文件名能说出这个主题，正文里不出现第二个并列主题。

**现状**：每份文档讲的那一件事——

| 文档 | 它讲的那一件事 |
|---|---|
| [软件理念设计](软件理念设计.md) | 产品要什么、不要什么（「轻」与「省 token」） |
| [核心功能设计](核心功能设计.md) | 有哪四个核心功能 |
| [技术栈设计](技术栈设计.md) | 为什么选 Flutter / Drift / DeepSeek，放弃了什么 |
| [架构和功能开发流程设计](架构和功能开发流程设计.md) | 代码怎么分层、日常怎么改、出问题怎么办 |
| [数据库设计](数据库设计.md) | 数据存在哪、表与字段、迁移历史 |
| [界面设计](界面设计.md) | 有哪几屏、关键交互与视觉规范 |
| [目录设计](目录设计.md) | 文件放哪、叫什么名字 |
| [测试设计](测试设计.md) | 测了什么、怎么跑 |
| [AI接入设计](AI接入设计.md) | 怎么接 DeepSeek、花多少钱、怎么省 |
| [文档设计](文档设计.md) | 文档怎么写、放哪、叫什么（本文） |

`README.md` 是索引，不参与这条规则。

**为什么**：

- **找东西不用先猜**。"改表要注意什么"必然在《数据库设计》，不存在"可能在架构那篇里"。
- **改动范围清楚**。改一件事只动一份文件，评审只看一份 diff。
- **混在一起的总纲没人敢改**：一份文档什么都写一点，每次改动都牵连它，于是所有人都绕着它走，
  它很快变成最过时的那份。

**怎么判断**（三个自测问句）：

1. **一句话测试**——能不能用一句话说完这份文档，且这句话里不需要"以及 / 还有 / 顺便"？
   曾经的《01-技术选型与架构设计》是"选型**以及**架构**以及** AI 接入**以及**费用**以及**路线图"，
   五个"以及"，就是五件事，所以被拆成了几份。
2. **改动触发测试**——它的"什么时候改它"是不是唯一一类事件？触发条件超过一类，就该拆。
3. **读者测试**——有没有一类读者只关心其中一半？（只想知道"花多少钱"的人，不需要读分层与依赖方向。）

**"一件事"的边界是主题，不是篇幅**：《数据库设计》很长也只是一件事（数据怎么存），
《软件理念设计》只有几行也自成一份（产品要什么、不要什么）。长 != 混，短 != 不配单独成文。

**边界情况**：

- 同一件事的"设计"和"实施步骤"写在**同一份文档**里分节，不要为"步骤"另开一份。
- 被多份文档共用的前提（如"依赖方向"）：放在它自己的那份文档里，其它文档用一两句话重申结论
  （见第 3 条）。
- 一份文档确实是一件事但太长：继续加长，靠节标题和索引定位。拆分的正当理由只有"出现了第二个主题"。
- **拆分收尾动作（必须做）**：更新 `README.md` 的两张表；全仓库搜旧文件名改掉所有引用
  （`git grep 旧文件名`）；去掉数字编号前缀（见第 4 条）。
- **新功能默认不单独开文档**，改动直接写进对应的设计文档——本仓库不用规格书（见第 4 节"子目录"）。

## 3. 文档之间应该独立

**要求**：任取一份文档，单读它就能读懂它讲的那件事：关键前提、结论、判据都在本文之内。
可以链接别的文档做延伸阅读；不许把关键前提只放在别处，让读者必须点过去才看得懂。

**与"链接"的区别**：

|  | 允许 | 不允许 |
|---|---|---|
| 形式 | 读完本文后还想看更多 → 给链接 | 不读另一份就读不懂本文 |
| 例子 | "完整命令速查见《架构和功能开发流程设计》" | "本文的分层规则见《架构和功能开发流程设计》第三节"（本文却没说规则是什么） |

**判据**：把被引用的文档从仓库里删掉，本文还成立吗？成立 → 是延伸链接，可以留；不成立 → 是依赖，
必须把前提搬回本文。

**引用方式**：写文件名或文档标题（`《数据库设计》`、`[数据库设计](数据库设计.md)`），
不要写"见某份文档的第 N 节"——文件名和节号是两个假设，任何一个变了引用就废。文档内部的节引用同理，
优先引节标题，不引节号。

**为什么**：指向"文件的某一节"是最脆的引用——文件名会改、节号会漂、文件会被删，而引用它的地方
遍布文档与代码注释，没人会记得同步。曾经就有注释指向一个根本不存在的文件名、以及指向一个
改过名的旧文档，都成了死链；也有一处写"规范第 7 节"却没说是哪份文档、节号也早换了，
读者照这句话找不到东西。

**怎么查**：

1. **删链接测试**：逐条检查文档里的"见……"，确认被引文档删掉后本文仍成立。
2. **死链检查**：文档里每一处指向 `.md` 的链接，目标文件是否真的存在；代码注释里的 `docs/...`
   路径同样要查（这类最容易被漏掉）。
3. **节号检查**：全文搜 `第 N 节` / `§N`，确认 N 对应的小节标题没变过。

**边界情况**：

- **背景确实在别的文档**：在本文里用一到两句话复述结论（哪怕显得重复），再给链接。重复是可接受的代价。
- **引用代码**：写"文件路径 + 符号名"（`lib/core/db/tables.dart` 的 `Notes` 表），不要写行号——行号天天在变。
- **引用别的文档**：写文件名或标题，不写节号；确实要指某一节时，写节标题而不是节号。

## 4. 文档直接用主题名，不加数字前缀

**要求**：文件名 = 主题名，不加 `01-` / `1_` / `1.` 之类前缀。

**为什么**：

- **编号不携带信息**：看到 `03` 不知道讲什么，看到"目录设计"就知道了。
- **编号会假装有顺序**：本仓库的文档没有阅读顺序，都是按需查的。
- **编号逼着重编号**：往中间插一份新文档，后面的全要改名，git 会把一次"插入"记成一串"删除 + 新增"，
  其它文档里的引用同时失效。
- **编号会和内容解绑**：号码被复用换主题时，历史里只看得到一个删除和一个新增。

**怎么查**：

```powershell
# 应为 0 个
Get-ChildItem docs -Recurse -File | Where-Object { $_.Name -match '^\d+[-_.]' }
```

**命名约定**：`docs/` 顶层的 10 份设计文档全部以"设计"结尾，形如 **`<主题>设计.md`**（`README.md`
是唯一例外，它是索引）。

- 新文档默认叫 `<主题>设计.md`，主题用中文名词（`数据库`、`界面`、`测试`、`AI接入`）。
- **不加日期、不加作者、不加版本号、不加 `-v2` / `-最终版`**。改内容就改同一份文件，版本交给 git。
- 不要英文名或中英混排（现有全是中文名）；`README.md` 这类约定俗成的名字除外。
- 文件名要能被第 2 条的一句话测试包住——起不出名字，通常说明这份文档混了两件事。

**子目录**：

- **`docs/specs/` 已撤销**：本仓库不再使用"规格书"，改动直接写进对应的设计文档。所以不要再往
  `specs/` 加文件，也不要新建 `specs/` 这种**按文档体裁**分类的目录。
- **什么时候才建子目录**：只有一个主题的文档多到一张索引表装不下时才建目录，目录按主题分
  （例如将来表多到一份文档装不下，才考虑 `docs/数据库/`），不按体裁分、不按编号分。
- **当前不建子目录**：10 份设计文档用 `docs/README.md` 一张索引表就能管住，多一层目录只会多一层成本。

## 5. 两条维护约定

### 5.1 文档与代码不一致时，以代码为准，然后改文档

**代码是唯一运行的真相。** 发现不一致当成 bug 修：先确认代码的实际行为，再改文档把它写对。

不允许的两种做法：

- (a) 照着文档去改代码——除非已经确认那处代码是 bug、且确实要改行为；
- (b) 记一句"文档过时了"就放着——按本约定，这是一个未修的 bug。

### 5.2 改表必须同时改 `lib/core/db/tables.dart` 与 [数据库设计](数据库设计.md)

`tables.dart` 的文件头也写了这条提醒。数据模型文档脱节的代价很高（错的字段名会让人写出跑不通的代码，
甚至写出错的迁移），所以单独强调。

顺序：先改 `tables.dart` → 跑 `build_runner` → 写迁移 → 同步 `docs/数据库设计.md`
（至少三处：表结构、已删除的表、迁移历史）。反过来同样成立：只改文档不改表，也是制造不一致，
按 5.1 属于 bug。

## 6. 提交前的自检

```powershell
# 1) docs/ 之外还有没有文档？——应只有 README.md
Get-ChildItem -Recurse -File -Filter *.md |
  Where-Object { $_.FullName -notmatch '\\(build|\.dart_tool|\.git|\.idea|windows|android|__pycache__)\\' -and
                 $_.FullName -notmatch '\\docs\\' }

# 2) 还有没有数字前缀？——应为 0 个
Get-ChildItem docs -Recurse -File | Where-Object { $_.Name -match '^\d+[-_.]' }

# 3) 文档里的 .md 链接目标还在不在？——逐条核对输出
Select-String -Path docs\*.md -Pattern '\]\(([^)]+\.md)\)' | Select-Object Path, LineNumber, Line
```

清单：

- [ ] **只讲一件事**：过了"一句话测试"（不含"以及"），改动触发条件唯一
- [ ] **单读能懂**：关键前提、结论、判据都在本文之内；删掉被引用的文档本文仍成立
- [ ] **文件名**是 `<主题>设计.md`，无数字前缀、无版本号、无日期
- [ ] **没有新增目录**；没有重新引入"规格书"这类按体裁分的目录
- [ ] **引用都有效**：目标是"文件名或标题"，不是节号、不是行号；目标文件存在
- [ ] **更新了 `README.md`** 的两张表
- [ ] **数字与行为以代码为准**，且能指到出处（文件路径 + 符号名）
- [ ] 改了表 → 同时改了 `tables.dart` 与 [数据库设计](数据库设计.md)
