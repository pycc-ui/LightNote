# 文档设计

**本文是 `docs/` 的元规则**：管"文档放哪、拆几份、怎么互相引用、叫什么名字"，
不管"数据库有几个字段"（那是 [数据库设计](数据库设计.md) 的事）。

> **规则来源**：下面四条由项目所有者定稿，原文照录，一字不改。
> 本文其余部分只做一件事——**把它们变成能照着做的判据**：
> 每条讲清「要求什么 / 为什么 / 怎么判断合规 / 边界情况怎么办」。
> 规则本身要改，先改这个引用块。

> 1.所有的文档都应该在这个docs里面
>
> 2.一个文档只记录一个事情
>
> 3.文档和文档间,应该独立
>
> 4.文档直接命名,不适用数字加名字的格式,应该直接命名

---

## 1. 所有的文档都应该在这个 `docs` 里面

### 要求什么

仓库里**除仓库首页外**的所有 Markdown 文档，都放在 `docs/` 下。
不允许散落在 `tool/`、`lib/`、根目录（首页除外）或新增的其它位置。

### 为什么

- **只有一个地方要找**。想知道"这个仓库有哪些文档"，看一个目录就够了，
  不需要 `git ls-files "*.md"` 去猜。
- **搬迁只发生在一个目录内**。文档改名、拆分、合并全都落在 `docs/` 里，
  代码目录的树不会被文档搅乱。
- **索引能管住**。《README》的两张表能覆盖全部文档，前提是它们都在同一层。

### 现状（已核实）

`docs/` 顶层有 **11 个 `.md`**：10 份设计文档 + `README.md`（索引）。
全仓库的 `.md` 一共 **12 个**，`docs/` 之外**只有一个**：根目录的 `README.md`。

| 位置 | 内容 |
|---|---|
| `docs/` 顶层 | 10 份设计文档 + `README.md`（索引） |
| 仓库根目录 | `README.md` —— **唯一例外**，见下 |

### 怎么判断合规

```powershell
# 应只输出 README.md（仓库首页）
Get-ChildItem -Recurse -File -Filter *.md |
  Where-Object { $_.FullName -notmatch '\\(build|\.dart_tool|\.git|\.idea|windows|android|__pycache__)\\' -and
                 $_.FullName -notmatch '\\docs\\' }
```

输出里出现除 `README.md` 以外的任何路径 = 违反第 1 条。

### 边界情况怎么办

**唯一例外：根目录 `README.md`（这是定案，不是遗漏）。**
它的定位是**仓库首页**——GitHub / 编辑器打开这个仓库第一眼看到的就是它，
内容面向"第一次打开这个仓库的人"：环境状态、目录结构、构建方式、常见问题。
`docs/README.md` 里也明确记着它是"**仓库首页**，刻意留在根目录"。
所以第 1 条的准确读法是：**除仓库首页 `README.md` 外，所有文档都在 `docs/` 里。**
它讲的是"这个仓库怎么用起来"，不是"设计与规范"；除此之外的任何 `.md`
留在 `docs/` 外面都算违规。

**判断一个文件该不该搬**：**它讲的是"仓库首页"还是"设计与规范"？**
后者一律进 `docs/`。搬运后必须同步所有引用它的地方（见第 3 节）。

**其它边界：**

- 说明性内容写在文档里，不要写在脚本/代码目录里（不要在那里建 `README`）。
- 文档里引用代码用相对路径（`lib/core/theme/dimens.dart`），
  但**不要把代码贴成一节文档**放在 `docs/` 里——文档讲设计，代码是代码。
- 根目录的 `README.md` 不因为它是例外就可以随便长：它只写"仓库首页"该有的东西
  （环境、结构、构建、常见问题），具体设计一律链到 `docs/`。它的开头就是这么写的：
  "全部文档从 `docs/README.md` 进"。

## 2. 一个文档只记录一个事情

### 要求什么

一份文档 = 一个主题。文件名能说出这个主题，正文里不出现第二个**并列**主题。

### 现状（已核实）：每份文档讲的那一件事

| 文档 | 它讲的那一件事 |
|---|---|
| [软件理念设计](软件理念设计.md) | 产品要什么、不要什么（「轻」与「省 token」） |
| [核心功能设计](核心功能设计.md) | 有哪四个核心功能 |
| [技术栈设计](技术栈设计.md) | 为什么选 Flutter / Drift / DeepSeek，放弃了什么 |
| [架构和功能开发流程设计](架构和功能开发流程设计.md) | 代码怎么分层、日常怎么改、出问题怎么办 |
| [数据库设计](数据库设计.md) | 数据存在哪、表与字段、迁移历史 |
| [界面设计](界面设计.md) | 有哪几屏、关键交互与视觉规范 |
| [目录设计](目录设计.md) | 文件放哪、叫什么名字 |
| [测试设计](测试设计.md) | 测了什么、怎么跑 |
| [AI接入设计](AI接入设计.md) | 怎么接 DeepSeek、花多少钱、怎么省 |
| [文档设计](文档设计.md) | 文档怎么写、放哪、叫什么（本文） |

`README.md` 是索引，不是文档，不参与这条规则。

### 为什么

- **找东西不用先猜**。"改表要注意什么"必然在《数据库设计》，不存在"可能在架构那篇里"。
- **改动范围清楚**。改一件事只动一份文件，评审只看一份 diff。
- **混在一起的总纲没人敢改**：一份文档什么都写一点，每次改动都牵连它，
  于是所有人都绕着它走，它很快变成最过时的那份。下面的真实案例就是这样。

### 怎么判断合规：三个自测问句

1. **一句话测试**——能不能用一句话说完这份文档，且这句话里**不需要"以及 / 还有 / 顺便"**？
   - 过：《技术栈设计》= "为什么选这些技术、放弃了什么"。
   - 不过：曾经的《01-技术选型与架构设计》= "选型**以及**架构**以及** AI 接入**以及**费用
     **以及**路线图"——五个"以及"，就是五件事。
2. **改动触发测试**——它的"什么时候需要改它"是不是**唯一一类**事件？
   （`README.md` 文档清单表的最后一列就是这一列判据。触发条件超过一类，就该拆。）
3. **读者测试**——有没有一类读者只关心其中一半？（只想知道"花多少钱"的人，
   不需要读分层与依赖方向。）

### 真实案例：`01-技术选型与架构设计.md` 为什么被拆

它还叫 `docs/01-技术选型与架构设计.md` 时，一份文档 9 节，同时讲了五件事：

| 它当时讲的 | 现在的落点 |
|---|---|
| 为什么是 Flutter、为什么是 Drift（选型） | [技术栈设计](技术栈设计.md) |
| 状态管理与项目分层、架构总览（架构） | [架构和功能开发流程设计](架构和功能开发流程设计.md) |
| DeepSeek 接入设计、费用模型、省钱策略 | [AI接入设计](AI接入设计.md) |
| 记忆卡片算法、阅读模式 | 功能整体删除，文档随之消失；阅读/编辑两态写进 [界面设计](界面设计.md) |
| 开发路线图 | 不再单独成文（进度交给 git 与规格书，规格书也已撤销） |
| 页面与交互、数据模型、目录命名（散落其中） | [界面设计](界面设计.md)、[数据库设计](数据库设计.md)、[目录设计](目录设计.md) |

**"一件事"的边界在哪：判据是主题，不是篇幅。**

- 《数据库设计》47 KB、12 节，仍然只是一件事（数据怎么存）；
  《测试设计》42 KB 也只是一件事（怎么测）。**长 != 混**，不要为了长度去拆。
- 反过来，《软件理念设计》只有几行也自成一份，因为它回答的是另一个问题
  （产品要什么、不要什么）。**短 != 不配单独成文。**
- 拆完留下的痕迹是各文档末尾的"**原 01 / 02 / 03 / 04 文档里已过时、本次已修正的说法**"
  一节。这**不算**第二件事：它记录的是本文档自己的修订历史，属于同一主题。

### 边界情况怎么办

- **同一件事的"设计"和"实施步骤"**：写在**同一份文档**里分节，不要为"步骤"另开一份。
- **被多份文档共用的前提**（如"依赖方向"）：放在它自己的那份文档里；
  其它文档用一两句话重申结论，不要让读者必须跳过去（见第 3 条）。
- **一份文档确实是一件事但太长**：继续加长，靠节标题和索引定位。
  拆分的正当理由只有"出现了第二个主题"，没有"太长了"。
- **拆分的收尾动作（必须做）**：
  1. 更新 `README.md` 的"我想做什么""文档清单"两张表；
  2. 全仓库搜旧文件名，把所有引用改到新文件（`git grep 旧文件名`）；
  3. 旧的数字编号前缀一并去掉（见第 4 条）。
- **新功能要不要单独一份文档**：默认**不要**。改动直接写进对应的设计文档
  （本仓库已定案不用规格书，见第 4 节"子目录"）。

## 3. 文档和文档间，应该独立

### 要求什么

任取一份文档，**单读它就能读懂它讲的那件事**：关键前提、结论、判据都在本文之内。
**可以**链接别的文档做延伸阅读；**不许**把关键前提只放在别处，
让读者"必须点过去才看得懂"。

### 与"链接"的区别

| | 允许 | 不允许 |
|---|---|---|
| 形式 | 读完本文后还想看更多 → 给链接 | 不读另一份就读不懂本文 |
| 例子 | "完整命令速查见《架构和功能开发流程设计》" | "本文的分层规则见《架构和功能开发流程设计》第三节"（本文却没说规则是什么） |

**判据问句：把被引用的文档从仓库里删掉，本文还成立吗？**
成立 → 是延伸链接，可以留；不成立 → 是依赖，必须把前提搬回本文。

**引用方式**：写**文件名或文档标题**（`《数据库设计》`、`[数据库设计](数据库设计.md)`），
**不要写"见某份文档的第 N 节"**——文件名和节号是两个假设，任何一个变了引用就废。
本文档内部的节引用同理：优先引节标题，不引节号。

### 怎么判断合规

1. **删链接测试**：见上面的判据问句，逐条检查文档里的"见……"。
2. **死链检查**：文档里每一处指向 `.md` 的链接，目标文件是否真的存在；
   代码注释里的 `docs/...` 路径同样要查（这类最容易被漏掉）。
3. **节号检查**：全文搜 `第 N 节` / `§N`，确认 N 对应的小节标题没变过。

### 为什么（本仓库的真实代价）

指向"文件的某一节"是最脆的引用：**文件名会改、节号会漂、文件会被删**，
而引用它的地方遍布文档与代码注释，没人会记得同步。下面是真实发生过的五类：

**① 指向根本不存在的文件。**
`lib/core/theme/dimens.dart` 讲卡片流尺寸的注释曾写着
"详见 `docs/specs/轻笔记消费流.md` 4.6"。
**这份文件在本仓库任何一次提交里都不存在**（全历史搜不到这个文件名）；
卡片流的真实设计在同目录的 `轻笔记-AI卡片流.md`，而那一节讲的是"篇幅上限"，
并不是卡片尺寸（卡片尺寸在该文档的另一节）。注释后来改成了
`轻笔记-AI卡片流.md`——**并且顺手去掉了节号**，这正是本文推荐的写法。
（注意：它当时指向 `docs/specs/`，而那个目录后来被整体撤销，于是**再次**变成了死链。
所以正文里的设计结论要尽量留在设计文档中，别让代码注释成为唯一入口。）

**② 指向已删除的文件。**
`lib/core/db/tables.dart` 顶部注释曾指向 `docs/02-数据模型设计.md`。
重构后那份文档改名为《数据库设计》（`docs/数据库设计.md`），注释成了死链。
《数据库设计》自己把这件事记在"已过时说法"一节里作为待办。

**③ 节号漂移（最典型的一例）。**
`docs/specs/模板-新增功能规格书.md` 里写着
"判断标准见**规范第 7 节**：有自己的表、或会出现在导航/设置首页 → 才算新 feature"。
两个问题叠在一起：**没说是哪一份文档**（"规范"是三份数字编号文档时代的叫法），
而且那条判据现在在《目录设计》的
**"新增一个 feature 的步骤"**一节（`docs/目录设计.md`），
它当前的"命名规范"那一节里并没有这条。
文件名换了两次、节号也换了，读者照这句话**找不到东西**——
这就是"必须跳转才能读懂"的坏味。正确写法是：
把判据本身抄进模板，或写成"见《目录设计》的『新增一个 feature 的步骤』"。

**⑤ 批量替换的残留会顺着引用传播。**
《架构和功能开发流程设计》记着：同一份文档**至少 6 处**把"目录"误写成"笔记库"
（"打开**笔记库**""删 `build\` **笔记库**"），是某次批量替换的残留，
与"笔记库"（用户数据）毫无关系。文档互相依赖时，这类错误会被读者当成事实继续传播；
独立成文时，它只能错在一处。

### 边界情况怎么办

- **背景确实在别的文档**：在本文里用**一到两句话复述结论**（哪怕显得重复），再给链接。
  重复是可接受的代价；"读不懂"不是。
- **引用代码**：写"文件路径 + 符号名"（`lib/core/db/tables.dart` 的 `Notes` 表），
  **不要写行号**——行号天天在变。
- **引用别的文档**：写文件名或标题，不写节号；确实要指某一节时，
  写**节标题**而不是节号。
- **已知待处理（本文不链接该目录）**：仓库里仍有多处指向
  `docs/specs/` 的链接——`docs/README.md` 的索引表、根 `README.md` 的常用文档列表、
  `docs/目录设计.md` 的目录树与"新增一个 feature 的步骤"。
  该目录撤销时必须一并改掉，否则会一次性多出若干个死链。

## 4. 文档直接命名，不用数字加名字的格式

### 要求什么

文件名 = 主题名，**不加 `01-` / `1_` / `1.` 之类前缀**。

### 为什么

- **编号不携带信息**：看到 `03` 不知道讲什么，看到"目录设计"就知道了。
- **编号会假装有顺序**：本仓库的文档**没有阅读顺序**，都是按需查的。
- **编号逼着重编号**：往中间插一份新文档，后面的全要改名，
  git 会把一次"插入"记成一串"删除 + 新增"，其它文档里的引用同时失效。
- **编号会和内容解绑**：号码被复用换主题时，历史里只看得到一个删除和一个新增。

### 怎么判断合规

```powershell
# 应为 0 个
Get-ChildItem docs -Recurse -File | Where-Object { $_.Name -match '^\d+[-_.]' }
```

**本次核实结果：`docs/` 下 0 个带数字前缀的文件。**

### 历史反例

`docs/` 曾经长这样（首次提交就有前三份）：

| 文件 | 后来 |
|---|---|
| `01-技术选型与架构设计.md` | 拆成三份（见第 2 节），改名《技术栈设计》 |
| `02-数据模型设计.md` | 改名《数据库设计》（`docs/数据库设计.md`） |
| `03-界面设计实施说明.md` | **被 `03-目录与命名规范.md` 顶掉**——同一个号码换了主题 |
| `03-目录与命名规范.md` | 改名《目录设计》 |
| `04-UI结构与实现.md` | 改名《界面设计》 |

这五个文件名暴露了编号的真实问题：

- **`03` 换过主题**：git 只能记成"删一个、加一个"，编号与内容彻底解绑；
  同时 `03-界面设计实施说明.md` 是**唯一被直接删掉的文档**，它的内容没有对应的新家。
- **改名与重构混在一起**：`01-`~`04-` 的重命名发生在一次大重构里，
  要和代码迁移混着读才找得回历史。
- **编号没表达任何顺序**：这四个号码既不是阅读顺序，也不是优先级、也不是依赖关系，
  只制造了"有序"的错觉。
- **代价已经付过一次**：`04-UI结构与实现.md` 被别的文档按编号引用，
  删除后引用就烂在那里（《目录设计》的"已过时说法"里专门记了这一条：
  "该文档已删除，改为更新《界面设计》"）。

**现状**：上述四份全部改成不带前缀的名字，`docs/` 现在是 **0 个数字前缀**。

### 命名约定（照着起名）

观察 `docs/` 顶层除 `README.md` 外的**全部 11 份文档**，共同点非常整齐：

- **全部以"设计"结尾**，形如 **`<主题>设计.md`**。这是本仓库的默认形态。
- `README.md` 是唯一例外——它是索引，不是文档。

因此：

- 新文档默认叫 **`<主题>设计.md`**：主题用中文名词（`数据库`、`界面`、`测试`、`AI接入`）。
- **不加日期、不加作者、不加版本号、不加 `-v2` / `-最终版`**。改内容就改同一份文件，
  版本交给 git；要写"为什么改"就写在文档的"已过时说法"一节里。
- 不要英文名或中英混排（现有全是中文名）；`README.md` 这类约定俗成的名字除外。
- 文件名要能被第 2 条的**一句话测试**包住——文件名就是那句话的主语。
  起不出名字，通常说明这份文档混了两件事。

### 子目录

- **`docs/specs/` 已撤销**：本仓库不再使用"规格书"，**改动直接写进对应的设计文档**。
  因此：
  - 不要再往 `specs/` 里加文件；
  - 不要再新建 `specs/` 这种**按文档体裁**分类的目录
    （"规格书 / 模板 / 草稿"都是体裁，不是主题）；
  - 撤销时按第 3 节的"已知待处理"清掉所有指向它的链接。
- **什么时候才建子目录**：只有当一个主题的文档**多到一张索引表已经装不下**，
  才建目录；目录按**主题**分（例如将来表多到一份文档装不下，才考虑 `docs/数据库/`），
  **不按体裁分、不按编号分**。
- **当前结论：不建子目录。** 11 份文档用 `docs/README.md` 一张索引表就能管住，
  多一层目录只会多一层"要翻两个地方"的成本。
- 建了子目录之后，`docs/README.md` 的索引仍要能**一层点到位**。

## 5. 两条维护约定

这两条本来写在 [README](README.md) 里。这里抄一份，
让本文**单独读也完整**——这本身就是第 3 条在自我执行。

### 5.1 文档与代码不一致时，以代码为准，然后改文档

**代码是唯一运行的真相。** 发现不一致**当成 bug 修**：先确认代码的实际行为，
再改文档把它写对。

不允许的两种做法：

- (a) 照着文档去改代码——除非已经确认那处代码是 bug、且确实要改行为；
- (b) 记一句"文档过时了"就放着——按本约定，这是**一个未修的 bug**。

本仓库的实际做法值得沿用：**改完之后在文档里留一节"已过时、本次已修正的说法"**，
逐条写"原文说什么 / 实际是什么"。这不是形式主义——《数据库设计》那一节里，
第 1、2、4 条都是**会导致升级/迁移直接出错的硬错误**
（如：原文写 `schemaVersion = 10`，实际是 `11`；迁移代码块里的列名写成了改名前的
`notebook_id`，照抄会在真机上迁移失败）。

### 5.2 改表必须同时改 `lib/core/db/tables.dart` 与 [数据库设计](数据库设计.md)

`tables.dart` 的文件头已经写了这条提醒。**数据模型文档脱节的代价很高**
（错的字段名会让人写出跑不通的代码，甚至写出错的迁移），所以这条单独强调。

顺序：**先改 `tables.dart`** → 跑 `build_runner` → 写迁移 →
**同步 `docs/数据库设计.md`**（至少三处：表结构、已删除的表、迁移历史）。

反过来同样成立：**只改文档不改表，也是制造不一致**，按 5.1 属于 bug。

## 6. 落笔前 / 提交前的自检

```powershell
# 1) docs/ 之外还有没有文档？——应只有 README.md
Get-ChildItem -Recurse -File -Filter *.md |
  Where-Object { $_.FullName -notmatch '\\(build|\.dart_tool|\.git|\.idea|windows|android|__pycache__)\\' -and
                 $_.FullName -notmatch '\\docs\\' }

# 2) 还有没有数字前缀？——应为 0 个
Get-ChildItem docs -Recurse -File | Where-Object { $_.Name -match '^\d+[-_.]' }

# 3) 文档里的 .md 链接目标还在不在？——逐条核对输出
Select-String -Path docs\*.md -Pattern '\]\(([^)]+\.md)\)' | Select-Object Path, LineNumber, Line
```
