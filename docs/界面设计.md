# 界面设计

这份文档讲界面：有哪几屏、每屏的关键交互、视觉与提示规范。文中路径都相对项目根，以 `lib/` 下的真实
代码为准——文档与代码不一致时改文档。

相关：[目录设计](目录设计.md)（文件放哪、各自什么职责）、[软件理念设计](软件理念设计.md)
（为什么功能上做减法）。

## 1. 信息架构

```
底部导航（3 个位置，lib/app/app_shell.dart）
├── 轻笔记     AI 从素材里生成的新卡片（消费端，不产出内容）
├── 笔记库     笔记库（平铺）+「我的轻笔记」区块；右下角两个 FAB（上：AI 助手，下：新建）
└── 设置       只做导航，见 §3.9

其他入口
├── 搜索        笔记库页顶栏（全局，含「我的轻笔记」）/ 笔记库详情页顶栏（只搜本库）
├── 素材来源     轻笔记页右上角调节图标（Icons.tune）
├── AI 助手      笔记库页右下角、新建 FAB 上方
├── 轻笔记详情   点卡片流里的卡片
├── 笔记库详情   笔记库 → 点某个笔记库
└── 笔记编辑     点任意笔记（进阅读态）；新建走笔记库页 `+` / 笔记库详情页 `+`
```

**AI 不进底部导航**：它是"偶尔进去问一次"的助手，不该和三个主页面平级的常驻 tab 并列。
入口放在笔记库页右下角、新建 FAB 上方——它和"新建"同属"一个动作入口"，放在一起既不抢主流程，
又随时够得着。

### 一个重要的语义分工

「轻笔记」这个词出现两次，指的不是同一批内容：

| 位置 | 内容 |
|---|---|
| 底部导航的**轻笔记页** | AI 从选定素材里**新生成**的卡片（看完可以收下，也可以直接走掉） |
| 笔记库页的**「我的轻笔记」区块** | **未归档**笔记（`is_inbox = true`，尚未归入任何笔记库） |

两者的关系是**单向**的：轻笔记 →（点「加入我的轻笔记」）→ 我的轻笔记；反过来不成立
（「我的轻笔记」的笔记不会变成卡片流里的内容——卡片流只从素材**新生成**）。
所以它们叫法再像也不是同一批东西：一个页面在"生成"，另一个区块在"存放还没归档的笔记"。

**速记（随手记）的入口在笔记库页**，不在轻笔记页——消费流不产出内容。所以"随手记一句"走笔记库页 `+` →
「新建笔记到「我的轻笔记」」。

## 3. 各屏关键交互

### 3.1 轻笔记页：AI 卡片流

**卡片上只有标题**（最多 3 行，超出省略），另有：

- 一行「点开看全文 ›」提示——卡片上只有标题，必须让用户知道还有下文；
- 左下角一个短标签（生成结果里的第一个标签）；没有标签时退回「AI 生成」；
- 右下角是一个开关式按钮：未收下时「加入我的轻笔记」，收下后变「从我的轻笔记移出」。

标题为空时占位显示「（无标题）」。

卡片高度**自适应**：内容少就按内容高，最多到屏高 2/3（下限 445），不写死像素。一屏基本只完整显示一张，
下一张露头提示"下面还有"。固定成 2/3 屏效果很差：1 行标题的卡片也占满 2/3 屏、中间一大片空白。
改成自适应时要注意：用 `Spacer` 撑底部会把 `Column` 拉到上限高度，正确做法是 `spaceBetween`。

| 用户动作 | 结果 |
|---|---|
| 下拉（RefreshIndicator 的圆圈） | 前向追加：新的 2 张插到列表最前面（3 → 5 → 7…，累积） |
| 滚动到底 | 什么都不做（没有上拉加载，也没"滚到底自动加载"） |
| 点卡片 | 进轻笔记详情页看全文（卡片内容此刻还没落库） |
| 点「加入我的轻笔记」 | 立刻写出一条未归档笔记，提示「已加入「我的轻笔记」」；按钮变「从我的轻笔记移出」 |
| 点「从我的轻笔记移出」 | 删掉那条笔记（逻辑删除），提示「已从「我的轻笔记」移出」 |

"已加入"从数据库实时推导（按标题+正文指纹，或本次会话记住的 noteId），不记在页面内存里：用户跑到笔记库页
把它删了，卡片这边会跟着变回「加入」。

**为什么卡片上不放正文预览**：两种做法都试过并都放弃了——截正文前 N 字，读起来就是"被截断的正文"；
让 AI 单独生成一段摘要，要维护两个内容字段，而且模型根本不守字数（要求 45–60 字，稳定返回 116–160 字）。
于是卡片只剩标题，标题就得一个人承担"让人想点进去"的责任：提示词里专门要求它是一句有钩子的话，
而不是「间隔重复」这种干标签。左下角那一格也因此给了标签——按钮文案已经能表达加入状态，用户更想知道的是
"这条在讲什么"。

**为什么加入之后按钮变成「移出」而不是变灰**：加入后置灰禁用会让用户以为坏了——其实是想撤销收下，
却没有入口。现在它是个开关，两个方向都点得动。

**每次看到的内容为什么不一样**

卡片不是"已有笔记的视图"，每张卡片都是 AI 就某一份素材现写的新内容。素材只有一样东西：**片内开头一段截断的原文**（没有摘要）。

切片是给搜索与卡片流用的语义单元（按标题层级切，上限 700 字；代码块 / 表格 / 列表不拆散，是唯一允许
超上限的例外。见 [数据库设计](数据库设计.md) 的「note_chunks（笔记切片）」一节）；卡片流是消费侧，
只从片里开一个短窗口（`FeedWindow`，大小见 `FeedLimits.windowChars`）——片比窗口短就是整片。AI Agent 不按片读正文（它走 `sql` 里的读函数，见 §3.8），但"发送前那次本地检索"检索的正是切片。
用户看不到"片"，能感觉到的只有一件事：同一篇笔记被反复抽到时，看到的段落在往后走。

| 机制 | 用户看到的效果 |
|---|---|
| 窗口起点候选 `0 / chars / 2*chars …`（`chars` = `FeedWindow.chars`），最后一个窗口尾部对齐 | 长笔记的尾段也一定被取到，不会只剩几十个字 |
| 用掉一个窗口后，下次从下一个候选起点开始（环形） | 一篇长笔记不会永远只出开头那一小段 |
| `note_chunks.last_used_at` 落库，取片时"最久没用过的排前面，从没用过的排最前" | 重启 App 也不会又抽到刚看过的那批片 |
| 会话内再记一层"最近用过的片"（60 个） | 同一会话里短期重复更少 |
| 来源冷却：最近 15 张卡片里，同一篇笔记最多出现 1 次 | 连着两批不会都在讲同一篇笔记 |

所以前后两次看到的内容不完全一样：素材是打乱后随机取的，窗口在片内往后轮换，用过的片还有持久化记录
兜着——这几层合起来，同一个位置、同一篇笔记很难被连着抽到两次。

标题层面还有三道防线，用户看到的是"卡片标题不重样"：取片时跳过最近用过的片 → 把已经生成过的标题列进
提示词让模型主动避开 → 生成后把标题太像的草稿直接丢掉（按"去掉标点/空白/大小写后只留实义字符"比指纹，
「抄书是最没用的努力」和「抄书是最没用的努力！」算同一张）。

素材取用本身还做了一件事：

- 库里笔记少时，同一篇笔记的不同片会被当成不同素材（每片说的是不同的事），所以"只有 3 条笔记"也凑得出
  一批卡片；片也不够时就是少几张——生成是"一路一份素材、只出 1 张"，不再让模型对着一份素材写多张。

**跨启动预留：为什么第二次打开就快了**

- 首次装完 App（库里没有预留）：只先**并发生成一屏 3 张**就上屏——3 张并行单卡比一次生成一批快得多；
  剩下的（补池、后台**单独生成**下次的预留）全部丢后台。这段时间显示骨架屏 + 一行「正在用你的笔记生成卡片…」；
- 之后进入：先把上次留在库里的 6 张放进池子（前 3 张立刻当第一屏，秒出），同时后台再补池、并生成新一批
  预留写回去。预留在库里是"消费即清 + 整批替换"，所以不会重复看到同一批。

池子常备 8 张（≈ 4 屏）、首屏取 3 张、下拉每次 2 张，取完立刻在后台补：用户连刷好几次才会碰到池子空。生成结果不落库，
唯一存下来的只有这份跨启动预留——卡片是"随手刷到的东西"，不是收藏品。

页面状态：

| 状态 | 表现 |
|---|---|
| 首次加载 | 骨架屏：一行「正在用你的笔记生成卡片…」+ 3 个灰块（约 200 高、卡片圆角），不用转圈 |
| 未选来源 | 「还没有选择素材来源」+ 按钮「选择笔记库」（完整文案见 §6） |
| 选了但无素材 | 「选中的来源没有可用素材」+ 按钮「换个来源」（完整文案见 §6） |
| 生成失败 | 「生成失败」+ 原因 + 按钮「重试」 |
| 已有卡片时刷新失败 | 不清空已有卡片，只弹一条 error 提示「生成失败：<原因>」 |
| 来源被全部取消 | 立刻切回「还没有选择素材来源」的引导；屏幕上已有的卡片不清空 |

**两类引导的分界**（`FeedSource.isEmpty`）：只有"笔记库一个都没勾 且 关掉「包含我的轻笔记」"才算
"没选来源"。只关掉一边（比如笔记库全不勾、但「包含我的轻笔记」还开着）不算没选来源，这时若库里没有
正文非空的笔记，落到的是「选中的来源没有可用素材」。空正文的笔记直接跳过，不参与生成。

**从素材来源页返回**（只有真的改了才会返回"有变化"）：

1. 丢掉数据层里那批用旧来源生成的池子——留着的话下次取卡片还是旧来源的内容；
2. 屏幕上已经显示的卡片保留：用户只是改了个设置，不该清空他正在看的东西；
3. 重新解析一次来源，如果一个来源都不剩，立刻切回「还没有选择素材来源」引导；
4. 只有本来就没有卡片时才立刻取一屏；有卡片就什么都不做，等用户自己下拉。

未配 API Key 时：预热会安静失败，页面照走按需生成；真发不出去就落到「生成失败」+ 原因，不是静默空白。

### 3.2 轻笔记详情页

- 顶部标题、一行「AI 从你的笔记库生成」、下面 Markdown 渲染的全文（只读，没有编辑概念）；
- 顶栏右侧：未收下时是「加入我的轻笔记」（点击时按钮内显示转圈），收下后变成绿色的「已加入」；
- 返回时把"收下没有"带回列表，让卡片立刻显示成已加入；
- 加入失败弹 error「保存失败：<原因>」。

这一页（以及卡片上）只有"收下"这一个动作，别无其它（`feed_detail_page.dart` 的 AppBar 只有一个 action）：

| 有 | 没有 |
|---|---|
| 未收下时「加入我的轻笔记」（点击时按钮内转圈），收下后变成绿色的「已加入」 | 没有笔记库选择器：收下只会写进「我的轻笔记」，不能一步归到某个笔记库 |
| 返回（把"收下没有"带回列表） | 没有新建笔记的入口，也没有编辑 / 删除 / 更多菜单（卡片上同样只有「加入 / 移出」一个开关） |

所以"轻笔记长出笔记"这条链在归档那一步是断的：卡片能生成、能看全文、能收进「我的轻笔记」，
但要归进某个笔记库，用户必须再进笔记库页或编辑页操作一次（见 §8.5）。

### 3.3 素材来源页

- 说明文字：勾选作为素材的笔记库，以后新建的笔记库会自动加入，除非在这里取消勾选；
- 「包含我的轻笔记」开关（把未归档笔记也当素材）；
- 笔记库清单是平铺复选（笔记库没有层级，不存在父子级联问题）；
- 顶栏：全选 / 全不选、保存；页面底部另有「恢复默认」——清掉用户存的排除集（回到"我从没表过态"），
  没有它用户就再也回不到"新库自动加入"的状态；
- 选择与进来时完全一致时直接返回、不写库：否则用户打开这页点一下保存就会被记成"用户接管了来源"，
  之后新建的笔记库永远不再自动进来；
- 允许保存空选择，只提示一句「没有选任何来源，卡片流会是空的」。

页面上写死的文案（`feed_source_page.dart`）：

| 位置 | 文案 |
|---|---|
| 页首说明 | 「勾选作为素材的笔记库。AI 会从里面长出新内容。以后新建的笔记库会\*\*自动\*\*加入，除非你在这里取消勾选。」（原文里那对 `**` 是**字面量**，会原样显示——这段文字不是 Markdown） |
| 开关标题 / 副标题 | 「包含我的轻笔记」/「还没归档到任何笔记库的笔记，也拿来当素材」 |
| 分区标题 | 「笔记库」 |
| 无笔记库 | 「还没有笔记库」+「去「笔记库」建一个笔记库，笔记就能按笔记库参与卡片流。」 |
| 恢复默认 | 「恢复默认」/「全部笔记库 + 我的轻笔记，之后新建的也会自动加入」；已经是默认状态时置灰不可点（没排除任何库且包含「我的轻笔记」），点成功后提示「已恢复默认来源」 |

页面上不需要任何"同步/刷新"动作：用户取消勾选的库才会被记住（存的是"用户不要什么"），没表过态的库——
包括之后新建的——一律算勾上。所以"默认全选 + 新库自动进来"是构造性成立的，不是靠某个时机去对账。
界面上能看到的效果：在笔记库页新建一个库、切回轻笔记页，它已经在来源里（不用重启）。

### 3.4 笔记库页

结构是「笔记库」区块 + 「我的轻笔记」区块（`SectionHeader`）。

| 元素 | 交互 |
|---|---|
| 笔记库项 | 点进笔记库详情；长按弹菜单：重命名、删除笔记库（副标题「笔记库内笔记会回到轻笔记」） |
| 笔记库为空 | 「还没有笔记库」+ 按钮「新建笔记库」 |
| 笔记项（我的轻笔记） | 点进阅读态；左滑露出「置顶 / 取消置顶」和「删除」两颗按钮，点了哪颗才做哪颗；长按弹菜单：移动到笔记库 / 移回轻笔记 / 删除笔记 |
| 我的轻笔记为空 | 「还没有轻笔记。点右下角 + 「新建笔记」随手记一句，之后再归档到上面的笔记库。」 |
| 右下 FAB | 上：AI 助手（`Icons.auto_awesome_outlined`）；下：新建（`Icons.add`） |
| 顶栏 | 搜索（全局，含「我的轻笔记」）、「更多」→「调整笔记库顺序」/「多选笔记」 |

**新建 FAB 是三选一**（`showCreateSheet`，第一项最常用所以放最上面且不再追问）：

1. 新建笔记到「我的轻笔记」——随手记一句，之后再归档；
2. 新建笔记并选择笔记库——创建后直接归入某个库；
3. 新建笔记库——建容器，不是建笔记。

新建笔记不先落库：把"落到哪个笔记库"作为草稿参数传给编辑页，只有用户真的写了内容才创建。什么都不写就返回，
库里从头到尾没有这条笔记。

**删除的分工**：

| 动作 | 反馈 |
|---|---|
| 单条左滑删除 | 乐观删除 + 撤销：**划开只是露出按钮**，点「删除」才真的删（那一眼就是确认，所以不再弹确认框），底部提示「已删除「标题」」+「撤销」按钮（3 秒自动走） |
| 批量删除 | 二次确认：「删除 N 条笔记」/「这些笔记将被删除，不可恢复。」，红色「删除」；不给撤销（一次删几十条时把完整状态留在内存等撤销代价太大） |
| 删除笔记库 | 确认框写清后果：不删笔记，库内笔记会回到「轻笔记」，之后可以再归档到别的库 |

**左滑为什么从"划走即删"改成"划开露出按钮"**（`lib/features/note/ui/widgets/swipe_actions.dart` 的
`SwipeActions`）：老的 `Dismissible` 是划到底、松手就删，它的假设是"横滑这个动作本身就是一次明确的意图表达"——
那个假设不成立：横滑太容易误触（单手拿着手机、列表快速滑动时手指稍微偏一点就会划开），而删除是破坏性的。
现在中间多一道"**看到按钮**"：划开 → 露出按钮 → 点哪一颗才做哪一颗。那一眼就是确认，而且不用弹对话框
（弹窗比这个重得多，还挡住列表）。**撤销照样保留**（`LogBar.action`）：一个是事前看清，一个是事后可退，
两道防线不冲突。列表外面套一层 `SwipeActionsScope`（`SlidableAutoCloseBehavior`）让划开一行时自动收起其它行，
不然可能出现好几行同时敞着，看着像列表坏了。

**左滑那颗「置顶」和别的笔记列表是同一套语义**：点它把这条排到当前顺序的第一位并打上图钉，取消置顶**只清标记、
位置不动**（它就在你上次放的地方）。做法与理由见 §3.5。

**这个区块为什么也必须按 `sort_order` 排**（`AppDatabase.watchUnfiledNotes`；数据层里同族的 `watchInboxNotes`
一起改了）：那颗按钮只干一件事——写 `sort_order`。列表要是按 `pinned DESC` 排，同一个动作就变成**靠两套机制
生效**（一处写手动顺序、一处看标记），改一处忘一处立刻分叉：同一个「置顶」在库内是"挪到最前一次"，在这里却成了
"永远钉在最上面"。所以**界面上的笔记列表统一走 `_noteListOrder`**（`sort_order ASC, updated_at DESC`）——
库内那个（`watchNotesInNotebook`）、「我的轻笔记」这个（`watchUnfiledNotes`）、以及数据层的收件箱查询
（`watchInboxNotes`，就是未归档那批再多要求 `notebookId IS NULL`，界面上没有单独的页面用它）——置顶的含义到处
一致。（这里曾经单独写着 `pinned DESC`，是"置顶 = 钉住"那个时代的遗留。）

多选模式：顶栏左边关闭、标题「已选 N 条」、右边全选/全不选；底部操作条「移动」「删除」，未选中时按钮禁用并
提示「请选择要处理的笔记」。多选时长按也是切换选中（不弹菜单）。批量移动的目标可以是别的笔记库，
也可以是「移出笔记库（回到我的轻笔记）」。

**拖动排序（「调整笔记库顺序」）**：入口在顶栏「更多」的第一项（`Icons.swap_vert` + 「调整笔记库顺序」），
和多选互斥（进这个模式会先退出多选——两种模式下点击/长按的含义完全不同，同时开着必然打架）。进去之后是
**单独一屏、只列笔记库**——原来那一屏里混着「笔记库」和「我的轻笔记」两个区块和两个分区标题，拖动会在
"哪些能拖、能拖到哪"上冒出一堆边界情况，只列库则拖动的含义没有歧义。形状与笔记库详情页里那个「调整顺序」
完全一致：顶部一条提示（「拖动右边的 ≡ 调整笔记库顺序（共 N 个）」+ 右侧「完成」按钮）、每行行尾一个 ≡ 手柄
（`ReorderableDragStartListener`）、**这一屏里点一行不跳转**（手柄才是唯一的作用点，点一下跳进去会很突兀）。
拖完的顺序整份写回（`NotebookRepository.reorder` → `AppDatabase.reorderNotebooks`，从 1 开始密集编号、
0 留给"没排过"），**拖完即生效**，不需要再点一次保存；模式本身只是页面状态（退出页面再回来就回到常态，
顺序是立即落库的）。

笔记列表项（`NoteListTile`，笔记库页与详情页共用）显示：置顶图钉（有则显示）、标题（1 行）、相对时间、
正文前 200 字纯文本（无则不显示这一段）。多选模式下左侧是勾选图标、整行加一层淡底色，让"已选中"一眼看得出来。
它还有一个**可选的 `trailing` 槽**，目前只有"调整顺序"用它放拖动手柄——手柄必须显式可见，光靠"长按可以拖"
没人猜得到。

### 3.5 笔记库详情页

- 库内笔记列表；空库显示「该笔记库暂无笔记」+「点右下角 + 在这里新建一篇。」；
- 右下 FAB：在此笔记库新建笔记（多选 / 调整顺序时都不给：那两个模式下用户要做的不是新建，浮在那儿只会占地方、
  还可能挡住列表最后一行）；
- 顶栏搜索是库内搜索（不含「我的轻笔记」——进到库里再搜，预期就是"在这个库里找"）；
- 顶栏「更多」：调整顺序 / 多选笔记 / 重命名笔记库 / 删除笔记库。刻意没有「新建子笔记库」——笔记库是平铺的，不能嵌套；
- 左滑露出「置顶 / 取消置顶」和「删除」，点了才执行；
- 删除笔记库后自动退回上一层（笔记库页）。

**「调整顺序」**：入口是顶栏「更多」的第一项（`Icons.swap_vert` + 「调整顺序」），进去后列表只认手柄：顶部一条
提示（「拖动右边的 ≡ 调整顺序（共 N 篇）」+「完成」）、每行行尾一个 ≡ 手柄、**这一屏里点一行不跳转**（不然点一下
跳到编辑页会很突兀）。和多选互斥：进这个模式会先退出多选。拖完整份写回（`NoteRepository.reorder` →
`AppDatabase.reorderNotes`），不需要额外保存。用 `ReorderableListView.builder` 的 `onReorderItem` 而不是老的
`onReorder`：新回调给的 `newIndex` **已经**替算好"移除原位置之后"的下标，老回调那个"自己减一"的坑它内置处理了。
形状与笔记库页的「调整笔记库顺序」完全一致（同一套提示条 + 完成 + 手柄），用户不用重新认。

**置顶 = "挪到最前一次" + 图钉**（`NoteRepository.moveToFront`）：点「置顶」把这篇排到当前顺序的第一位并打上标记
（列表里显示图钉），取消置顶**只清标记、位置不动**——它就在你上次放的地方。为什么不做成独立的一层排序
（`pinned DESC` 再跟上手动顺序）：那样用户在界面上拖一篇到最前，它上面还挡着置顶的那几篇——要么"拖上去又被顶回来"
（吸附），要么把置顶的从列表里藏掉（用户以为丢了）。**一个列表只该有一个顺序来源。**代价是新建的笔记
（`sort_order = 0`）会落到"没排过"那组，靠 `updated_at` 排到最前，顺带把置顶过的往下挤一位——这是"置顶只顶这一次"
的自然结果，用户已经认了。**所有笔记列表用的是同一套排序（`AppDatabase._noteListOrder`）与同一套置顶语义**，
所以这套说法在哪个笔记列表里都成立（见 §3.4 里"同一个动作不能靠两套机制生效"那段）。

### 3.6 笔记编辑页：编辑 / 阅读两态

| 形态 | 内容 | 右上角 | 右下角 |
|---|---|---|---|
| 编辑 | 标题输入框 + 正文输入框 + 底部格式工具栏（占 `bottomNavigationBar`） | 一个勾：点了保存并进阅读态 | 目录 FAB（见下），离底部远了还有快速到底 |
| 阅读 | Markdown 渲染后的只读视图（按片渲染） | 「编辑」文字按钮 + 三个点菜单 | 目录 FAB（见下），离底部远了还有快速到底 |

- 从列表/搜索结果进来默认进阅读（`startInReading: true`）；从"新建"进来是编辑；
- 两态共用同一个 `TextEditingController`，切换不丢草稿；
- 顶栏标题位置显示保存状态：未保存 / 保存中… / 已保存 / 保存失败（失败用错误色）；
- 编辑态不放菜单：菜单里是删除/移动这类"对已存内容"的操作，而此刻屏幕上还有没保存的改动——先保存、
  进阅读态、再动菜单，顺序上不会出现"删了却发现刚才的改动没存"。

**「目录」（`NoteEditorPage._tocButton` / `_showToc`，两种模式都有）**：

- 入口是右下角一个小号 FAB（`FloatingActionButton.small` + `Icons.toc` + tooltip「目录」），与笔记库页
  右下角的「AI 助手」按钮是同一个形状：两者都是"点开还有一层"的动作入口、又都不属于主流程（主流程是读、
  是新建），所以都不该占顶栏或底部一整行；
- **编辑态也给**（以前只在阅读态给，理由是"编辑态右手边是正文输入框与格式工具栏，浮一个按钮上去会压住正文"）。
  那个顾虑现在由布局解决：格式工具栏挪进了 `bottomNavigationBar`，Scaffold 会把 FAB 排在它上方——压不到正文
  也压不到工具栏。而且长笔记在**编辑**的时候同样要能跳到某一节，那正是最需要导航的时候。正文的底部留白仍然
  多留一格（`xxl + md`），否则最后一行会被 FAB 压住；
- 点开是底部弹层，列每个小节一行，按层级缩进（顶层加粗）；点一行**阅读态滚到那一片、编辑态把光标挪到那一节的
  开头**（输入框会自己滚到光标那儿，所以效果一样是"跳过去了"）。编辑态按片自己的字符偏移（`NoteChunk.start`）
  定位，不重新解析一遍 Markdown——和目录是按片列出来的是同一个来源，所以"目录里那一行"与"跳过去的位置"必然对得上；
- 目录项来自切片器（`NoteChunker`）而不是另写一套 Markdown 解析：阅读视图本来就是按片渲染、每片一个
  `GlobalKey`，而片的分界正是标题层级——于是"目录里的一行"与"能滚到的那一片"天然是同一个东西。同一标题被
  拆成多片时只列第一片；
- 滚动复用"搜索结果点进来定位到命中片"那条路径（`_pendingScrollChunk` + `Scrollable.ensureVisible`），
  所以滚动行为只有一处实现；顺序是先关弹层再滚，让用户看见页面滚过去了；
- 没有小标题时入口照样显示，点开说明怎么才有（用「## 小节名」起头）——藏起来的话用户永远不会知道有这个
  功能，而"点开是空列表"又是另一回事。

**「快速到底」（`NoteEditorPage._jumpToBottomButton`）**：目录下面第二颗小号 FAB（`Icons.arrow_downward` +
tooltip「到底部」），形状与目录一样（两个都是"跳到别处去"的动作入口，用户不用重新认）。只在**离底部 240 以上**
才露出来（`_jumpThreshold`）——小一点的话手指刚滚一下就闪出来，很吵。两种模式的滚动物不是同一个，做法也不同：
阅读态直接 `animateTo(maxScrollExtent)`；编辑态够不着输入框内部的滚动，改成**把光标放到末尾**（输入框会自己滚到
光标那儿），副作用是光标也跟过去了——编辑态本来就是要接着写的，那正是想要的结果。判据只有一处：两种模式的
`ScrollNotification` 都会冒到 `body` 那一层的 `NotificationListener`，所以"离底部多远"只在这里判一次。

**格式工具栏为什么从 `body` 挪进 `bottomNavigationBar`**：`bottomNavigationBar` 占的位置 Scaffold 会**从 body
里扣掉**，于是右下角那两颗 FAB 自动排在它上方——不用去猜工具栏有多高，也不会出现"FAB 压住工具栏"。

**保存方式：手动。保存只发生在两个地方**——右上角那个勾，以及退出询问里选「保存并退出」。正文变了只是把状态
标成"未保存"，不排任何后台写盘。切片（搜索用的分段）也就在保存那一下更新。

**退出时若有未保存改动会问一句**（`PopScope(canPop: false)`），三个选项：

| 选项 | 结果 |
|---|---|
| 取消 / 点外面 | 留在编辑页（退出被拦下） |
| 放弃改动 | 直接退出，改动不落盘 |
| 保存并退出 | 先保存再退出；保存失败（超硬上限）就不退出，否则用户以为存了其实丢了 |

没有未保存改动时直接放行，不打扰。

**篇幅上限（正文按 UTF-8 字节数分三档，只在软上限以上才出现横幅）**：

| 档位 | 阈值 | 用户看到 |
|---|---|---|
| 轻提示 | ≥ 30 KB | 「笔记较长（x KB）」+「继续变长可能影响编辑流畅度。」（中性色） |
| 强警告 | ≥ 40 KB | 「笔记偏长（x KB）」+「建议拆成多篇。还能继续编辑，超过 50 KB 就无法保存了。」 |
| 硬上限 | ≥ 50 KB | 「超出上限（x KB），无法保存」+「上限 50 KB。内容还在编辑器里，请拆分成多篇，或裁剪到 30 KB 后再保存。」+ 裁剪按钮 |

上限是拒绝保存而不是阻止继续输入——拦输入要处理输入法组字、粘贴、撤销，漏一处就丢字。硬上限还**只管增长**：
判定是「当前字节数 > max(进编辑器时的字节数, 硬上限)」才拦（`_flush`），所以老库里按旧上限写下来的长笔记只要
不再变长就照样能存，不会"被自己的数据卡死"、连改一个字都存不了。点「裁剪」会先弹确认：
「裁剪到 30 KB？」/「会删掉末尾约 x KB 的内容。这个操作不能撤销。」裁剪不可恢复，所以只有硬上限这一档才给
这个按钮（软/强档不给，避免误触）。空草稿（标题与正文都空白）不会被写进库，连笔记都不创建。

**格式工具栏 6 个按钮**：加粗 / 斜体 / 下划线 / 列表 / 待办 / 标题。前三个包裹选中文本（没有选中就插入占位词
并选中），后三个在行首加/去前缀（再点一次即取消）。

**图片：不支持插图。** 正文里出现 `![alt](https://…)` 时不加载图片，只把 alt 与 URL 当文本显示
（URL 可选中复制）。理由是渲染即向第三方服务器发请求（隐私）、图床挂了就是破图且用户收不到提示、
小红书/微信一类链接带防盗链根本加载不出来——不渲染 = 不发任何请求。

**阅读视图按片渲染**：正文切成一片片 Markdown widget，每片套一个 key。从搜索结果点「笔记内容」进来时，
会滚动到命中那一片（`Scrollable.ensureVisible`，略靠上 6% 以免看起来像文章开头），并给那一片一层淡底色——
只滚动不标记的话，用户滚到那儿也看不出到底是哪一段被搜到了。正文为空时显示「_（正文为空）_」。字号由
「设置 → 外观 → 字体大小」统一控制。

阅读态的三个点菜单：

| 项 | 前提 / 行为 |
|---|---|
| 删除笔记 | 确认框「删除笔记」/「「标题」将被删除。」→ 取消 / 删除；删除后自动退出该页 |
| 复制全文 | 复制纯文本（标题 + 正文）到剪贴板，提示「已复制全文」 |
| 加入笔记库 / 移动到笔记库 | 未归档的显示前者，已归档的显示后者；打开笔记库选择器（可「移出笔记库」，也可就地新建笔记库） |

笔记还没创建（新草稿、还没落盘）时点菜单动作，会先落盘；实在没内容就提示「先写点内容，再操作这条笔记」。

### 3.7 搜索页

- 进页面自动聚焦输入框（打开搜索就是为了打字）；
- 输入 250ms 防抖后才查询（中文输入法组字会连续触发 `onChanged`）；
- 关键词在标题与命中片段里高亮；关键词长度 ≥ 2 才记进搜索历史（去重、超量截断）；
- 未输入时显示「搜索历史」chips，点一条即用它重搜；右上「清空」有确认框（「清空搜索历史」/
  「将删除全部搜索历史记录。」）；没有历史时提示「输入关键词搜索标题和正文」；
- 有结果时先一行「找到 N 条结果」，再分两节展示：

| 分类 | 含义 | 点进去 |
|---|---|---|
| 笔记（N） | 标题命中，整篇相关 | 阅读态，从头看 |
| 笔记内容（N） | 正文某一片命中 | 阅读态，滚动定位到命中那一片并高亮；列表项额外显示所属小节与命中片段 |

两类都进阅读视图（用户是来找内容的，不是来改的）。无结果时显示「没有找到相关笔记」并说明「当前是关键词匹配，
不是语义搜索」。

搜索范围：笔记库页进来是全局（含「我的轻笔记」）；笔记库详情页进来只搜本库（不含轻笔记）。

**结果怎么排序、最多几条**：标题命中 3 分、正文片命中 2 分，同一片里命中多次继续累加，按分数降序；
默认最多 20 条。同分按标题稳定排序，所以同一个库、同一个词，两次搜到的顺序一样。「笔记内容」的列表项在标题
下面多两行信息：所属小节（`heading`，形如「项目A / 风险」；没有小节就不显示这一行）与命中片段（命中位置
前后各 40 字，换行压成空格）；标题为空的那条显示「无标题」。

能搜到中文 2 字词（记忆 / 间隔 / 习惯）是因为匹配用的是 `LIKE '%词%'`，不是分词索引；`%` 与 `_` 按字面搜；
软删的笔记不出现在结果里，限定笔记库时库外的一条也不返回。

### 3.8 AI 助手页

顶栏：会话记录（底部弹层）、新建会话。

**会话记录弹层**：点一条切过去；右上角「多选」进入多选态（长按任意一条也能进，并顺带选中那一条），
多选态下头部变成「退出 ✕ / 已选 N 条 / 全选 · 全不选」，底部出现「删除 N 条」；一条都没选时按钮是灰的并
写明"请选择要删除的会话"。「全选」按当前列表里真实存在的会话算（列表是 `watch()` 推的，删完就变）。
单条与批量都先弹确认（「这些会话将被删除（含里面的全部消息），不可恢复。」），删完关掉弹层并提示
「已删除 N 条会话」；删掉的里面有当前会话就回到"新会话"空状态。三条约定与笔记库页的多选完全一致
（用单独的 `selecting` 标记判断是否在多选、全选按可见项算、批量删除必确认且没有撤销）——同一个 App 里不留
两套多选手感。

**会话可以置顶**：常态下每行行尾有两颗按钮——图钉（已置顶用实心，tooltip 跟着状态在「置顶 / 取消置顶」之间变）和
删除；标题前面还有一颗小图钉标记，和笔记列表里那个是同一个观感，一眼看出"这条是钉住的"。**多选态下这两颗按钮
不给**：那时"删"是底部那个批量动作，同时摆两个删除入口最容易误点。会话的置顶是字面意思（`pinned DESC,
updated_at DESC`，列表里钉住的就在最上面）——会话没有手动拖出来的顺序（`updated_at` 每聊一句就变），
不存在笔记那边"拖上去又被顶回来"的冲突；多条置顶之间仍按最近聊过排。

**没有授权确认闸门**：插上 Key 就能直接发指令，不把隐私做成一个需要用户操作的功能。"会发什么给 DeepSeek"
这件事在设置 → AI 里以说明文字告知（告知，不是需要同意）。

输入区（自上而下依次是）：

| 元素 | 交互 |
|---|---|
| 模型 | 底部弹层两档：DeepSeek Flash（默认，日常够用）/ DeepSeek Pro（更强、更贵）。**取代了原来的「工作区」入口**——工作区已取消，AI 能看到全部笔记 |
| 思考强度 | 底部弹层三档：低（最快最省）/ 中（默认）/ 高（最慢最贵，适合复杂结构化整理）；「中」以上才真正开思考模式 |
| 输入框 + 发送 | 生成中这颗按钮**变成「停止」**（可点，不是置灰的禁用状态）；**没有「选择文件」入口**——笔记原文一律由 AI 自己在 `sql` 里调 `outline_notes` / `read_note_batch` 按需读取，读到的片段只在该轮的工具结果里回灌 |

模型决定 AI 助手这次请求用哪个模型（`deepseek-flash` / `deepseek-v4-pro`），**按会话存**（复用 `ai_conversations.workspace_scope` 列）。卡片流固定用 flash。

**发送前会先做一次本地检索**：每条用户消息先过一遍"语义（向量）+ 关键词"两路融合（`NoteRetriever`），够确定就把
几条片段拼在**这条消息的末尾**一起发出去；库里那条消息**一个字节都不改**，素材只存在于请求里（不塞 system 头：
前缀缓存是逐块比对的，头一动整段就按全价重算），不确定（没过注入线 / 索引还太稀）就**什么都不给**。所以这次请求
"发了什么"= 用户这句话 + 可能附在末尾的几条素材；界面上看到的那条消息永远是用户自己写的话。

**任务栏（输入框上方）**：数据来自仓库**内存里**的进度（`AiChatRepository.progressFor`），所以只在真的有一轮在跑
时出现、跑完自己就没了，不用谁去关它。折叠态一行：转圈 + 此刻在做的事（如「读正文（3 篇）」；没有工具在跑时是
「正在思考…」）+「第 2/15 轮」+ 展开箭头；展开再多一段已经做完的步骤（一行一条打勾，只留最近 12 条）。
默认折叠的理由：一次长任务的步骤能有十几条，全摊开会把输入框顶上去，而用户 90% 的时候只想知道两件事——
"它还在动吗"、"在干嘛"。步骤写的是**人话**不是函数名：AI 干活几乎全走 `sql`（那些读函数是嵌在 SQL 里的），
把函数名摆给用户看等于什么都没说，翻译在 `ToolLabels` 里。

**思考过程折叠块（回答气泡上方，默认折叠）**：一行「思考过程（N 字）」+ 展开箭头，点开是一块浅底的思维链文字。
放在气泡**上方**而不是下方：它是"这条回答是怎么想出来的"，读的顺序本来就是先想后答。默认折叠是因为思维链往往比
正文还长，摊开会把回答挤到屏幕外；生成过程中点开过的话它是**实时长出来**的（思维链节流落库，界面跟着数据库刷新）。
它不进正文、也不进重发的历史，所以不会每轮重发、不重复计费。

**「回到最新」**：右下角一颗小号 FAB（`Icons.arrow_downward` + tooltip「回到最新」），只在**离底部 240 以上**才
露出来（`_jumpThreshold`）。它**放在消息列表那一层，不是 Scaffold 的 FAB 槽**——这不是风格选择，是踩过的坑：
FAB 槽是相对 **body 底部**定位的，而输入框就在 body 最下面，键盘一弹出来 body 被压缩，那颗按钮正好落到发送按钮上
（两个叠在一起，谁也点不准）。放进列表这一层就永远待在"输入框上方、列表右下角"，键盘开不开都不会越界。列表底部
也因此多留一格（48），否则它会压住最后一条回答的末尾——而那正是用户最想看的地方。

**新建会话不落库**：点「新建会话」只是切到一个空状态，会话行在用户发出第一句话时才创建
（`AiPage._ensureConversation`）。若"点一下就在库里建一行"，"新建 → 回看旧会话 → 再新建"每绕一圈就多一条
空会话，会话列表里堆一串「新会话」。会话列表现在也只列有消息的会话（`AppDatabase.watchConversations` 用
`EXISTS` 过滤），旧版本留下的空壳因此不会再出现在列表里（行不删，只是不显示）。

**AI 写操作没有确认层：调用即生效**（`lib/features/ai/domain/tool_executor.dart`）：上一版（命令语言）那套
"每条写命令都弹一次确认 + 撤销栈"**已经砍掉**——每写一次都要用户点一下，既慢，又拦不住真正危险的批量操作
（点习惯了就是闭眼点）。所以界面上对"AI 改笔记"**没有任何拦截**，用户唯一的保障在事前：提示词规则 10 明确写着
"修改与删除**只在用户明确要求时才做**，做完如实说明"。

改完之后界面上留下的是**一行回执**：助手消息末尾附一段 *本轮执行：…*（`_opsBlock`，只收真的改了数据的那些
调用，读函数不进去）。它的两个用处：用户翻回去就知道 AI 到底动了哪些笔记；「继续」时模型也看得到这一段，
那正是"已经执行过的操作不要重复做"的依据。**删除没有回收站、也没有撤销**——`delete_notes_batch` 是逻辑删除
（`deleted_at` 置位，数据还在库里），但界面上没有恢复入口，删了就是删了。

**「这条回答没写完」提示条**：回答没写完时（用户点了「停止」/ 网络断 / 超时 / 被系统杀掉 / 轮数用尽），气泡下面
显示一行提示 +「继续」「知道了」。点「停止」只是把这一轮掐断，**已生成的内容一个字都不删**（停住、内容留在那儿，
可以接着让它继续）。**界面上只分两类**（`AiChatRepository.isStopLike`）：被停下来（手动停止 / App 被杀 / 轮数
用尽 / 原因不明）显示「已停止」——用户自己停的他知道为什么、进程被杀他说了不算，写一句"App 被系统中断"只会让人
以为出了故障；出错（网络 / 超时 / 被限流 / Key 无效 / 余额不足）显示「⚠️ 原因」（如「⚠️ 网络断开」），因为
用户得知道问题在哪，否则会一直点「继续」而问题根本不在那儿。内容是逐段落库的，所以「继续」是**接着做**而不是
重试——指令里还写明「已经执行过的操作不要重复做」（依据是消息末尾那段「本轮执行：…」，见
[AI接入设计](AI接入设计.md) 的「断线续传」）。「知道了」只清标记、不删内容（内容是真实产出）。
正在生成的那条**不显示**这个提示条：它只是还没写完。

**「AI 在等你回答」是常驻提示条**：AI 用 `askUser` 提了问题就落库（挂起是持久化的），所以杀掉 App 重开也
照样能看到这条提示、点一下就接着答。答题层（`lib/features/ai/ui/agent_dialogs.dart` 的 `showAskSheet`）支持
输入文本 / 单选 / 多选 / 确认（好 / 不用），永远可以取消——"拒绝"是合法回答，也是用户从挂起状态脱身的唯一出口。

**选择题（单选 / 多选）的选项下面永远有一个输入框**，选项都不合适时可以自己写一句：

| 类型 | 输入框提示词 | 与选项的关系 |
|---|---|---|
| 单选 | 「也可以不选，直接写你的答案…」 | **互斥**：开始输入文字会自动取消已选选项，点选项会清空输入框。单选的语义就是"一个答案"，两者一起提交上去只会让模型猜哪个才算数 |
| 多选 | 「也可以自己写（一行一条）…」 | **可以并存**：选两条 + 自己再补一条都行 |

这个输入框是"看不上任何一条选项"时的正经出路：以前只认选项，那种情况下用户唯一的出路是点「取消」，
而**取消在语义上是拒绝**（模型会当成"他不做这件事"）——"我有别的想法"和"我不做"完全是两回事。
自己写的那句单独作为 `text` 回灌（不与选项 id 混在一起，否则模型会把一句话当成一个 id 用），`askUser` 的工具
说明里也写明"以它为准，别硬套回选项"。

**「确定」的可用性**：**写了字就算有答案**——单选是"选满一项**或**写了字"，多选是"至少一项**或**写了字"，
输入题是"文本非空"；都不满足时按钮是灰的，那就只剩「取消」。选项区可滚（选项多了不至于把弹层撑爆），
输入框固定在它下面；**没有可选项时不给空列表**，只提示「没有找到可选项。直接在下面写一句告诉我该怎么做。」
（同样是不逼用户先取消一次）。

另外两个细节：答题层是必须明确作答或取消的那种（代码里的 `isDismissible: false`）；输入题那个输入框的提示词是
「输入你的回答…」。

### 3.9 设置：首页只做导航

设置首页每一项都是「图标 + 名称 + 当前值 + 箭头」，点进去才改；从子页返回时首页自动刷新摘要。

```
设置
├── 个性化
│   └── 外观        当前主题（跟随系统 / 浅色 / 深色）
├── AI
│   ├── AI           已配置 Key / 尚未配置 API Key；未配 Key 时图标为错误色
│   ├── 查看余额     进入即查询 DeepSeek 账户余额
│   └── 用量与成本   查看累计 AI 花费
├── 数据
│   └── 存储与备份  当前目录（或「临时位置（有风险）」+ 错误色）
└── 其他
    └── 关于        版本、技术栈、隐私说明
```

**为什么这么分层**：破坏性操作（换工作目录、导入备份包）和日常开关（主题、字号）混在一页时很容易误触。
点进去才改，等于多了一道"我是来做这件事的"确认。

各子页要点：

| 子页 | 内容 |
|---|---|
| 外观 | 主题三选；正文字号滑块 0.8–1.4（6 档）+ 示例文字实时预览。只影响笔记正文的编辑与阅读视图，不影响界面其他文字 |
| AI | API Key（不明文回填，只显示状态；保存 / 测试连接 / 删除，删除有确认；Key 只在系统钥匙串，不进备份包）。不含模型与思考强度两项——两者都在 AI 页按会话选，放全局开关会与"按会话选"打架 |
| 存储与备份 | 数据库位置卡片（真实路径 + 状态 + 说明）、更换工作目录、诊断（把各候选路径与错误列出来）、导出备份包（.zip）、从备份包导入、清空 AI 历史；「恢复默认存储位置」只在当前不是私有目录时出现 |
| 账户余额 | 进入即调用 DeepSeek 的 `/user/balance`，展示各币种总 / 充值 / 赠送余额；失败可就地重试。只读，不改任何设置 |
| 用量与成本 | 累计估算成本 + 统计范围说明（清空 AI 历史会归零） |
| 关于 | 版本、技术栈、数据与隐私说明 |

**这一页集中了所有会碰数据文件、且不可逆或需要重启的操作**，各自的反馈：

| 操作 | 用户看到什么 |
|---|---|
| 导出备份包 | 桌面：系统保存对话框选位置。Android 没有保存对话框（`file_selector` 未实现 `getSaveLocation`），改成写进 App 缓存后拉系统分享面板让用户在「保存到文件 / 发微信 / 发网盘」里选去处。取消 = 不导出（不再兜底写私有目录）。完成后弹「备份已导出」或「备份包已生成」：路径（Android 上是「去分享面板选去处」）、大小、内容统计，并说明包里是标准 SQLite、不含 API Key |
| 从备份包导入 | 先校验，包不合法就弹「这个备份包不能用」+ 原因。合法则弹确认：备份时间、来源平台、内容摘要，并选覆盖当前数据或保留为另一个文件；明确说明导入前的旧库会改名 `before-import-….sqlite` 留在同目录。点「导入并重启」→ 因为数据库已打开无法原地替换，会再问一次「立即重启 / 稍后手动重启」 |
| 更换工作目录 | 目标目录里已有数据库时绝不覆盖，而是问：「使用它」（直接用那里的旧笔记，当前数据不带过去但留在原处）/「换个目录」/ 取消。正常切换会把数据一致性快照复制过去，然后询问重启 |
| 恢复默认存储位置 | 搬回 App 私有目录，同样询问重启 |
| 清空 AI 历史 | 确认框写清范围：删除每次调用的任务类型、模型、token 用量与估算成本；笔记正文、笔记库、卡片流预留不受影响 |
| 启动时完成了导入 | 顶部常驻提示「已从备份恢复：<摘要>」+ 旧数据留档路径，点「知道了」才消失——内容里有路径，3 秒自动消失等于没告诉 |

## 5. 提示（LogBar）的使用规范

全 App 只有 `lib/core/widgets/log_bar.dart` 一个地方直接操作 SnackBar，业务代码一律调它。
不是洁癖，是因为 Flutter 的 SnackBar 有两个坑：

1. **带按钮的提示永不消失**：`persist = persist ?? action != null`，而超时定时器遇到 `persist == true`
   直接 return。所以只要传了 `SnackBarAction`，`duration` 就被完全忽略。LogBar 统一显式指定 `persist`。
2. **SnackBar 是排队的**：前一条没走完，后一条一直等。所以 LogBar 在任务进行中（有 `busy`）时会丢弃普通
   提示——否则 AI 生成那几秒里用户点的几下，会在任务结束后变成一串过期提示刷屏。

| 级别 | 什么时候用 | 自动消失 |
|---|---|---|
| `info` | 中性反馈：确认、引导（没有成功/失败倾向） | 3 秒 |
| `success` | 操作做成了 | 3 秒 |
| `warn` | 做完了但结果不合预期（结果为空、被规则拦下） | 4 秒 |
| `error` | 失败，或挡住了用户想做的事 | 3 秒；能穿过 busy 被看到 |
| `action` | 带按钮（如撤销），或内容必须被看清（如备份留档路径） | 默认常驻，要自动走就显式传 `persist: false` |
| `busy` | 耗时任务进行中（带转圈，由返回的句柄收起） | 由句柄；兜底 5 分钟 |

- 怎么选：用户想做的事被挡住了 → `error`；做完了但结果不合预期 → `warn`；做成了 → `success`；
  纯粹告知 → `info`。`error` / `warn` 会带图标，扫一眼就能分辨"出问题了"还是"只是提示"。
- `busy` 必须用 `try / finally` 包，否则某条 `return` 越过了 `close()` 就会让转圈提示一直挡着。
- **撤销提示是 3 秒自动走的**：Flutter 的行为是"传了 `SnackBarAction` 就彻底忽略 `duration`"，所以时限只能靠
  `persist` 表达 —— 删除的「撤销」显式传 `persist: false`（3 秒），不然那条提示会一直压在列表上；**必须被看清
  的内容**（如备份留档路径）才用默认的常驻 +「知道了」。
- **没有撤销栈**：撤销就是提示条上那个闭包（`LogBar.action` 的 `onAction`，如 `repo.restore(id)`），只覆盖刚删的
  那一条；批量删除压根不给撤销（见 §3.4 的「删除的分工」）——撤销是"手滑了救一下"，不是版本历史。
- 需要先 pop 掉弹窗再提示时用 `LogBar.successTo(messenger, ...)`：pop 之后原 context 已失效，要在 pop 之前
  取好 messenger。
- 行为由 `test/log_bar_test.dart` 的 11 条用例锁住。

## 6. 空状态与文案

| 位置 | 文案 |
|---|---|
| 轻笔记（未选来源） | 「还没有选择素材来源」+「选几个笔记库，AI 会从里面长出新的轻笔记。」+ 按钮「选择笔记库」 |

| 轻笔记（来源被全部取消） | 与「未选来源」同一套文案——一个来源都不剩就等于没选来源，不另写一句（判据见 §3.1） |
| 笔记库（无笔记库） | 「还没有笔记库」+ 按钮「新建笔记库」 |

| 笔记库详情（空库） | 「该笔记库暂无笔记」+「点右下角 + 在这里新建一篇。」 |

| AI（未配 Key） | 设置页里 AI 项显示「尚未配置 API Key」并用错误色图标 |
| AI（未配 Key 以外的状态） | 没有授权闸门；未配 Key 时只影响设置页那一行提示 |
| AI 答题层（没有可选项） | 「没有找到可选项。直接在下面写一句告诉我该怎么做。」——不显示空列表（见 §3.8），也**不逼用户先取消一次** |

裁剪正文）的提示里要写清后果。

## 7. 关键行为约定

这几条容易在重构时被改坏，写下来：

| 行为 | 说明 |
|---|---|
| 删除笔记库不删笔记 | 库内笔记 `notebookId → null`、`isInbox → true`（回到「我的轻笔记」）。直接级联删笔记是数据丢失事故 |
| 未归档笔记必须可见 | `isInbox = false && notebookId IS NULL` 这种组合在两个入口都看不到，等于丢失。创建未归档笔记时写 `isInbox = true`，迁移里还修正过存量数据 |
| 笔记库是平铺的 | 没有层级、没有父子级联、界面上不提供"新建子笔记库" |
| 示例数据在启动时写 | 不能挂在某个页面上——轻笔记页要抽卡片，首屏就需要笔记库已存在 |
| AI 改数据没有确认层 | 写操作**调用即生效**（上一版的确认弹层与撤销栈已砍掉，见「AI 助手页」一节）。约束是结构性的：AI 只能发一条 `sql`，`SqlGuard` 只放行单条 `SELECT` / `WITH`，写操作只能调 `ai_functions` 里登记的写函数（业务上限在 UDF 里），直接写表 / DDL / 多语句一律被拒。事前唯一的防线是提示词规则 10"只在用户明确要求时才做"，事后留下的是消息末尾那段「本轮执行：…」 |
| AI 自己按需读笔记 | 请求里除了用户这句话（以及可能附在它末尾的几条检索素材，见 §3.8）不带任何笔记原文，也不做全库上传；AI 需要时自己在 `sql` 里调读函数（`outline_notes` / `read_note_batch` 等）按需读，读的范围是**整个笔记库**（不再有"勾选哪些笔记"这回事） |
| 卡片流不自动调 AI | 翻卡片不烧 token。卡片在补池 / 生成预留时产出，翻卡本身不发请求 |
| 追加只由下拉触发 | 首次进入替换（3 张）、下拉前向追加（每次新的 2 张插到最前面，累积成 5、7…）。滚动不做任何事——"滚到底自动加载"试过，但窗口重新布局（比如切后台回来）也会产生滚动通知，被误当成"用户滚到底"，卡片自己就往后长 |
| 每次看到的内容不重样 | 素材 = 片内的一小段窗口（大小见 `FeedWindow.chars`）；窗口位置轮换（`next_window_start`）、用过的片 `last_used_at` 落库（最久没用过的优先）、同一篇笔记在最近 15 张里最多出现 1 次 |
| 收下状态从库里推导 | 不记在页面内存里：卡片按"标题 + 正文"指纹（或本次会话记下的 noteId）实时对「我的轻笔记」；用户别处删了/改了，卡片跟着变 |
| 卡片/详情页只能收下，不能归档 | 收下的落点是「我的轻笔记」。收进指定笔记库要走笔记库页或编辑页（见 §8.5） |
| 空草稿不入库 | 新建笔记走"延迟创建"：标题与正文都空白就返回，库里不会留下空白笔记 |
| 手动保存 + 退出询问 | 只有勾与「保存并退出」两处写盘；退出时有未保存改动必须问，保存失败不许退出 |
| 笔记篇幅上限 | 正文 30 KB 轻提示 / 40 KB 强警告 / 50 KB 拒绝保存（可裁剪）；标题保存前截断到 200 字 |
| 一个列表只有一个顺序来源 | **界面上的笔记列表统一**用 `sort_order ASC, updated_at DESC`（`AppDatabase._noteListOrder`，库内 / 「我的轻笔记」/ 收件箱查询三处一起改过来的）：`pinned` **不是**独立的一层，置顶只是"挪到最前一次"+图钉，各处行为一致——左滑那颗按钮只写 `sort_order`，同一个动作绝不能靠两套机制生效（一处写手动顺序、一处看标记，改一处忘一处就分叉）。只有会话列表没有手动顺序，用 `pinned DESC, updated_at DESC`，置顶在那里就是字面意思的"钉住"。做成两层一定会出现"拖上去又被顶回来"的吸附 |
| 左滑只露出按钮，不直接执行 | `SwipeActions`（`flutter_slidable`）划开露出「置顶 / 删除」，点了才做；删除仍然给「撤销」 |
| 换库必须重启 | 导入备份、换工作目录都要重启才生效，因为数据库已打开时无法安全替换文件 |
| 破坏性操作先留档 | 导入前旧库改名留档（`before-import-….sqlite`）；导出只出用户要的那一份，不在私有目录另留 |

## 8. 明确不做（刻意没有的功能）

这里记的是刻意没有的功能。这类东西不写下来，下一轮很容易被当成漏做而补上——而它们当初都是有理由被拿掉的。
最后一小节 §8.5 相反：那是"还没打通"，不是"不做"。

### 8.1 卡片流

| 没做 | 为什么 |
|---|---|
| 卡片持久化 | 生成结果只在内存，收下才落库。卡片是"随手刷到的东西"，不是收藏品。（唯一例外：跨启动预留） |
| 卡片上的摘要 / 预览 | 两种做法都试过：截正文前 N 字读起来像被截断；让 AI 单独生成摘要要维护两个内容字段，而且模型不守字数（要求 45–60 字，稳定返回 116–160 字）。定案是只有标题 |
| 收藏 / 不感兴趣 / 到期复习 | 那是上一版"复习已有笔记"的配套（`note_feed_state` 的到期时间、间隔天数、难度因子、收藏），卡片改成 AI 新生成之后就没有意义了；配套的记忆卡片功能后来也整体移除 |
| 收下前编辑内容 | 卡片是只读预览，内容此刻还没落库。要编辑就先收下——收下后它就是一条普通笔记 |
| 卡片上的左右滑手势 | 左滑删除只属于笔记列表项；卡片内容还没落库，没有可删的对象 |
| 收下时选笔记库 / 从卡片或详情页新建笔记 | 收下的落点固定是「我的轻笔记」（见 §3.2、§8.5） |

### 8.2 搜索

| 没做 | 为什么 |
|---|---|
| FTS5 / bigram 分词索引 | 在项目自带的 SQLite 上实测：`unicode61` 把整段中文当成一个 token（2/3/4 字查询都是 0 条）；`trigram` 要求查询 ≥3 字符，中文最常见的 2 字词必然 0 条。`LIKE '%词%'` 各种长度都命中，先用它 |
| 拼音搜索 | FTS5 没有拼音分词器，要额外存一列转写 + 一份词典 |
| 搜索页的语义搜索（RAG / embedding） | 搜索页至今仍是关键词匹配（`LIKE '%词%'`），空结果里也直说"当前是关键词匹配，不是语义搜索"。**但当初那条理由（"RAG 太重，一点都不轻量化"）后来被推翻了**：语义检索真的做了，只是没接到搜索页——它走的是 **AI 请求前的素材注入**那一路（本地算向量 + 关键词两路融合，见 §3.8），要的是"给 AI 更准的上下文"，不是"把搜索页换成语义搜索" |
| AI 查询改写（扩词） | 列为后续可选项，本次不做 |

### 8.3 AI 与数据安全

| 没做 | 为什么 |
|---|---|
| 回收站 / 恢复入口 | 产品决定不做。删除的内部实现仍是软删除（`deletedAt`，数据还在库里），但没有恢复入口——所以删除类操作没有撤销（笔记列表的单条左滑删除还有一条 3 秒的「撤销」提示，批量删除和 AI 的删除都没有），事前只能靠用户自己看清 |
| 让 AI 碰敏感数据 | 通道里根本没有"改设置 / 改 API Key / 文件系统 / 清空数据库"这一类入口：AI 只能发一条 `sql`，`SqlGuard` 只放行单条 `SELECT` / `WITH`，写操作只能调 `ai_functions` 里登记的函数，业务上限写在 UDF 里——这是结构性保证。**注意它不是靠确认层拦的**：这一版没有确认层 |
| 批量超过 10 条 / 删除全部 | 灾难性操作 |
| 笔记的版本号列 | 用"全文快照比对 + 锚点校验"就够了，不为此引入版本列 |
| 每篇笔记的用户可见摘要 | 展示型摘要随 v7 删除；后来的卡片流素材摘要（`ai_note_summaries`）也随 schema v12 删除——卡片素材改成一段截断的原文，用户始终看不到任何摘要 |
| 会话切片落库 | 现算毫秒级；落库会让表跟着对话无限增长 |
| 历史全量重发 | 只带最近 5 轮、单条截断 500 字——历史是每条消息都重发的，不设上限成本是 O(N²) |

### 8.4 已经删掉、别再加回来（墓碑清单）

| 已经删掉 | 什么时候 |
|---|---|
| Markdown 导出（编辑页「导出 Markdown」/ 设置页「导出全部」） | 2026-10 |

| 「自动保存」开关 | 保存方式定案为手动（见「笔记编辑页：编辑 / 阅读两态」一节） |
| 「AI 数据使用授权」开关与首次隐私横幅 | 授权确认机制整体去掉（见「AI 助手页」一节） |

AI 工具从 22 个 function-calling 工具收敛成 1 个 SQL 工具（`sql`）+ 挂起用的 `askUser`，是同一类决定：
所有操作都写成 SQL —— 查列表用 `list_notes`、取目录与元信息用 `outline_notes`、定位正文用 `find_in_note` /
`read_around`（一次读一批用 `read_note_batch`）。语法与边界见 [AI操作数据库设计](AI操作数据库设计.md)，这里不展开。

### 8.5 已知差距：归档那一步是断的

不是"不做"，是还没打通，所以别把它当成已经有的能力。

「轻笔记」这条链目前是：卡片生成 → 点开看全文（详情页，只读）→ 「加入我的轻笔记」。到"归进某个笔记库"就断了：

| 能做到 | 做不到 |
|---|---|
| 卡片上「加入我的轻笔记 / 从我的轻笔记移出」 | 卡片或详情页上选一个笔记库直接归档 |
