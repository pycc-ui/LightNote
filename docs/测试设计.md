# 测试设计

LightNote 的测试总览：怎么跑、分几类、每份文件在验什么、踩过哪些坑。

当前 `test\` 下共 26 份测试文件、418 个用例（`test(` 358 个 + `testWidgets(` 60 个）。
曾经另有 3 份需要真实 API Key 的真机测试（`live` 标签，6 个用例），已删除，见第四节。

命令语言改造后，旧的 function-calling 工具层测试（`tool_specs_test`、`tool_executor_test`、
`tool_write_test`、`tool_delete_test`、`agent_workspace_test`）与笔记摘要测试（`ai_asset_test`）
已随功能一起删除；`agent_loop_test` 已按命令语言重写。命令语言自身的语法测试见
[命令语言设计](命令语言设计.md) §13。

## 一、总约定：大版本发布前才跑测试

规矩是：**测试没有大版本发布前不要做。**

- 日常改动不跑 `flutter test`，也不跑发布前的全量验证（见第二节）。
- 大版本发布前跑一次全量（26 份 / 418 个用例）。
- 日常自检靠这三样：
  1. `flutter analyze`
  2. `flutter build windows --debug` —— 以编译结果为准，`analyze` 对刚保存的改动有缓存延迟，
     偶尔会说 "No issues found" 而实际编译报错
  3. 手动打开 App，把这次改动的那条路径走一遍

为什么这么定：

- 测试主要是一张历史缺陷的回归网（第六节的每份文件背后几乎都有一次真实 bug），日常改动碰不到网上的结。
- 那 3 份真机测试要真实 API Key、会真的花钱，本来就不能进日常循环。
- 全量跑一次要起几十个测试进程、建一批临时库，窗口期成本高于收益。

真要确认某一处时，只跑那一个文件：

```powershell
flutter test test\note_chunker_test.dart
```

## 二、怎么跑（Windows）

命令一律在工程根目录执行，直接用 `flutter` 命令（需要 Flutter SDK stable 与 Dart 工具链）。

| 目的 | 命令 |
|---|---|
| 跑测试 | `flutter test` |
| 静态分析 | `flutter analyze` |
| 只跑一个文件 | `flutter test test\note_chunker_test.dart` |
| 发布前全量验证 | ① `flutter analyze` ② `flutter test` ③ `flutter build windows --debug` ④ 启动构建出的程序，确认能建库、能打开 |

单文件 / 单个分组的跑法：

```powershell
flutter test test\note_chunker_test.dart
flutter test test\note_chunker_test.dart --plain-name "空与短"
```

`flutter test` 之后的参数原样透传，不会重新拆词。

## 三、测试分工

| 类别 | 文件数 | 用例数 | 测什么 | 不测什么 |
|---|---|---|---|---|
| 单元 / 数据层 | 19 | 324 | 纯函数（切片、窗口、命中位置、篇幅分档）、仓储语义（软删、级联、事务、幂等、回填与自愈）、AI 协议拼装与 Agent 主循环的终止条件、`askUser` 挂起 | 屏幕上渲染出什么、真实网络、真实文件系统 |
| widget | 5 | 62 | "渲染出来是什么、点下去返回什么"：AI 确认层/答题层、编辑页生命周期、卡片底部布局、LogBar 计时、阅读视图按片渲染与定位 | 数据库语义（依赖用内存库兜住） |
| 迁移与备份 | 2 | 32 | 真实文件库上的 schema 升级（v1 → v12）、备份包的导出/校验/启动换库 | 界面、网络 |

分类依据（写在测试文件的头注释里）：

- **数据层一律用真实（内存）数据库**：`AppDatabase.forTesting(NativeDatabase.memory())`。
  工具的活儿就是查库与切片的组合，mock 掉数据库等于什么都没测。
- **界面类必须 widget 测试**：正确性全在"屏幕上出现了什么"，而且有些缺陷出在页面生命周期上
  （`dispose` → `_flush()` → `saveContent`），纯数据层测不出来。
- **迁移必须在真实文件上测**：迁移只在打开已存在的库时触发，内存库测不到，所以 `migration_test.dart`
  手工造 v1 形态的库文件。
- **手势故意不测**：`Dismissible`、多选顶栏属于 UI，跟手写用例价值低、易脆；真正容易做错的是它背后的
  数据语义，所以 `list_actions_test.dart` 只测数据层。

## 四、真机测试（`live` 标签）——已删除

这里曾经有 3 份需要真实 API Key 的集成测试（共 6 个用例）：文件首行打 `@Tags(['live'])`，
`..\dart_test.yaml` 给 `live` 标签配 `skip`，所以日常 `flutter test` 不会执行它们。

| 文件（已删除） | 用例 | 验什么 |
|---|---|---|
| `agent_live_test.dart` | 1 | 阶段 0 真机验收：真实服务端接不接受我们拼的 `tools` / `tool_choice` / `role: tool` 形状；流式下 `tool_calls` 的真实分片方式；`arguments` 到底给不给合法 JSON。只放一个"零参数、无副作用、答案确定"的 `listNotebooks`，失败就一定是协议/鉴权问题 |
| `agent_search_live_test.dart` | 1 | 阶段 5 真机验收：问"我关于 X 写了什么"，AI 是否自己搜到笔记、读懂 `listChunks` 的目录、`readChunk` 读到那一片并引用原文作答。关键事实故意埋在离查询词约 600 字处（摘要 ±40 字窗口够不到），模型想答对就必须自己去读 |
| `feed_live_test.dart` | 4 | 卡片流生成：真调能为笔记生成摘要与标签并入库、预留入库且每次进入只展示 3 张、能从素材生成可解析的轻笔记、收下后成为一条真正的未归档笔记 |

### 为什么删

不会真的去跑，留着只是维护负担。三条负担都是真的：

- **要真机**：得有一台装好 App 的设备，以及能通的网络与代理（不通就红，红的原因是机器而不是代码，
  混进日常流水线只会污染信号）；
- **要真钱**：这 6 个用例会真的打到付费接口；
- **要维护**：标签配置、3 份文件里的 `skip` 理由与跑法说明（Key 从环境变量读、跑的时候要显式指定标签），
  都得跟着代码一起改——而它们从写下来那天起就没被跑过。

### 删掉的代价

删掉之后，下面三类现在完全没有测试覆盖，回归只能靠人工（发版前手动把这几条路径走一遍）：

1. **协议报文形状** —— 请求体里的 `tools` / `tool_choice` 服务端收不收、`role: tool` 回灌的形状对不对。
   假模型是我们自己写的，它当然照收。
2. **模型会不会主动用工具 / 命令** —— 假模型只会走我们写好的那条路，"它会不会自己搜、自己读"只能真调一次
   才知道。原来的 `agent_search_live_test.dart` 靠把关键事实埋在离查询词约 600 字处，逼模型自己走完
   `searchNotes` → `listChunks` → `readChunk`；换成命令语言后，对应的是模型自己写出 `grep` / `sed -n`。
3. **真实 SSE 的分片方式** —— 增量 `arguments` 到底分几片、怎么切、给不给合法 JSON。用假 SSE 只能模拟
   我们以为的形状。

将来若又要加回来：`..\dart_test.yaml` 里把 `tags: live: skip:` 加回去、测试文件首行加
`@Tags(['live'])` 即可。

### 哪些验收项靠测试守住、哪些只能真机跑

先分类再决定怎么验，能省下一次白跑的真机：

| 验收项 | 谁守住 | 说明 |
|---|---|---|
| 中文 2 字 / 中英混合 / 不存在的词都能搜到 | `search_service_test.dart` | 纯函数 + 真实内存库，假数据足够 |
| 结果分两类、点正文命中能定位到片 | `search_service_test.dart` + `search_ui_test.dart` | 片号来自落库的切片，与阅读态同一套规则 |
| 历史自动 5 轮 / 单条 500 字 | `history_window_test.dart` | 窗口钉死不随对话变长 |
| 工具调用链不被从中间截断 | `history_chunker_test.dart` | 片边界只落在完整轮次上 |
| 更早历史的摘要只生成一次 | `history_summary_test.dart` | 用"数调用次数"验证，不靠人看日志 |
| 风险拦截与模型行为解耦、删除措辞、一次提议只执行一次 | `agent_dialogs_test.dart` | 判据全在 App 侧，故意不依赖模型 |
| `askUser` ≤5（跨恢复）/ 轮数上限 15 | `agent_loop_test.dart`、`ask_flow_test.dart`、`ask_user_test.dart` | 造个假模型就能测到上限，不用花额度 |
| 命令语言的 9 个命令、4 个原语、执行上限（50 条 / 200 行 / 50 命中 / 100 次循环） | 暂无自动化测试 | 实现已落地（`command/`），测试尚未补齐，见 [命令语言设计](命令语言设计.md) §13 |

上表之外还有三类只有真调一次才验得到（协议报文形状、模型会不会主动调工具、真实 SSE 的分片方式）。
真机测试删掉之后，这三类没有自动化覆盖，只能在发版前靠人工走一遍。

顺带两样也只能真机验：**Key / 网络 / 代理到底通不通**；**生成参数**——思考模式默认开启，
`max_tokens=20` 时 20 个 token 全被思考吃掉、正文返回空串，所以生成类调用显式关掉了思考，
而假模型永远不会有这个现象。这两样同样没有自动化覆盖。

**（如果将来再写真机测试）不要断言"模型的自然语言"**：只断言结构与入库（能解析、能入库、条数对）。
模型根本不守字数——要 45~60 字的摘要，它稳定返回 116~160 字；摘要与标签的兜底因此必须在代码里
（`..\lib\core\util\ai_limits.dart`）。

**成本预算类的两条不能当成断言**（措辞比实际严格）：

- "单批输入 ≤4000 字"是设计预算、运行时不强制：真实 prompt 还含"避开标题"清单，
  整段会超过 4000。测试守住的是素材正文 ≤4000（`feed_window_test.dart`）。
- "命令脚本一次 ≤50 条 / `sed -n` 读 ≤200 行 / `grep` 命中 ≤50"是设计上限，由
  `CommandLimits`（`app_params.dart`）在解释器里强制；目前没有直接测这些边界的用例。

还有一批指标只能上线后观察、测试测不出来：工具 token 占比、确认层拒绝率、命令语法错误率、
自愈触发次数、卡片重复率、挂起未恢复的会话数。

## 六、测试与实现踩过的坑

### 测试数据与断言

**1. 周期性测试数据会让"轮换"看起来没生效** —— `feed_window_test.dart`

造"位置可辨认"的数据时，周期性是最容易踩的坑，而且踩两次：

- `'内容句子。' * 140`：周期 5，而 300 是 5 的倍数 → `body[0..400]` 与 `body[300..700]` 字面上完全相同
- `String.fromCharCode(0x4E00 + (i % 400))`：周期 400 < 700 → `body[650..700]` 那 50 个字照样能在
  `body[0..400]` 里找到

两次都让"轮换看起来没生效"，而实现其实是对的。结论：要造"位置可辨认"的正文，必须让每个下标对应一个
独一无二的字（不取模）。

**2. 会话历史每轮长度必须落在 [300, 700]，且断言不许硬写片数** —— `history_chunker_test.dart`

每轮长度要落在 [300, 700] 才会"一轮一片"：太短（< 300）被合并成一片；太长（> 700）一轮被拆成两片。
所以断言里不硬写片数，而是拿切片器的结果当基准。

**3. 假时间戳按"消息序号"递增会让两轮交错** —— `history_chunker_test.dart`

时间必须整轮递增，不能按消息条数递增。早先用同一个"消息序号"当秒数，于是第 2 轮的 user 落在
`00:00:02`、而第 1 轮的 assistant 落在 `00:00:05` —— 按时间排序后两轮交错，`HistoryChunker` 的分组自然全乱。
那是测试数据不真实（真实对话的时间天然递增），不是实现的问题。

**4. 配置锚点会跨用例、跨测试进程互相污染** —— `backup_test.dart`

配置锚点之一是「程序所在目录」，而在测试进程里 `Platform.resolvedExecutable` 指向 dart SDK 的
`bin\dart.exe`——那里的 `storage.json` 会跨测试用例、跨 test 进程一直留着，上个用例写的 workingDir
会被下个用例读到。而且绝不能污染开发者的真实配置：往 dart SDK 目录写个指向临时目录的 `storage.json`，
之后又用那个 SDK 跑了 App，就会用错工作目录。

处置：每个用例 `setUp` / `tearDown` 都 `_clearAllConfigAnchors()` + `DatabaseLocation.resetCacheForTesting()`，
且 tearDown 里先清配置再清目录。

**5. Windows 上临时目录偶尔删不掉（文件句柄还没释放）** —— `backup_test.dart`

不影响断言。

**6. `pump` 一次性推进时间不会触发中途到期的 Timer** —— `log_bar_test.dart`

两个坑：时间要分步推进（`pump(Duration(seconds: 4))` 只渲染一帧、不让中途 Timer 触发，据此得出的结论会错）；
点击前要等入场动画跑完，否则按钮透明度为 0，hit test 打不中。

**7. 迁移测试里的表名/列名不能提前改成新名字** —— `migration_test.dart`

这里必须叫 `folders`、必须有 `parent_id`：迁移测试要模拟真实老库，表名与列名都不能提前变成新名字，
否则测的就不是迁移了。

**8. 要断言的"被删表"必须先在 v1 脚本里建出来** —— `migration_test.dart`

它不是 v1 的原生表，写在这里是为了让 v8 的 `DROP TABLE` 真的作用到东西，否则那两条删表语句在测试里是空转。
同源的一条：漏建表会让整个迁移失败——drift 的 `Migrator.createAll()` 只创建"尚不存在"的表，而迁移末尾会调用
`_createIndexes()`，那条语句要给 `ai_messages` 等表建索引，表不存在就会整个迁移失败。（`ai_note_summaries`
的索引曾是受害者，该表已随 v12 删除。）

**9. drift 与 flutter_test 的 `isNull` / `isNotNull` 同名冲突** —— `data_layer_test.dart`

drift 导出的 `isNull` / `isNotNull` 与 flutter_test 的 matcher 同名，会报 `ambiguous_import`。
写法：`import 'package:drift/drift.dart' hide isNull, isNotNull;`（`ask_user_test.dart`、
`history_window_test.dart`、`history_summary_test.dart`、`note_chunk_repository_test.dart`、
`backup_test.dart` 同样处理。）

**10. 存储 key 改名时不能反向复用老 key** —— `feed_source_test.dart`

这两个 key 的名字不能变回 `feed_source_notebooks`：老数据里那个 key 存的是"包含集"，
当"排除集"读会把来源整个清空。

**11. 修顺序不等于修契约** —— `ai_init_race_test.dart`

修法不是在 main 里补一个 await（那只是把顺序碰对，下次改别处又会踩）。所以这条回归测的是
"不显式 `init` 也能正常发请求"，而不是"main 里的调用顺序对不对"。

**12. `SnackBarAction` ⇒ `persist` 默认 true ⇒ `duration` 被完全忽略** —— `log_bar_test.dart`

那个 bug 光读 `log_bar.dart` 看不出来——那里明明写了 `duration: 3` 秒。真正的开关在 Flutter 内部：

```
// snack_bar.dart
persist = persist ?? action != null;        // 有 action 就默认 true
// scaffold.dart
_snackBarTimer = Timer(snackBar.duration, () {
  if (snackBar.persist) return;             // 直接返回，永不超时
  hideCurrentSnackBar(reason: timeout);
});
```

所以：传了 `SnackBarAction` ⇒ `persist` 默认 true ⇒ `duration` 被完全忽略。

### 实现时踩过的坑

`arguments` 也可能不是合法 JSON。根因：把模型当成"守格式的函数"，测试数据只造了理想输入。对策：

`TODO`：`normalizeTag` 目前只有代码兜底、没有直接用例。

**15. `expect(version, 常量)` 是永真断言，抓不到"忘改常量"** —— `migration_test.dart`

**16. 测试自己的缺陷会和实现缺陷长得一模一样** —— `note_chunker_test.dart`

切片用例红了一片，其中四个是测试自己的错：期望片数写错、断言范围过宽、用 20 字单元去套 200 字单元算出的
期望值、把围栏长度估成 810（实测 677）。根因：期望值是手算的或照抄文档伪代码的，不是从规则推出来的。
对策：期望值尽量由被测的同一套规则算出来，不硬写数字；断言限定到区域 / 偏移 / 时间上；红了先怀疑数据与
期望值，再怀疑实现。

**17. 切片类用例必须有一条"内容全丢"的兜底不变量** —— `note_chunker.dart`

实现两次出现"整篇 0 片、内容全丢"（片起点从"标题之后"算而不是节的起点、`_splitByLines` 遇到单行超长
直接返回空）。根因：分层切分每一步都可能产出空集合，而"某片内容对得上"这类断言在没有片时是空转。
对策：正文非空时断言片数 ≥ 1，再跑一遍"所有片合起来覆盖全部正文"的整体校验。

对策：让每段 > 350 字（370 × 2 = 740 > 700，两段装不进一片，于是段数就是片数）；夹具定义放 `main()`

**28. 给"没要求的功能"写测试是白费——先确认需求存在** —— `inbox_page.dart`

对策：写测试前先问"这条行为是谁提的需求"；用户已有的改动不要擅自改。

**29. 流式写库必须幂等，而"单事件假客户端"测不出来** —— `ask_flow_test.dart`

有些回答里同一句话按字数递增地重复上百遍（`已` / `已删除，` / `已删除，「我的轻笔记」…` 这种锯齿），

对策：续写起点在 `run()` 开始时读一次就定死，写入是「起点 + 累计文本」的覆盖（重复写同一个累计文本必须幂等）；

对策：派生字段只留一个纯函数入口（`TextUtils.excerpt` / `TextUtils.wordCountOfMarkdown`），所有写入方都调它；

### 中断测试会留下进程锁住 `sqlite3.dll`

这条不是从测试注释里读到的，是开发过程中实测遇到的。收录它是因为这类失败极难自查：报错信息把人引向
完全错误的方向。

现象：测试被中断过几次（超时、手动终止）之后，后续 `flutter test` 会直接失败：

```
Flutter failed to delete file at "...\build\native_assets\windows\sqlite3.dll".
The flutter tool cannot access the file or directory.
Please ensure that the SDK and/or project is installed in a location that has
read/write permissions for the current user.
```

这段话会让人去查目录权限——但那不是原因。真实原因是残留的 `dart.exe` / `flutter_tester.exe` 进程仍然持有
那个 DLL。处理：先杀掉残留进程再跑。

```powershell
Get-Process -Name flutter_tester,dart -ErrorAction SilentlyContinue |
  Stop-Process -Force
```

这是"中断测试"的真实代价：它不只丢一次结果，还会让接下来几次跑测全部失败，而且失败信息指向错误方向——
日常按约定不跑全量测试时，更容易被误判成"环境坏了"。与第 5 条（`backup_test.dart` 的 Windows 文件句柄
未释放）是同一类问题，但影响面不同：那条只影响一个用例的临时目录，这条会让整个测试进程起不来。

### `unawaited` 的后台任务必须吞异常 —— `feed_repository.dart`

现象：`warmup_test` 的 `tearDown` 关掉数据库之后，后台补池的任务才走到查库那一步，抛出
`Bad state: Can't re-open a database after closing it`——而这个异常被算到上一个测试头上，看起来像一次
完全无关的失败。根因：`refill` / `_reserveTail` 这类调用在 `unawaited` 里，异常没人接，就成了未捕获的
异步错误；测试进程会把它归给"当时正在跑的那个测试"。对策：fire-and-forget 的任务自己 `catchError` 吞掉
并打一行日志（补池是尽力而为，真失败了下拉刷新会按需生成）。

### 「新建的笔记库没进来源」那次缺陷

现象：启动 App → 在「笔记库」新建一个库 → 切回「轻笔记」→ 新库不在来源里；重启 App 又会自己好。

根因（两个 bug 叠在一起）：

- 来源当时存的是一份包含集快照 + 一段对账，而对账只在页面 `initState` 跑一次；三个 tab 用 `IndexedStack`
  保活（切标签不重建页面）→ 对账再也不发生。"重启就好"正是它的指纹。
- 来源页的「保存」无条件把用户标记成"改过"——用户打开看一眼、什么都没改、点保存，需求（新库默认勾选）
  就永久失效，而界面上没有任何迹象。

修法：来源的"真值"从「存下来的包含集快照 + 对账」改成「当前全部笔记库 − 用户明确排除的」，每次现算；
解析收进仓储层，调用方不能再塞一份来源进去（`feed_repository.dart`）。

凡"把当前状态存成快照、之后再对账"的设计，都要盯这几条：

- **缓存 / 快照类缺陷，必须"不重启"验**：新建库 → 切回目标页 → 立刻生效（页面被 `IndexedStack` 保活，
  `initState` 不会再跑）；触发路径不止一条（切 tab、下拉刷新、后台补池），都要走同一次现算。
- **"读"与"写"分开验**：全新安装结果 = 全选且一个 key 都不写（默认态是算出来的）；打开来源页什么都不改、
  直接保存 → 零写入（代码用 `_sameAs` 挡掉）；打开页面时刚建的库是勾上的；`writeSource` 存的是"没勾上的"。
- **三条需求必须能同时成立**：取消 X → 重启后仍不含 X → 重新勾上能恢复；在"取消过 X"的状态下新建 Y →
  Y 自动勾选、X 仍不含；全部取消 → 仍显示引导；「恢复默认」回到默认态且已在默认态时该入口不可用。
- **脏数据与老数据**：删掉一个笔记库 → 来源里不残留它的 id；老 key（`feed_source_notebooks`）不被读取；
  排除集的 JSON 损坏 → 当成"没排除任何"，不是崩，更不是全排除。
- **结构性盯点**：只要设计里出现"把当前状态存成快照、之后再对账"，就问一句"没有触发对账的路径怎么办"
  （保活页面、后台回调、别的入口）；任何"解析"都不要留在调用方——收进边界层；「保存」必须能区分
  "用户真的改了"和"用户只是点了一下"。

这条缺陷的回归网是 `feed_source_test.dart`（16 个用例），它守的是仓储层。页面上那两条
（"什么都不改直接保存"、"打开时刚建的库是勾上的"）以及结构性盯点目前只有代码保证、没有用例——
来源页没有 widget 测试。
