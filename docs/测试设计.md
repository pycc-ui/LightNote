# 测试设计

LightNote 的测试总览：**怎么跑、分几类、每份文件在验什么、踩过哪些坑**。

本文只讲测试。当前 `test\` 下共 **32 份**测试文件、**591 个**用例
（`test(` 531 个 + `testWidgets(` 60 个，从源码数出来的）。曾经另有 **3 份**是
需要真实 API Key 的真机测试（`live` 标签，6 个用例），**已按用户定案删除**，见第四节。

---

## 一、总约定：大版本发布前才跑测试

用户定的规矩，原文照录：

> **「测试没有大版本发布前不要做」**

具体含义：

- **日常改动不跑 `flutter test`**，也不跑发布前的全量验证（见第二节）。
- **大版本发布前**跑一次全量（32 份 / 591 个用例），一条命令见第二节。
- 日常自检靠这三样：
  1. `flutter analyze`
  2. `flutter build windows --debug` —— **以编译结果为准**，`analyze` 对刚保存的改动有缓存延迟，偶尔会说 "No issues found" 而实际编译报错
  3. 手动打开 App，把这次改动的那条路径走一遍

为什么这么定：

- 测试主要是一张**历史缺陷的回归网**（第六节的每一份文件背后几乎都有一次真实 bug），日常改动碰不到网上的结。
- 那 3 份真机测试要真实 API Key、**会真的花钱**，本来就不能进日常循环；
  它们现已删除（第四节说明为什么删、代价是什么）。
- 全量跑一次要起几十个测试进程、建一批临时库，窗口期成本高于收益。

真要确认某一处时，唯一不违反这条的做法是**只跑那一个文件**（这不叫"跑测试"，是查单点）：

```powershell
flutter test test\note_chunker_test.dart
```

## 二、怎么跑（Windows）

命令一律在工程根目录执行，直接用 `flutter` 命令（需要 Flutter SDK stable 与 Dart 工具链）。

| 目的 | 命令 |
|---|---|
| 跑测试 | `flutter test` |
| 静态分析 | `flutter analyze` |
| 只跑一个文件 | `flutter test test\note_chunker_test.dart` |
| 发布前全量验证 | ① `flutter analyze` ② `flutter test` ③ `flutter build windows --debug` ④ 启动构建出的程序，确认能建库、能打开 |

单文件 / 单个分组的跑法：

```powershell
flutter test test\note_chunker_test.dart
flutter test test\note_chunker_test.dart --plain-name "空与短"
```

`flutter test` 之后的参数原样透传，不会重新拆词。

## 三、测试分工

| 类别 | 文件数 | 用例数 | 测什么 | 不测什么 |
|---|---|---|---|---|
| 单元 / 数据层 | 24 | 463 | 纯函数（切片、窗口、命中位置、标签规整、篇幅分档）、仓储语义（软删、级联、事务、幂等、回填与自愈）、AI 协议拼装与 Agent 主循环的终止条件 | 屏幕上渲染出什么、真实网络、真实文件系统 |
| widget | 5 | 57 | "渲染出来是什么、点下去返回什么"：AI 确认层/答题层、编辑页生命周期、卡片底部布局、LogBar 计时、阅读视图按片渲染与定位 | 数据库语义（依赖用内存库兜住） |
| 迁移与备份 | 2 | 32 | **真实文件库**上的 schema 升级（v1 → v11）、备份包的导出/校验/启动换库 | 界面、网络 |

（原来还有第四类「真机（live）」3 份 / 6 个用例，已删除，见第四节。）

分类依据（都写在测试文件的头注释里）：

- **数据层一律用真实（内存）数据库**：`AppDatabase.forTesting(NativeDatabase.memory())`。
  工具的活儿就是查库与切片的组合，mock 掉数据库等于什么都没测。
- **界面类必须 widget 测试**：正确性全在"屏幕上出现了什么"，而且有些缺陷出在
  **页面生命周期**上（`dispose` → `_flush()` → `saveContent`），纯数据层测不出来。
- **迁移必须在真实文件上测**：迁移只在打开**已存在**的库时触发，内存库测不到，
  所以 `migration_test.dart` 手工造 v1 形态的库文件。
- **手势故意不测**：`Dismissible`、多选顶栏属于 UI，跟手写用例价值低、易脆；
  真正容易做错的是它背后的数据语义，所以 `list_actions_test.dart` 只测数据层。

## 四、真机测试（`live` 标签）——已删除

**这里曾经有 3 份**需要真实 API Key 的集成测试（共 6 个用例）：文件首行打
`@Tags(['live'])`，`..\dart_test.yaml` 给 `live` 标签配 `skip`，所以日常 `flutter test`
不会执行它们（`skip` 的两条理由：**会真的花钱**、**依赖代理与网络，机器不通时会误报失败**）。

| 文件（已删除） | 用例 | 验什么 |
|---|---|---|
| `agent_live_test.dart` | 1 | **阶段 0 真机验收**：真实服务端接不接受我们拼的 `tools` / `tool_choice` / `role: tool` 形状；流式下 `tool_calls` 的真实分片方式；`arguments` 到底给不给合法 JSON。只放一个"零参数、无副作用、答案确定"的 `listNotebooks`，失败就一定是协议/鉴权问题 |
| `agent_search_live_test.dart` | 1 | **阶段 5 真机验收**：问"我关于 X 写了什么"，AI 是否**自己**搜到笔记、读懂 `listChunks` 的目录、`readChunk` 读到那一片并**引用原文**作答。关键事实故意埋在离查询词约 600 字处（摘要 ±40 字窗口够不到），模型想答对就必须自己去读 |
| `feed_live_test.dart` | 4 | 卡片流生成：真调能为笔记生成摘要与标签并入库、预留入库且每次进入只展示 3 张、能从素材生成可解析的轻笔记、收下后成为一条真正的未归档笔记 |

### 为什么删

用户定案：**不会真的去跑**，留着只是维护负担。三条负担都是真的：

- **要真机**：得有一台装好 App 的设备，以及能通的网络与代理（不通就红，红的原因是机器而不是代码，
  混进日常流水线只会污染信号）；
- **要真钱**：这 6 个用例会真的打到付费接口；
- **要维护**：标签配置、3 份文件里的 `skip` 理由与跑法说明（Key 从环境变量读、
  跑的时候要显式指定标签），都得跟着代码一起改——而它们从写下来那天起就没被跑过。

### 代价如实写明

删掉之后，下面三类**现在完全没有测试覆盖**，回归只能靠人工（发版前手动把这几条路径走一遍）：

1. **协议报文形状** —— 请求体里的 `tools` / `tool_choice` 服务端收不收、`role: tool` 回灌的形状对不对。假模型是我们自己写的，它当然照收。
2. **模型会不会主动调工具** —— 假模型只会走我们写好的那条路，"它会不会自己搜"只能真调一次才知道。原来靠 `agent_search_live_test.dart` 把关键事实埋在离查询词约 600 字处（摘要的 ±40 字窗口够不到），模型想答对就**必须**自己走完 `searchNotes` → `listChunks` → `readChunk`。
3. **真实 SSE 的分片方式** —— 增量 `arguments` 到底分几片、怎么切、给不给合法 JSON。用假 SSE 只能模拟我们**以为**的形状。

将来若又要加回来：`..\dart_test.yaml` 里把 `tags: live: skip:` 加回去、测试文件首行加
`@Tags(['live'])` 即可（那个文件保留着这段说明与删除原因）。

### 哪些验收项靠测试守住、哪些只能真机跑

验收标准那一批条目不是同一类东西。先分类再决定怎么验，能省下一次白跑的真机：

| 验收项 | 谁守住 | 说明 |
|---|---|---|
| 中文 2 字 / 中英混合 / 不存在的词都能搜到 | `..\test\search_service_test.dart` | 纯函数 + 真实内存库，假数据足够 |
| 结果分两类、点正文命中能定位到片 | `search_service_test.dart` + `..\test\search_ui_test.dart` | 片号来自落库的切片，与阅读态同一套规则 |
| `listChunks` 不含正文 | `..\test\tool_executor_test.dart` | 有专门用例断言编码后的目录里没有正文片段 |
| `readChunk` 每轮 ≤3 片、≤1500 字 | `tool_executor_test.dart` | `beginTurn()` 每轮重置，预算是**轮**级的 |
| 历史自动 5 轮 / 单条 500 字 / `readHistory` ≤3 片 | `..\test\history_window_test.dart`、`tool_executor_test.dart` | 窗口钉死不随对话变长 |
| 工具调用链不被从中间截断 | `..\test\history_chunker_test.dart` | 片边界只落在完整轮次上 |
| 更早历史的摘要只生成一次 | `..\test\history_summary_test.dart` | 用"数调用次数"验证，不靠人看日志 |
| 风险拦截与模型行为解耦、删除措辞、一次提议只执行一次、锚点失败一个字不改 | `..\test\tool_write_test.dart`、`..\test\tool_delete_test.dart`、`..\test\agent_dialogs_test.dart` | 判据全在 App 侧，**故意**不依赖模型 |
| `askUser` ≤5（跨恢复）/ `requestTools` ≤6 / 批量 ≤10 / 轮数上限 15 | `..\test\agent_loop_test.dart`、`..\test\ask_flow_test.dart`、`tool_delete_test.dart` | 造个假模型就能测到上限，不用花额度 |

上表之外还有三类**只有真调一次才验得到**——即第四节"代价如实写明"里那三条
（协议报文形状、模型会不会主动调工具、真实 SSE 的分片方式）。真机测试删掉之后，
这三类**没有自动化覆盖**，只能在发版前靠人工走一遍。

顺带两样也只能真机验：**Key / 网络 / 代理到底通不通**；**生成参数**——思考模式默认开启，`max_tokens=20` 时 20 个 token 全被思考吃掉、正文返回空串（实测），所以生成类调用显式关掉了思考，而假模型永远不会有这个现象。这两样同样没有自动化覆盖。

**（如果将来再写真机测试）不要断言"模型的自然语言"**：只断言结构与入库（能解析、能入库、条数对）。**实测模型根本不守字数**——要 45~60 字的摘要，它稳定返回 116~160 字；摘要与标签的兜底因此必须在代码里（`..\lib\core\util\ai_limits.dart`）。

**成本预算类的两条不能当成断言**（措辞比实际严格）：

- "单批输入 ≤4000 字"是**设计预算、运行时不强制**：真实 prompt 还含每篇摘要（≤300 字）与"避开标题"清单，整段会超过 4000。测试守住的是**素材正文** ≤4000（`feed_window_test.dart`）。
- "`readChunk` 单次 ≤3 片"不准确：工具参数只有**单片** `index`，真实约束在**轮**那一级（`beginTurn` 之后累计 ≤3 片、≤1500 字）。

还有一批指标**只能上线后观察、测试测不出来**：工具 token 占比、确认层拒绝率、锚点校验失败率、自愈触发次数、卡片重复率、挂起未恢复的会话数。

## 六、测试陷阱（从测试文件注释里读到的）

下面每一条都出自测试文件里的注释，附行号，可直接去核对。

**1. 周期性测试数据会让"轮换"看起来没生效** —— `..\test\feed_window_test.dart`

> ⚠️ 造这种"位置可辨认"的数据时，**周期性是最容易踩的坑**，而且踩两次：
> · `'内容句子。' * 140`：周期 5，而 300 是 5 的倍数 → `body[0..400]` 与 `body[300..700]` **字面上完全相同**
> · `String.fromCharCode(0x4E00 + (i % 400))`：周期 400 < 700 → `body[650..700]` 那 50 个字**照样能在 `body[0..400]` 里找到**
> 两次都让"轮换看起来没生效"，而实现其实是对的。

结论：要造"位置可辨认"的正文，必须让每个下标对应一个独一无二的字（不取模）。

**2. 会话历史每轮长度必须落在 [300, 700]，且断言不许硬写片数** —— `..\test\tool_executor_test.dart`

> ⚠️ 每轮的长度要落在 **[300, 700]** 这个区间里，才会"一轮一片"：
> · 太短（< 300）→ 被合并成一片（那是切片器该做的，避免碎片）
> · 太长（> 700）→ 一轮被拆成两片
> 实测两版数据都栽在这里（先是 1 片、后是 6 片）。所以断言里**不硬写片数**，而是拿切片器的结果当基准。

**3. 假时间戳按"消息序号"递增会让两轮交错** —— `..\test\history_chunker_test.dart`

> ## ⚠️ 时间必须**整轮递增**，不能按消息条数递增
> 早先这里用同一个"消息序号"当秒数，于是第 2 轮的 user 落在 `00:00:02`、而第 1 轮的 assistant 落在 `00:00:05` —— 按时间排序后两轮**交错**在一起，`HistoryChunker` 的分组自然全乱。
> **那是测试数据不真实（真实对话的时间天然递增），不是实现的问题。**

**4. 配置锚点会跨用例、跨测试进程互相污染** —— `..\test\backup_test.dart`

> 1. **测试之间会互相污染**。配置锚点之一是「程序所在目录」，而在测试进程里 `Platform.resolvedExecutable` 指向 dart SDK 的 `bin\dart.exe`——那里的 `storage.json` 会**跨测试用例、跨 test 进程一直留着**。上个用例写的 workingDir 会被下个用例读到，表现为莫名其妙的断言失败（实际发生过）。
> 2. **绝不能污染开发者的真实配置**。跑测试时如果往 dart SDK 目录写了个指向临时目录的 `storage.json`，而某次又用那个 SDK 跑了 App，就会莫名其妙用错工作目录。

处置：每个用例 `setUp` / `tearDown` 都 `_clearAllConfigAnchors()` +
`DatabaseLocation.resetCacheForTesting()`，且 **tearDown 里先清配置再清目录**。

**23. 备份的"必需表清单"只能是结构表，不能收可重建的派生表** —— `..\lib\core\backup\backup_service.dart`

现象：早先把 `cards` 列进必需表清单，功能删掉后**每一个新备份都被自己判定为"不是有效的笔记数据库"**；`settings` 改名 `app_kv` 时清单没跟着改，同样把所有新备份挡在门外——`folders` → `notebooks` 那次已经踩过一回。

根因：清单把"结构表"与"派生 / 历史表"混在一起，而派生数据缺了应该**自动重建**，不是判定备份无效。

怎么避免：清单只认 `notes`、`app_kv`（或旧名 `settings`）、`notebooks`（或旧名 `folders`），**新旧名字都要接受**（老备份包里是旧名）；`note_chunks` 这类可重建的派生表**不许进清单**。这条目前只有代码保证、没有用例，值得补一条"缺 `note_chunks` 的备份仍判定有效"。

**24. Provider 顺序：测试里的树要和 `main.dart` 一致** —— `..\lib\main.dart`

现象：`Could not find the correct Provider<AiRepository>`（实测踩过）。

根因：`FeedRepository` 依赖 `AiRepository`，而 Provider 是**惰性解析**的——写在前面，第一次读取时就找不到。

怎么避免：搭测试用的 Provider 树时按 `main.dart` 的顺序（依赖在前）。这类"只在真机装配时才炸"的错误，如果 widget 测试自建了一棵顺序不同的树，会给出假绿灯。

**25. 布局类缺陷不会让测试失败（没有 overflow 报警），只能用尺寸断言抓** —— `..\test\feed_card_layout_test.dart`

现象：固定卡片高度让 1 行标题的卡片占满 2/3 屏、中间一大片空白（实测踩过）；改成自适应后 `Spacer` 是 flex，照样把 `Column` 撑到 `maxHeight`。

根因：这类问题既不溢出也不报错，`pump` 之后"渲染成功"什么都说明不了。

怎么避免：用 `tester.getRect` / `getSize` **量**出位置与尺寸再断言——那个文件头写着"是为了量出来的东西，不是猜出来的"。别拿"能渲染出来"当通过。

**26. 挂起（`pendingAction`）类缺陷的两个盯点** —— `..\lib\features\ai\domain\ai_chat_repository.dart`、`..\lib\features\ai\domain\agent_loop.dart`

现象 A：消息文本与挂起记录分开写，中间崩一次就留下"有挂起没提问文本"（用户看到空白卡片）或"有文本但挂起失效"（点了没反应）。

现象 B：`askUser` 的次数只在单次循环里计数 ⇒ 用户回答后是**新的一次 `run()`**，计数从 0 起，上限永远到不了，用户被反复问。

根因：挂起状态跨两处存储；"一问一答"在实现上是两次独立调用。

怎么避免：A 用**同一个事务**写，用例写完后**只从库里读**还原挂起（`..\test\ask_user_test.dart`）；恢复时要用**事件带回来的** `messages`（含本轮工具往来），用错的话用户答完没法接着跑（实测踩到）。B 把已问次数存进挂起记录、恢复时用 `asksSoFar` 带回，用例必须**跨恢复累计**（`..\test\ask_flow_test.dart`）——只测"一次 run 内问到第 3 次"会漏掉这个 bug。

**27. 常驻动画 + 重依赖树的页面，`pumpAndSettle` 永不收敛 ⇒ 宁可记为人工项** —— `..\lib\features\ai\ui\ai_page.dart`

现象：「AI 在等你回答」那条常驻提示条没有 widget 测试。

根因：`AiPage` 有常驻动画，`pumpAndSettle` 永远等不到"没有待处理帧"，测试会挂到超时。

怎么避免：这一条**明确记为人工复核项**——"宁可记为人工项，也不留一个会挂的测试"。真要自动化就用 `pump(固定时长)` 分步推进（见第 6 条），不要用 `pumpAndSettle`。

**28. 给"没要求的功能"写测试是白费——先确认需求存在** —— `..\lib\features\note\ui\inbox_page.dart`

现象：有人擅自加了"滚到底自动加载下一屏"，还为它写了 7 条测试证明"程序触发的滚动不会加载"。而"切后台回来卡片自己往后追加"的真正原因是**窗口重新布局也会产生滚动通知**，被误当成"用户滚到底"。最后那一层整块删掉，7 条测试全是白费。

根因：那个功能压根不该存在。测试只能证明"实现符合需求"，证明不了"需求正确"。

**29. 流式写库必须幂等，而"单事件假客户端"测不出来** —— `..\test\ask_flow_test.dart`（「流式分片续写」）

现象：有些回答里，同一句话按字数递增地重复上百遍（`已` / `已删除，` / `已删除，「我的轻笔记」…` 这种锯齿），一段几百字的回答变成几十 KB 的垃圾。只在"AI 提问 → 用户回答 → 接着跑"的回答里出现，所以看起来像"有时候"。

根因：`AgentText` 带的是**这一段该怎么显示**的累计文本，而写库时每写一次都**重新读一遍行内容**再 `before + '\n\n' + text`。第 k 个分片于是把前 k-1 个分片重写一遍 —— 平方级膨胀。单事件（一次 `fullText`）时只多出一份，看着像正常拼接。

怎么避免：续写起点在 `run()` 开始时读**一次**就定死，写入是「起点 + 累计文本」的**覆盖**（重复写同一个累计文本必须幂等）；用例必须让假模型**分片**（`FakeClient(stream: ...)`），并且用**精确相等**而不是 `contains` —— `contains` 会被"同一句话写两遍"骗过去（`ask_flow_test` 里原来那条就是 `contains`，所以这个 bug 一直在）。

**30. 同一个派生字段有多个写入方 ⇒ 口径必然分叉；上限只加在一处 ⇒ 另一条路能绕过去** —— `..\test\tool_write_test.dart`（「AI 写笔记受与编辑页同一套上限」「派生字段的口径与编辑页完全一致」）

现象：`notes.excerpt` 在编辑页那条路是"剥 Markdown + 200 字"，在 AI 那条路是"压空白 + 80 字"；`notes.wordCount` 一边是"中文按字 + 英文按词"，另一边是 `content.length`。于是**同一篇笔记，AI 写过和人改过，列表里的字数与预览不一样** —— 用户看到的是"这软件的数会变"。同族还有一条：编辑页在 100 KB 处拒绝保存，而 AI 的写入路径完全不看上限。

根因：一个字段有 N 个写入方，而实现被抄了 N 份（`note_repository.dart` 里那份私有副本的理由还写错了 —— 它说"core 层不该反向依赖 feature 层"，可 `text_utils.dart` 本来就在 `core/util/`，方向是对的）。

怎么避免：
- **派生字段只留一个纯函数入口**（这里是 `TextUtils.excerpt` / `TextUtils.wordCountOfMarkdown`），所有写入方都调它；抄一份私有的当"省事"，代价是两个数字慢慢分叉；
- **上限要长在写入路径上，而且每个写入方都要过**（`ToolExecutor._fitForSave`）。"编辑页拦住了"不等于"写不进去"；
- 用例要**横着比**：同内容分别经两条路写一遍，断言派生字段**相等**。只测一条路永远发现不了这种分叉。

怎么避免：写测试前先问"这条行为是谁提的需求"；用户已有的改动（`first` 参数、首次替换 / 下拉前向追加）**不要擅自改**。追加只能由下拉刷新触发，滚动不做任何事。

### 中断测试会留下进程锁住 `sqlite3.dll`

> **出处说明**：这一条**不是从测试注释里读到的**（在 32 份测试文件、`dart_test.yaml`、
> `..\tool\`（现在只剩 `inspect_db.dart`）与 `..\docs\` 里搜 `sqlite3.dll` 均零命中），
> 而是**开发过程中实测遇到**的。
> 收录它是因为这类失败**极难自查**：报错信息把人引向完全错误的方向。

现象：测试被中断过几次（超时、手动终止）之后，后续 `flutter test` 会**直接失败**：

```
Flutter failed to delete file at "...\build\native_assets\windows\sqlite3.dll".
The flutter tool cannot access the file or directory.
Please ensure that the SDK and/or project is installed in a location that has
read/write permissions for the current user.
```

这段话会让人去查目录权限 —— **但那不是原因**。真实原因是残留的
`dart.exe` / `flutter_tester.exe` 进程仍然持有那个 DLL。

处理：先杀掉残留进程再跑。

```powershell
Get-Process -Name flutter_tester,dart -ErrorAction SilentlyContinue |
  Stop-Process -Force
```

**这是"中断测试"的真实代价**：它不只丢一次结果，还会让**接下来几次**跑测全部失败，
而且失败信息指向错误方向 —— 日常按约定不跑全量测试时，更容易被误判成"环境坏了"。

与上面第 5 条（`backup_test.dart` 的 Windows 文件句柄未释放）是同一类问题，
但影响面不同：那条只影响一个用例的临时目录，这条会让**整个测试进程起不来**。

### 一条出自实现记录、不是测试注释的坑

**`unawaited` 的后台任务必须吞异常** —— `..\lib\features\note\data\feed_repository.dart`

现象：`warmup_test` 的 `tearDown` 关掉数据库之后，后台补池的任务才走到查库那一步，抛出 `Bad state: Can't re-open a database after closing it`——而这个异常被算到**上一个测试**头上，看起来像一次完全无关的失败。

根因：`refill` / `_reserveTail` 这类调用在 `unawaited` 里，异常没人接，就成了未捕获的异步错误；测试进程会把它归给"当时正在跑的那个测试"。

怎么避免：fire-and-forget 的任务自己 `catchError` 吞掉并打一行日志（补池是尽力而为，真失败了下拉刷新会按需生成）。这条已经写进代码注释，测试侧看不出痕迹，所以单独记在这里。

### 「新建的笔记库没进来源」那次缺陷：这类缺陷要盯住哪些点

**现象**：启动 App → 在「笔记库」新建一个库 → 切回「轻笔记」→ **新库不在来源里**；重启 App 又会自己好。

**根因**（两个 bug 叠在一起）：

- 来源当时存的是**一份包含集快照 + 一段对账**，而对账只在页面 `initState` 跑一次；三个 tab 用 `IndexedStack` 保活（切标签不重建页面）→ 对账再也不发生。**"重启就好"正是它的指纹。**
- 来源页的「保存」**无条件**把用户标记成"改过"——用户打开看一眼、什么都没改、点保存，需求③（新库默认勾选）就**永久失效**，而界面上没有任何迹象。

**修法**：来源的"真值"从「存下来的包含集快照 + 对账」改成「**当前全部笔记库 − 用户明确排除的**」，每次现算；解析收进仓储层，调用方不能再塞一份来源进去（`..\lib\features\note\data\feed_repository.dart`）。

下面这份清单比这一个 bug 本身更值得留着——**凡是"把当前状态存成快照、之后再对账"的设计，都要按这几条盯**：

**① 缓存 / 快照类缺陷，必须"不重启"验**

- [ ] 新建库 → **切回**目标页 → 立刻生效（页面被 `IndexedStack` 保活，`initState` 不会再跑）
- [ ] 触发路径不止一条：切 tab、下拉刷新、后台补池，都要走同一次现算

**② "读"与"写"分开验**

- [ ] 全新安装：结果 = 全选，且**一个 key 都不写**（默认态是算出来的，不是存出来的）
- [ ] 打开来源页、**什么都不改**、直接保存 → **零写入**（代码在 `..\lib\features\note\ui\feed_source_page.dart` 用 `_sameAs` 挡掉了；这个页面没有 widget 测试，这条目前只有代码保证）
- [ ] 打开页面时**刚建的库是勾上的**（展示的是有效来源，不是过期快照）
- [ ] `writeSource` 存的是"没勾上的"（排除集），不是"勾上的"

**③ 三条需求必须能"同时"成立**

- [ ] 取消 X → **重启后仍不含 X** → 重新勾上能恢复
- [ ] 在"取消过 X"的状态下新建 Y → **Y 自动勾选、X 仍不含**
- [ ] 全部取消（笔记库 +「我的轻笔记」）→ 仍显示引导，**不被"自动补充"覆盖**
- [ ] 「恢复默认」→ 回到默认态，且已在默认态时该入口不可用

**④ 脏数据与老数据**

- [ ] 删掉一个笔记库 → 来源里**不残留**它的 id
- [ ] 老 key（`feed_source_notebooks`）**不被读取**；新 key 必须换名字——老的是包含集，当排除集读会把来源整个清空
- [ ] 排除集的 JSON 损坏 → 当成"没排除任何"，不是崩，更不是全排除

**⑤ 结构性盯点**

- [ ] 只要设计里出现"把当前状态存成快照、之后再对账"，就问一句：**没有触发对账的路径怎么办**（保活页面、后台回调、别的入口）
- [ ] 任何"解析"都不要留在调用方——收进边界层，让"塞进过期快照"在结构上不可能
- [ ] 「保存」必须能区分"用户真的改了"和"用户只是点了一下"

这条缺陷的回归网是 `..\test\feed_source_test.dart`（16 个用例，逐条说明在第五节），它守的是**仓储层**：默认态、排除集语义、需求②③同时成立、老 key、脏 JSON、删库残留、恢复默认都有用例。**页面上那两条（"什么都不改直接保存"、"打开时刚建的库是勾上的"）以及 ⑤ 的结构性盯点目前只有代码保证、没有用例**——来源页没有 widget 测试。
