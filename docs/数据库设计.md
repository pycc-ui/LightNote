# 数据库设计

这份文档讲数据库：表、字段、索引、迁移。内容以真实代码为准：`lib/core/db/tables.dart`（表定义）、
`lib/core/db/app_database.dart`（`schemaVersion` / 迁移链 / 索引）、`lib/core/db/database_location.dart`
（`kCurrentSchemaVersion`）、`lib/core/db/app_database.g.dart`（生成的列名 / 类型 / 默认值 / 可空性）。
**改表要先改代码和本文，两边必须一致。**

相关：[技术栈设计](技术栈设计.md)（为什么是 SQLite + Drift）、[测试设计](测试设计.md)（迁移测试怎么跑）。

## 0. 库文件与总览

- **文件名 `lightnote.sqlite`**（`kDatabaseFileName`）。发布正式版之后就不能再改名——改名等于让所有老用户的库
  "凭空消失"（App 会在新路径建一个空库）。备份包里的条目路径 `kBackupDbEntryPath`（`data/lightnote.sqlite`）
  必须同步。
- **位置**由 `DatabaseLocation` 逐档真实试写后决定：环境变量 `LIGHTNOTE_DB_DIR` → 用户配置的工作目录 →
  App 私有目录。而"私有目录"自己也是逐档试出来的：App 数据目录 → 文档目录 → 用户主目录 → 程序所在目录
  （最后这档落在 `build\` 下面，会显式警告"删 build 就没了"）。"数据库位置"这个配置存在数据库之外的
  `storage.json`（先有鸡还是先有蛋）。
- **当前 `schemaVersion = 11`**（见第 10 节）。

**9 张表**（成对的表在下面合并成一行，如 `ai_conversations` / `ai_messages`；索引统一在
`AppDatabase._createIndexes()` 里建）：

| 表 | 行类 | 作用 |
|---|---|---|
| `notebooks` | `Notebook` | 笔记库（平铺，无层级） |
| `notes` | `Note` | 笔记主表 |
| `ai_note_summaries` | `AiNoteSummary` | 每篇笔记的 AI 摘要（卡片流素材，一篇一行） |
| `ai_conversations` / `ai_messages` | `AiConversation` / `AiMessage` | AI 会话与消息 |
| `ai_calls` | `AiCall` | AI 调用审计 |
| `app_kv` | `AppKvData` | key-value 轻量配置（v9 从 `settings` 改名） |
| `feed_reserve` | `FeedReserveData` | 轻笔记的跨启动预留卡片 |
| `note_chunks` | `NoteChunkRow` | 笔记的切片（只存偏移，不存正文；v10 新增） |

> 行类名不是随手写的：`AppKv` 会和表类重名，Drift 自动加了 `Data` 后缀；`NoteChunks` 撞上了领域层的
> `NoteChunk`，所以表上显式写了 `@DataClassName('NoteChunkRow')`（见第 9 节）。

### 几条贯穿始终的设计决定

1. **主键一律用 UUID 文本**，不用自增整数。将来做多设备同步时不会冲突。
2. **逻辑删除**用 `deletedAt` 时间戳而非布尔——可以做回收站排序，也能给增量同步当游标。
3. **AI 产物与原文分离**：摘要等 AI 产物（`ai_note_summaries`）不进笔记正文，单独表存，可整体丢弃重算。
   上面这 9 张表之外，历史上还有 8 张已删除的表（见第 3 节）。
4. **时间统一 UTC 存储**，`DateTimeColumn` 由 Drift 自动转成 Unix 时间戳（SQL 里看到的是 `INTEGER`）。
5. **布尔列在 DDL 里是 `INTEGER NOT NULL CHECK (col IN (0, 1))`**，不是 `BOOLEAN`。
6. **TEXT 列一律不带长度约束（有意为之）**：所有文本字段都是裸 `text()`，`title` / `content` / `name` /
   `summary` 全都没有上限。不在 DDL 上写 `CHECK(length(...))` 的原因：

   - SQLite 的 CHECK 失败只能抛异常，给不出"这篇太大了，请拆成多篇"这种能照着做的提示。上限的真实目的
     就是让写的人知道怎么办，所以它必须长在写入路径上（`AiLimits` + `TextUtils`，两个写入入口都会过一遍）；
   - 加约束要重建 9 张表（高风险迁移），而想要的边界全都能在代码里表达；
   - 导入备份包绕过全部写入路径。约束会把"能打开的旧库"变成"打不开的旧库"。

   代价：绕过写入路径（导入、迁移、将来新增的写入方）就没有上限——所以新增写入方时请调
   `TextUtils.excerpt` / `TextUtils.wordCountOfMarkdown` / `AiLimits`，不要直接 `upsertNote`。
   （各字段上限的完整清单见《软件理念设计》第 3 节。）

## 1. notebooks（笔记库）

平铺，没有层级。v3 从 `folders`（目录）改名而来，同时删掉了 `parent_id`。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | TEXT | PK | UUID |
| name | TEXT | NOT NULL | 展示名 |
| sort_order | INT | NOT NULL, default 0 | 列表排序 |
| created_at | TIMESTAMP | NOT NULL | |
| updated_at | TIMESTAMP | NOT NULL | |
| deleted_at | TIMESTAMP | NULL | 逻辑删除 |

索引：`idx_notebooks_order` on `(sort_order, name)`

> **为什么不保留层级**：当初选 SQLite 而不是文件系统，本来就是为了不模仿目录树；再长出子目录等于把文件系统的
> 复杂性搬回来。去掉层级的附带好处是不再需要"删父目录时子目录上浮"这类最容易出错的边界处理。

**关键行为**：删除笔记库不删笔记。`softDeleteNotebook` 在一个事务里把库内笔记 `notebook_id → NULL` 且
`is_inbox → true`（回到「我的轻笔记」），然后把笔记库本身逻辑删除。如果直接级联删笔记，用户整理笔记库时会
一次丢掉一批内容——那是数据丢失事故。

## 2. notes（笔记主表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | TEXT | PK | UUID |
| notebook_id | TEXT | NULL, FK→notebooks.id ON DELETE SET NULL | 为空表示「我的轻笔记」（未归档） |
| title | TEXT | NOT NULL, default '' | 允许空，列表显示"无标题" |
| content | TEXT | NOT NULL, default '' | Markdown 原文 |
| excerpt | TEXT | NOT NULL, default '' | 前 200 字纯文本（`_excerpt(max: 200)`，超长加 `…`），列表页预览用，避免读全文 |
| source | TEXT | NOT NULL, default 'local' | 数据来源。列注释预留 `local` / `import` / `share` / `ai`，但目前只有默认值 `local` 会被真正写入（没有别的写入方） |
| is_inbox | BOOL | NOT NULL, default false | true=未归档（在「我的轻笔记」），false=已归档到某笔记库 |
| pinned | BOOL | NOT NULL, default false | 置顶 |
| word_count | INT | NOT NULL, default 0 | 写入时算好：中文按字 + 英文按词（`_wordCount`） |
| last_ai_at | TIMESTAMP | NULL | 上次 AI 整理成功的时间。写入方只剩 `streamOrganize()` 里的 `markNoteAiDone()`，而 `streamOrganize` 自身零调用方（源码注释里写明属于死代码）；全项目唯一读它的地方是 `tool_executor` 写回笔记时原样带回，没有任何界面展示它 |
| created_at | TIMESTAMP | NOT NULL | |
| updated_at | TIMESTAMP | NOT NULL | 每次写入必须更新 |
| deleted_at | TIMESTAMP | NULL | 逻辑删除 |

> 「我的轻笔记」与「笔记库」是同一张表的两种视图，靠 `is_inbox` 与 `notebook_id` 区分，不是两张表。
> 这样归档只是改两个字段，不用搬数据。`moveNoteToNotebook(noteId, null)` 会把 `is_inbox` 一并置回 true。

**已移除的字段**：`reading_progress` / `reading_seconds`。沉浸阅读页下线后它们没有写入方，留着只会误导。

索引（4 条）：

- `idx_notes_updated` on `(updated_at DESC)` —— 默认列表排序
- `idx_notes_inbox` on `(is_inbox, updated_at DESC)` —— 轻笔记页主力索引
- `idx_notes_notebook` on `(notebook_id, updated_at DESC)` —— 笔记库详情页
- `idx_notes_deleted` on `(deleted_at)` —— 过滤已删除

## 3. 已删除的 8 张表

这些表在真实代码里已经没有表定义、也没有读写方，只在老库里靠迁移清理。建表语句只存在于
`test/migration_test.dart`（手工造老库用，否则 `DROP TABLE` 在测试里是空转，"删掉了"的断言没有意义）。

| 表 | 什么时候删的 | 为什么是死表 |
|---|---|---|
| `cards` | v6 | 记忆卡片（SM-2 复习）整体移除，「轻笔记」AI 卡片流取代了它 |
| `card_decks` | v6 | 同上（卡组） |
| `reviews` | v6 | 同上（复习流水） |
| `note_summaries` | v7 | 「AI 整理要点」的落库表：只写不读（读侧 `watchLatestSummary` 零调用方） |
| `note_feed_state` | v8 | 卡片流"复习已有笔记"时代的调度状态；`AppDatabase` / `FeedRepository` 里的读写方法早已删干净 |
| `note_ai_tags` | v8 | 每篇笔记的 AI 标签：读侧链路（`NoteAiAssetRepository.get()` → `FeedRepository.tagsOf()`）零调用方 |
| `tags` | v9 | 用户手动打的笔记标签（主表） |
| `note_tags` | v9 | 手动标签的连接表，复合主键 `(note_id, tag_id)`，两个外键都 `ON DELETE CASCADE` |

**历史字段（留档，便于读老备份）**

`tags`：`id` TEXT PK / `name` TEXT NOT NULL / `normalized_name` TEXT NOT NULL UNIQUE / `color_value` INT NULL /
`usage_count` INT NOT NULL DEFAULT 0 / `created_at` TIMESTAMP NOT NULL。

`note_feed_state`：`note_id` TEXT PK FK→notes(id) CASCADE / `due_at` TIMESTAMP / `interval_days` INT DEFAULT 0 /
`ease` REAL DEFAULT 2.5 / `repetitions` INT DEFAULT 0 / `lapses` INT DEFAULT 0 / `shown_count` INT DEFAULT 0 /
`opened_count` INT DEFAULT 0 / `last_shown_at` TIMESTAMP NULL / `last_opened_at` TIMESTAMP NULL /
`starred` BOOL DEFAULT false / `created_at` / `updated_at`。它当年还有两条索引，也已在 v8 一起删掉：
`idx_feed_due` on `(due_at)`、`idx_feed_starred` on `(starred, due_at)`——这两条每次启动都在建，
是删表时最容易漏掉的一半。

> **为什么删手动标签**：它是个闭环——写入只有编辑页那个「标签」弹窗，读取只有那个弹窗自己，外加 Markdown
> 导出里一行 `> 标签：`。产品明确说"导出 Markdown 时多一行 `> 标签：` 这完全不需要"，于是整条链路
> （含 `usage_count` 那个只服务 `watchTags` 的 ORDER BY，而 `watchTags` 零调用方的反范式计数器）在 v9
> 迁移里删掉。两张表的表定义、`@DriftDatabase` 注册项、`AppDatabase` 的 `ensureTag` / `attachTag` /
> `detachTag` / `watchTags` / `tagsOfNote`、`NoteRepository` 的对应包装、编辑页工具栏的第 7 个按钮与它的
> 弹窗、Markdown 导出的 `tags` 具名参数、`BackupStats.tags` 全部一并移除。连带后续是整个 Markdown 导出
> 功能也被删掉了（`MarkdownExportService` 及 `renderSingle` / `exportAll` 全部移除，编辑页菜单不再有
> 「导出 Markdown」）；唯一留下的是「复制全文」——它只把标题 + 正文当纯文本放进剪贴板，组装逻辑在
> `TextUtils.noteCopyText`。

> **卡片级标签与这些表无关，仍然保留**：卡片左下角那个标签来自卡片自己的 `FeedDraft.tag`（见 `displayTag`），
> 存进 `feed_reserve.tags` 字符串列（列名是历史遗留：早先存的是 JSON 数组，现在只放一个标签）；生成时由
> `AiPrompts.parseFeedCards` → `sanitizeTag` 规整（在 `core/util/ai_limits.dart`，与 `normalizeTag` 同处）。

> **别把已删除的 `note_summaries` 和仍在用的 `ai_note_summaries` 搞混**——两者只差一个 `ai`，
> 却是完全不同的东西（见下一节）。同理，已删除的 `note_ai_tags` 与已删除的 `tags` / `note_tags` 也是两回事：
> 后者是用户手动打的笔记标签（有 `usage_count`、要跨笔记聚合），前者是 AI 自动打的、且只写不读。

## 4. ai_note_summaries（卡片流素材）

一篇笔记一行，新结果覆盖旧的——与已删除的 `note_summaries` 语义正好相反（那个是"一次整理一条、
不覆盖历史"的展示型记录）。它只服务于喂给 AI 的素材，用户看不到；卡片流之所以便宜又快，就是因为发的是摘要
而不是全文。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| note_id | TEXT | PK, FK→notes.id ON DELETE CASCADE | 一篇笔记一行 |
| summary | TEXT | NOT NULL | 摘要正文，硬上限 220 字，写入前已截断 |
| model | TEXT | NOT NULL, default '' | 生成时用的模型 |
| source_bytes | INT | NOT NULL, default 0 | 生成时笔记正文的 UTF-8 字节数，用来判断摘要是否过期 |
| created_at | TIMESTAMP | NOT NULL | |
| updated_at | TIMESTAMP | NOT NULL | |

索引：`idx_ai_summaries_updated` on `ai_note_summaries(updated_at DESC)`

> 表名在 v9 迁移里从 `note_ai_summaries` 改成 `ai_note_summaries`（`ALTER TABLE ... RENAME TO ...`），
> 只是为了跟同族的 `ai_calls` / `ai_conversations` 对齐命名——内容是同一份，一个字都没动。行类名跟着变成
> `AiNoteSummary`。同一批（v4）还建过一张 `note_ai_tags`（每篇笔记的 AI 标签），已在 v8 删除。

> **为什么用字节数而不是 `updated_at` 判断过期**：`updated_at` 只要写一次就变，用户改个错别字也会让摘要
> 作废，等于每次编辑都白烧一次 token。字节数配合 20% 阈值（`NoteAiAssetRepository.staleRatio = 0.20`）
> 就实现了防抖。

## 6. ai_conversations / ai_messages

### ai_conversations

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| id | TEXT | PK | |
| workspace_scope | TEXT | NOT NULL, default '' | 工作区（AI 能看到哪些笔记），JSON。见下 |
| thinking_effort | TEXT | NOT NULL, default 'medium' | `low` / `medium` / `high` |
| title | TEXT | NOT NULL, default '' | |
| created_at | TIMESTAMP | NOT NULL | |
| updated_at | TIMESTAMP | NOT NULL | |

`workspace_scope` 是 v11 引入的，取代了原来的 `workspace_notebook_id`（单个笔记库 id）。
形状由 `AgentWorkspace.toJson` 决定：

```json
{ "mode": "none" | "all" | "pick",
  "notebookIds": ["…"],        // 仅 pick 模式才写这个键
  "includeUnfiled": false }    // 仅 pick 模式才写这个键
```

- `none` —— 不选择，AI 看不到任何笔记（只能靠用户显式附上的文件）
- `all`  —— 全部笔记库 + 我的轻笔记（新会话的默认值，见下）
- `pick` —— 指定的若干笔记库，`includeUnfiled` 另外决定要不要带上轻笔记

**读取规则是三分支，别把"空串"和"坏数据"混为一谈**（`AgentWorkspace.parse`）：

| 列里的值 | 读成 | 为什么 |
|---|---|---|
| `NULL`（连会话记录都没有） | `none` | 说不清是什么情况 → 保守，不要突然放宽 |
| 空串（v11 之前的老会话） | `all`（= `AgentWorkspace.initial`） | 空串表达的是"用户没做过这个选择"，必须和新会话的默认一致；读成 `none` 会让老会话与新会话两套默认 |
| 坏 JSON / 认不出的 mode | `none` | 读不懂就按最保守的算 |

用户显式选「不选择」时存的是 `{"mode":"none"}`，与空串分得清——所以"空串读成 all"不会把用户的选择改掉。

> 这个范围同时是 AI 工具的范围：`searchNotes` / `listNotes` 会被它限制。否则"选了库 A"却还能搜到库 B，
> 工作区就只是个标签。列上没有外键（`notebookIds` 是 JSON 里的一串 id，SQLite 管不了）。老库升级后，
> 那一列 `workspace_notebook_id` 会留在表里但不被 Drift 读取——v11 用的是 `ALTER TABLE ADD COLUMN`，
> 不重建表，也不删旧列（无害）。

## 7. app_kv（key-value）

v9 从 `settings` 改名而来。原先那个名字不准确：里面 10 个 key 有 6 个根本不是"设置"（`search_history`、
`feed_source_excluded`、`feed_include_unfiled`、`ai_privacy_accepted` 等等）。改名照 `folders` →
`notebooks` 的先例做：改类名（Drift 由类名推导表名）+ 迁移里 `ALTER TABLE settings RENAME TO app_kv`。
漏掉那条 RENAME，老库升级就会丢掉全部配置。

| 字段 | 类型 | 约束 |
|---|---|---|
| key | TEXT | PK |
| value | TEXT | NOT NULL |

目前代码里会读写的 key：

| key | 内容 |
|---|---|
| `search_history` | 搜索历史，JSON 数组（`PreferencesService`） |
| `theme_mode` | 主题模式，缺省 `system` |
| `editor_font_scale` | 编辑区字号倍数 |
| `seeded_<key>` | 「首次初始化」标记 |
| `ai_privacy_accepted` | 已废弃（v11 后不再读写）：授权确认机制已整体移除。老库里可能残留这个 key，无害 |
| `ai_history_summary_<conversationId>` | 会话历史摘要缓存 |
| `feed_source_excluded` | 卡片流来源，见下 |
| `feed_include_unfiled` | 卡片流来源，见下 |

**刻意不引入 `shared_preferences`**：少一个依赖，且这些设置能和笔记一起进同一个备份包（`app_kv` 是备份
导入校验的必需表之一）。

### 卡片流的来源配置也在这里

| key | 值 | 说明 |
|---|---|---|
| `feed_source_excluded` | JSON 数组 | 用户明确取消勾选的笔记库 id。不存在或为空 = 全选 |
| `feed_include_unfiled` | `'true'` / `'false'` | 是否包含「我的轻笔记」。不存在 = `true`（读取判据是 `!= 'false'`） |

**只存"用户不要什么"，不存"用户要什么"**——这一点是刻意的，也是全部规则的来源：

- 默认（两个 key 都不存在）→ 全选所有笔记库 + 我的轻笔记，而且不需要写任何东西
- 用户取消勾选某个库 → 它进排除集，不再参与（以用户的为准）
- 新建的笔记库不在排除集里 → 自动被勾选（不需要任何"对账"逻辑）

> **别把这两个 key 换回老名字**。早先用的是包含集（`feed_source_notebooks` + `feed_source_initialized` +
> `feed_source_customized`），那套的问题是："一个 id 不在集合里"分不清"从没见过"和"用户取消的"，于是不得不
> 加 `customized` 标记来区分，再靠一段"把缺的库补回来"的对账实现"新库自动加入"。而那段对账只在页面
> `initState` 跑一次，三个 tab 又是 `IndexedStack` 保活的（切标签不重建页面）→ 用户在笔记库页新建的库不进
> 来源，要重启 App 才对。改成排除集之后这两个毛病一起消失。新 key 必须换名字：老的"包含集"一旦被当"排除集"读，
> 语义正好反过来，会把用户的来源整个清空。

## 8. feed_reserve（跨启动预留的卡片）

轻笔记卡片流要求"每次打开都秒出"，不能等一次 AI 生成（要几秒）。库里没有预留（第一次装、或上次没留成）时，
先并发生成一屏 3 张上屏，剩下的（补池 + 给下次留预留）丢后台。给下次预留的做法是：后台**单独生成**最多
6 张存进这张表（不从内存池搬，所以不会掏空当前池子），下次先取表里的（秒出），取出即清空，再后台生成新的
一批写回来。

（相关常量在 `feed_repository.dart` 顶部：`kFeedFirstScreenCount = 3` / `kFeedPullSize = 2` /
`kGenParallelism = 4` / `kFeedReserveSize = 6` / `kFeedPoolTarget = 8`。）

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| id | TEXT | PK | UUID，写入时现生成 |
| title | TEXT | NOT NULL | 卡片标题 |
| body | TEXT | NOT NULL | 完整正文（Markdown） |
| tags | TEXT | NOT NULL, default '[]' | 标签 JSON 数组字符串（卡片自己的标签，与已删除的手动标签无关） |
| position | INT | NOT NULL | 取出顺序，0 最先展示 |
| created_at | TIMESTAMP | NOT NULL | |

无显式索引（表里就是一小批——写入方传的是池子尾部的 6 张，且总是整表取 / 整表替换，不需要索引）。

> **取出即清**："取全部 + 删全部"在同一个事务里，否则两个并发取用可能都拿到同一批，同一张卡片被展示两次。
> **写入即替换**，不追加——累积起来会让下次打开看到一堆旧内容。

> **这张表不影响列表是替换还是追加**：它只决定"进来时先拿哪 6 张"。列表行为在 UI 层
> （`InboxPage._loadBatch`）：首次进入是替换，下拉刷新是前向追加。

> **为什么用表而不是 `app_kv` 里的 JSON**：这些是真正的卡片内容，该有自己的表——能单独查询 / 清理，
> 不跟配置混在一起，结构也显式（标题、正文、标签各一列）。

## 9. note_chunks（笔记切片，v10 新增）

把正文按标题层次切成一片片"原文区间"。搜索要返回"命中哪一片"、AI 的 `readChunk(noteId, index)` 要稳定的片
索引、搜索结果要能跳转到原文那一段——这三件事都要求片与正文的映射预先算好并落库。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| note_id | TEXT | FK→notes.id ON DELETE CASCADE | 复合主键之一 |
| idx | INT | NOT NULL | 复合主键之一。顺序号，0 起。AI 的 `readChunk` 用的就是它 |
| heading | TEXT | NOT NULL, default '' | 标题路径，如 `工作 / 项目A / 风险`（无标题为空串） |
| level | INT | NOT NULL, default 0 | 来自几级标题（1~6；0 = 不在任何标题下） |
| start_offset | INT | NOT NULL | 在 `notes.content` 上的起点（含） |
| end_offset | INT | NOT NULL | 终点（不含）。左闭右开 |
| char_count | INT | NOT NULL | `end - start`（冗余一份便于排序统计） |
| content_hash | INT | NOT NULL | 这一片正文的 hash，自愈用 |
| last_used_at | TIMESTAMP | NULL | 卡片流上次用掉这片的时间（null = 从没用过） |
| next_window_start | INT | NOT NULL, default 0 | 卡片流下次开窗口的起点（片内相对偏移，窗口轮换） |
| created_at | TIMESTAMP | NOT NULL | |

**主键 `(note_id, idx)`**；索引 `idx_chunks_used` on `(last_used_at)`。

### 这些片是怎么切出来的（`NoteChunker`）

切法是纯函数：`NoteChunker.chunk(content)` 输入正文、输出片列表，不碰数据库
（`lib/features/note/domain/note_chunker.dart`）。落库、搜索定位、卡片流取素材三处用的是同一个函数，
同输入同输出——所以搜索结果里的 `chunkIndex` 与阅读态渲染出的片号必然对得上（阅读态因此不用查库，
把切好的片按正文缓存起来即可）。

**阈值**（长度都是 `String.length`，即 UTF-16 code unit；中文一字 = 1，emoji 一符 = 2）：

| 常量 | 值 | 性质 |
|---|---|---|
| `NoteChunker.cap` | 700 | 硬上限：除"不可拆散单元"外，任何一片都不超过它 |
| `NoteChunker.floor` | 300 | 期望值，不参与逻辑（合并是"填到上限为止"，见下） |
| `NoteChunker.shortNoteLimit` | 400 | `length <= 400` 且整篇没有任何标题 → 整篇一片 |
| `NoteChunker.atomicCeiling` | 1500 | 不可拆散单元的硬顶，超过就按行拆 |
| `FeedWindow.chars` | 400 | 卡片流一份素材的窗口长度（与 `shortNoteLimit` 数值相同，但不是同一件事） |

> **为什么 700 是硬约束**：卡片流的单批预算 `FeedWindow.batchBudget = 4000` 是拿 `kGenParallelism = 4`
> × 400 = 1600 算出来的，它默认片不会失控。片一旦能远超 700，这个估算连同提示词长度、token 成本、
> 一次请求装不装得下就一起崩。上限是消费侧预算的基础。

**切分顺序**（严格按这个顺序，`chunk()` 就是照这个流程写的）：

1. **空正文**（`isEmpty` 或整篇只有空白）→ 返回空列表，调用方据此跳过这篇笔记；
2. **短笔记兜底**：`length <= 400` 且整篇没有标题行 → 整篇一片（首尾空白仍不进片）；
3. **按标题层次切**：`#`~`######` 行把正文切成"节"（第一个标题之前的内容也算一节，标题路径为空）；
4. 节 > 700 → 用它内部更深一级的标题继续切，递归；标题用尽（到 6 级）还超 → 下一步；
5. **按段落切成"原子单元"**：连续同类行之间的空行不切断这一组（列表项之间空一行仍是同一个列表，
   表格写法里也常有空行，切断了就散了）；
6. 单元还超 700：

   - 不可拆散单元（围栏代码块 / 连续表格行 / 连续引用行 / 连续列表项）不拆，允许超 700；但超过 1500
     就得按行切；
   - 其余 → 句子（`。！？!?…`）→ 子句（`，；,;：:`）→ 字符硬切；标点留在前一片末尾，读起来还是原句；

7. **小片合并**（见下）→ 填 `index` / `heading` / `level` / `contentHash`。

**顺序不能换**：先标题、只在标题用尽时才动段落/句子——这样每一片天然落在"一个话题"里，而且带上标题路径当
上下文。旧版累积到 400 字就切，片不知道自己来自哪一节的标题，AI 拿到一段原文却没有任何上下文；超长段落又按
句子平均劈，劈出来的片常横跨两个话题。

**标题路径是完整路径**（`工作 / 项目A / 风险`），不是本节标题：维护一个标题栈，每遇到一个标题先把它这一级及
更深的残留清空再放自己（`# A` → `## B` → `# C` 之后，C 的路径就是 `C`，不是 `A / B / C`）；层级可以跳
（`#` 直接到 `###`），只把非空的拼起来。标题行识别：缩进最多 3 个空格（tab 缩进的 `#` 不算标题），
`#` 后必须跟空格或 tab，1~6 级。

**偏移基于原始 `content`，不归一化**：不把 CRLF 折成 LF、也不 trim 之后再算下标，
`chunk(c)[i].textOf(c) == c.substring(start, end)` 逐字成立。代价是片与片之间允许留空隙（首尾空白、分隔空行
不进任何片），但任何非空白字符都必定落在某一片里。首尾空白统一由一个 `_trim` 收边界——切分有四五条路径，
各自记得 trim 迟早漏一条。

**节的起点含标题行**：用的是 `s.start`（`#` 的位置），不是"标题之后的正文"。标题行的文字本身就是内容：
`# AA的正文` 这类笔记每节只有标题行有字，从标题之后开始会让每节都变成空片、整篇内容一片不剩；而且"标题与
它下面的正文在同一片里"本来就是要的行为——读片的人得看到这片讲的是哪一节。

### 小片合并：填到上限为止，且不跨标题边界

```
cur = 空
for 每一片 p（按原顺序）:
    if cur 为空:                                                   cur = p
    elif cur.heading == p.heading && cur.level == p.level
         && cur.len + p.len <= 700:                                cur += p
    else:                                                          定稿 cur；cur = p
定稿最后一个 cur
```

两条规则缺一不可，理由不同：

- **① 填到上限为止，不是"填到下限就停"。** 设计里那个 1400 字 → `600 / 600 / 200` 的例子说的就是这条：
  `200 + 200 + 200 = 600`，第 4 个会到 800 > 700 所以停。早先写成"`cur` 还没到 300 才并"，会在 400 就停、
  得到 `400 / 400 / …`，与例子不符。`floor = 300` 因此完全不参与逻辑，它只表达"不该切出一堆碎片"这个期望
  （单测据此断言"除尾片外不低于下限"）。尾片可以远小于 300，这是接受的。
- **② 不跨标题边界。** `heading` 是对"这片讲的是什么"的承诺；把「无标题的前言」和「`#` 后面的标题」并成
  一片、`heading` 却只写其中一个，等于对另一半撒谎。宁可多一片，也不给假路径。

合并只能向后、不打乱片序，结果是"所有片 ≤ 上限"。

> **"不可拆散"说的是不拆，不是不合并。** 不可拆散单元自己成片后，只要与邻片同标题且合起来 ≤ 700，
> 仍会被合并（`protected` 只是把它标记成"整块"，合并时取或）。真正被保证的只有"不会被从中间切开"。
> 所以 1500 这个硬顶很重要：它不是拍脑袋定的，`readChunk`（AI 读片）的单次预算就是 1500 字——一片超过
> 1500，AI 根本读不进来，那它作为"片"就没意义了。宁可拆散，也不能切出一片没人能读的东西。

> **长度精度**：单测都按 `<= cap` 断言，700 是硬约束；只有"字符硬切"那条路径为了不把切点落在字符/单词中间，
> 会往后找最近的空白边界，因此偶尔会略微越过 700（测试里造素材长度时因此留了 `cap + 1` 的余量）。

### 只存偏移，不存正文

存正文等于把全部笔记文本再存一份（库里文本量翻倍）。只存偏移的话，读片 = 用 `[start, end)` 从
`notes.content` 现取，永远和正文一致，不存在"片正文过期"这种状态。

代价是正文改了偏移就错了——但错的是位置不是内容，而且能被检出：读片时比对 `content_hash`，不符就当场重切
一次写回（见下）。

### 为什么要落库

切片本身不含新增信息，最早的做法是"现切不存"。改成落库是因为上面那三个需求只有持久化能满足。代价是必须维护
重切链路，这一条是明确认下的。`NoteChunkRepository` 里三条路径：

| 场景 | 做什么 | 成本 |
|---|---|---|
| 笔记保存后（`onNoteSaved`，`saveContent` 是唯一漏斗） | 只在"还没切过"或"长度变化超过 20%"（`staleRatio = 0.20`）时重切 | 一次切片 |
| 读片时（`chunksFor`） | 校验 `content_hash`，不符才重切（自愈） | 一次 hash |
| 后台补（`backfillMissing`，一次最多 50 篇） | 给"从没切过"的老笔记补上，限量 | 一次切片 |

**"小改动不重切"能成立，全靠读时自愈兜底**——否则偏移会悄悄失效。保存路径求快、读取路径求准，
两者靠 hash 兜在一起。

### 懒回填，而不是迁移里回填

升级那一刻不回填。两个原因：

1. drift 的 `customSelect` 在迁移回调里拿不到数据（v8→v9 那段踩过同一个坑），而回填需要读全部笔记正文；
2. 几万条笔记会在升级时卡住启动，而且中断了只补一半，很难判断谁补过。

所以老库升上来时 `note_chunks` 是空的，等某篇笔记真的被用到（搜索命中、读片）时由 `NoteChunkRepository`
当场切一遍写回。用户完全无感。

后台那条补充路径（`backfillMissing`）一次最多补 50 篇，只补"从没切过"的：`noteIdsWithoutChunks` 的 SQL
已经排除了软删的笔记（`deleted_at IS NULL`），空正文的笔记再被 `backfillMissing` 跳过。分批做是为了不卡启动、
也为了能随时中断。

### 自愈与重切阈值：哈希怎么兜住不一致

保存后如果每次都重切，用户每敲一个字（防抖 500ms 后）就会切一遍全文。而偏移失效是能被检出的
（`content_hash`），所以完全可以等到"真的有人要读"时再重切——那正是 `chunksFor` 做的事。
保存路径求快、读取路径求准，两者靠 hash 兜在一起。

`chunksFor(noteId, content)` 是唯一的读入口，三种情况：一片都没有（老库升上来的）就现切一遍写回
（懒回填；正文只有空白则返回空）；有片但校验不过就当场重切（自愈）再返回新片；有片且都校验过就直接用，
零写入。

校验（`_isConsistent`）任何一条不成立就重切：`start_offset >= 0`、`end_offset <= content.length`、
`end_offset > start_offset`、`end_offset - start_offset == char_count`，以及
`NoteChunk.hashOf(content, start, end) == content_hash`。

`content_hash` 用 Dart 的 `String.hashCode`，不是加密 hash：这里只需要"变了没有"，不需要抗碰撞，
而 `hashCode` 零成本。正因为如此它不是跨版本稳定的内容指纹，只用于这张表内部的自比，别拿它去和别处的内容
hash 对齐。越界时 `textOf` 返回空串、`_isConsistent` 直接判不过——偏移失效的那一刻不该让整个页面崩掉，
上层会发现"读出来是空的/比预期短"从而触发重切。

重切 = `rebuild` → `replaceNoteChunks`（事务内先删后插）。分两步做的话，中间那一瞬读到的是"旧片已删、
新片没插"的空表，搜索/卡片流刚好撞上就会以为这篇笔记没内容。

**保存时**（`onNoteSaved`，所有保存都经过 `saveContent` 这个漏斗）的实际分支是：

| 情况 | 行为 |
|---|---|
| 还没切过 | 正文非空就切一遍；空则什么都不做 |
| 正文变空 | 把片清掉（否则会留着一堆指向空文本的偏移） |
| 长度变化超过 `staleRatio = 0.20` | 主动重切 |
| 其他 | 什么都不做，留给读时自愈 |

> 阈值的基准是最后一片的 `end_offset`，不是"上一版正文的长度"：
> `delta = |content.length - rows.last.endOffset|`，`before = 0` 时比例按 `1.0` 算。取 20% 与摘要资产的
> 失效阈值同一个思路：小改动靠读时自愈，大改动才值得在保存那一刻多花一次切片。保存是手动的
> （编辑态右上角一个勾），所以"什么时候切"完全由用户按下那一下决定。

> **重切会复位卡片流那两列**（`last_used_at` 变回 null、`next_window_start` 变回 0）——`_toRow` 只写偏移
> 与 hash，不搬旧状态。这是刻意的近似：片号都变了，旧的"用过没用过"本来也不再对应同一段文字。

`cachedChunks` 是只给目录用的轻量版：不校验、不重切（调用方只关心片数与标题路径时才用它）。`readChunk`
越界返回 `null`，与"取到了空串"是两回事——调用方要能区分，否则会以为笔记没内容。

### 卡片流：片内 400 字窗口与轮换

`last_used_at` / `next_window_start` 是卡片流的状态，不是"片是什么"。放在同一条记录上是因为它们与片同一行、
同一生命周期；拆出去的话，每次取片都要按 `(note_id, idx)` 再查一次。

**为什么片是 700 而素材还是 400**：片是给搜索与 AI 用的语义单元（按标题层次切、上限 700）；卡片流是消费侧，
它的提示词、成本估算、抽取逻辑都是围绕"一份素材 400 字"设计的。两者共用同一个切片器，卡片流只从片里开
400 字的窗口——这样卡片流那一整套一个字都不用改。

每份素材是摘要（面）+ 片内窗口（点）两样：摘要给整体背景、存库复用；窗口是原文、不失真。不能只发摘要——
摘要天生概括，AI 拿到概括只能再概括一遍，卡片就"大而空"；具体数字、具体说法、具体例子都在原文那一段里。

**候选窗口起点**（`FeedWindow.starts(len)`，片内相对偏移）：`0, 400, 800, …` 一直到不超过 `len - 400`，
最后一个窗口尾部对齐（直接取 `len - 400`），免得尾段只剩几十个字。`len <= 400` 时整片、只有一个起点 `[0]`。

| 片长 | 候选起点 |
|---|---|
| 350 | `[0]`（整片，不用开窗） |
| 700 | `[0, 300]` |
| 1500 | `[0, 400, 800, 1100]` |

> **尾窗对齐是最容易错的一处**：700 的片是 `[0, 300]` 而不是 `[0, 400]`——`700 - 400 = 300` 已经越过 400，
> 只能尾部对齐；1500 的片末尾是 `1500 - 400 = 1100`，与 `800 + 400 = 1200` 差 100。候选起点不是等距网格，
> 最后一个点是"倒着量"出来的。

**轮换**：用掉一个窗口后，`next_window_start` 推进到下一个候选起点（环形）——取到末尾就回到第一个
（`nextStart`），这样一片的每个窗口都会轮到，不会出现"后半段永远不出卡片"。轮换位不在候选里时（正文改过、
候选变了）回到第一个：这是唯一安全的落点，猜一个下标可能越界。取文本（`FeedWindow.textOf`）从片内 `start`
起 400 字，不越出片，越界一律收敛到片边界。

**`last_used_at` 才是"不重复"的真正保证**：

- 取素材时先在 Dart 里对每篇笔记的片排序：`last_used_at` 为 `null`（从没用过）的排最前，其余按时间升序
  （越久没用过越优先）；
- 排序之后，内存里的 `_recentChunks`（`kRecentChunkKeep = 60`）再把本会话用过的挪到后面——它只是会话内的
  快速过滤，重启即失效，不是保证；
- 用完一片就 `markChunkUsed(noteId, idx, at, nextWindowStart)` 一次写两列（`last_used_at = now`、
  `next_window_start = 下一个起点`），落库，重启后仍然生效。

> 内存那层的键必须是 `noteId:idx`，不能是片正文的 hash。素材改成 400 字窗口之后，同一片每次取出的文字都不一样，
> 按 text hash 去重等于完全没记（早先就是这么写的，静默失效）。

> **为什么必须落库**：一次最多取 5 份素材，一篇 10 片的笔记等于每批用掉一半，不记就必然重复。片变大让这事更糟：
> 4000 字笔记按 700 字切只有约 6 片，连 5 份不同的素材都可能凑不出来（期望重叠 ≈ `5 × 5 / N`，N = 可抽片数）。
> 早先只在内存里记（`_recentChunks`），重启即失效，于是每次冷启动都重新抽到同一批片。

> 实现细节：取片走的是 `chunksOf(noteId)`（按 `note_id` 过滤、按 `idx` 排序），"最近没用过优先"是在 Dart 里
> 对取回的行排序（`feed_repository.dart`），目前没有任何 SQL 写 `ORDER BY last_used_at`。所以 `idx_chunks_used`
> 暂时没有查询真正吃到它——留它是为将来"跨笔记按 `last_used_at` 排序取片"这类查询（写片则是
> `markChunkUsed()`，真实调用方在卡片流里）。

### 软删除要显式清片

外键带 `ON DELETE CASCADE`，但项目用的是软删除（`deleted_at` 置位、行还在），级联不会触发。软删的笔记若还
留着片，搜索就会把"命中哪一片"算到已删笔记头上，用户点进去发现笔记没了。所以 `NoteRepository.softDelete` /
`softDeleteMany` 会显式调 `NoteChunkRepository.clearFor()`（内部就是"用空列表替换"）。恢复时切片按需重建
（读路径发现 0 片就现切），所以清掉是安全的。

AI 的删除工具也显式清，而且没有绕开这条路：`ToolExecutor` 的 `deleteNote` 直接 `softDeleteNote` + `clearFor`；
批量删除走 `NoteRepository.softDeleteMany`（那里面同样逐条清）。换句话说，"删笔记"这个动作在任何入口都必须
带上清片，不能只靠外键。

### 数据类是 `NoteChunkRow`，不是 `NoteChunk`

Drift 默认会生成一个叫 `NoteChunk` 的 row 类，而领域层 `features/note/domain/note_chunk.dart` 里已经有一个
`NoteChunk`（描述"原文的哪一段"，是切片器与仓储之间传递的对象）。两者同名的话，任何同时用到数据库与切片器的
文件都编译失败——所以表上加了 `@DataClassName('NoteChunkRow')`。

### 踩坑记录（它们解释了代码为什么长这样）

下面这些改切片器时很容易被当成冗余删掉，然后整篇内容悄悄丢光：

| 坑 | 表现 | 现在的写法 |
|---|---|---|
| 短笔记兜底只看长度 | 带标题的短笔记也被压成"1 片、`heading` 空、`level 0`"，整条分层流程被绕过，标题路径白写、AI 与搜索页都拿不到上下文 | 兜底条件加"整篇没有标题"；有标题就说明有结构，走分层 |
| 兜底直接返回整篇 `[0, length)` | `'  \n\n正文\n\n  '` 的片首尾都挂着空白 | 兜底路径同样过 `_trim` |
| 合并写成"填到下限" | 与设计自己的 `600 / 600 / 200` 例子不符（得到 `400 / 400 / …`） | 改成"填到上限为止"，`floor` 退出逻辑 |
| 片起点用"标题之后" | `# AA的正文` 这类笔记每节都成空片 → 整篇 0 片、内容全丢 | 起点用含标题行的 `s.start`；"整节都是空白"的判据也覆盖整节，而不是只看标题之后 |
| `_splitByLines` 遇到"单行超长" | `'a' * 2000` 直接切出 0 片 → 又是内容全丢 | 先判单行长度：一行自己就超上限时字符硬切；硬切点原地不动时往前推一个 `cap`，防死循环 |
| `heading` 只拼本节标题 | 子节拿不到祖先路径 | 维护标题栈，遇本级及更深即清空 |
| 内存去重键用片正文 hash | 素材改成窗口后同一片文字每次都不同，去重静默失效 | 键改 `noteId:idx` |
| 行首/行尾判据用"位置上的字符" | 递归切子节时区间从一行中间开始，靠 `c[i-1] == '\n'` 会漏掉第一行之后的所有行 | 改成按"这一行从哪开始、到哪结束"扫描（`_lineStart` / `_lineEnd`），CRLF 一起跳 |

### 备份不单独处理这张表

备份用的是 SQLite 的 `VACUUM INTO` 整库快照（`AppDatabase.snapshotTo`），归档里就是整个数据库文件——
所以切片会跟着一起走，而且与它所指向的笔记正文来自同一份快照，偏移不可能错位。这正是"只存偏移、不存正文"
的好处：没有第二份会过期的数据。

导入是整库替换，不是逐表合并——所以不会出现"旧切片残留、指向新笔记"这种错位。

`BackupService` 的必需表清单里只列 `notes` / `notebooks` / `app_kv`（后两者同时接受旧名 `folders` /
`settings`），刻意不含 `note_chunks`：老备份包（v10 以前）里根本没有这张表，把它列进必需表会让老包被判成
"不是有效的笔记数据库"。老包导入后表由迁移建出、内容由仓储懒回填。

## 10. schemaVersion 与迁移

**当前 `schemaVersion = 11`。**

- `AppDatabase.schemaVersion` 直接返回 `kCurrentSchemaVersion`；
- `kCurrentSchemaVersion` 在 `lib/core/db/database_location.dart`（= 11）。单独提出来是给备份/恢复用的：
  `BackupService` 需要在不构造 `AppDatabase` 的前提下知道版本号，才能判断一个备份包是否兼容；
- 两处必须一致（改 `AppDatabase.schemaVersion` 就要同步这里），否则会出现"能导入但打不开"。

**开发期**：改表后跑 `dart run build_runner build`，然后删掉数据库让它重建（先导出备份）。

**一旦对外发布过**，改表必须：

1. 递增版本号（上面两处）
2. 在 `MigrationStrategy.onUpgrade` 里写迁移
3. 用 `drift_dev schema dump` 存一份 schema 快照，并在 `test/migration_test.dart` 里补一条迁移测试

**迁移规则：只追加，永不修改已发布的版本分支。**

> **索引必须在 `onUpgrade` 的最末尾补**（`await _createIndexes()`）：迁移回调里 `m.createTable` 的 DDL
> 是延迟到回调结束后才执行的，在同一次回调里紧跟建索引会报 `no such table`。`_createIndexes()` 原先只在
> `onCreate`（全新库）里调用，于是从老版本升级上来的库永远拿不到后来新增的索引，大库上会明显变慢而且很难发现；
> 现在 `onCreate` 与 `onUpgrade` 末尾各调一次。

### v1 → v2：数据修正

### v2 → v3：改名 + 去层级

```dart
if (from < 3) {
  Future<void> trySql(String sql) async {
    try { await customStatement(sql); } catch (_) { /* 目标不存在 = 已是新结构 */ }
  }
  await trySql('ALTER TABLE folders RENAME TO notebooks');
  await trySql('ALTER TABLE notes RENAME COLUMN folder_id TO notebook_id');
  await trySql('ALTER TABLE ai_conversations '
      'RENAME COLUMN workspace_folder_id TO workspace_notebook_id');
  try {
    await customStatement('ALTER TABLE notebooks DROP COLUMN parent_id');
  } catch (_) {
    await trySql('UPDATE notebooks SET parent_id = NULL'); // SQLite < 3.35 的退路
  }
  await trySql('DROP INDEX IF EXISTS idx_folders_parent');
  await customStatement(
    'CREATE INDEX IF NOT EXISTS idx_notebooks_order '
    'ON notebooks(sort_order, name)');
}
```

> 这一段踩了两个坑：**列名**——在 `tables.dart` 给字段加 `@JsonKey('folder_id')` 不能让 SQL 列名保持不变，
> `@JsonKey` 只作用于 Drift 的 JSON 序列化、不参与建表，真正控制列名的是 `named('...')`；drift 按字段名生成了
> `notebook_id`，而老库还是 `folder_id`，查询报 `no such column: notebook_id`。**探测**——想用
> `PRAGMA table_info(notebooks)` 或查 `sqlite_master` 判断"是不是老库"，在 `onUpgrade` 里都拿不到结果
> （drift 的 `customSelect` 在这个阶段返回空），据此判断会漏掉改名步骤。所以这里不做探测：直接执行改名，
> 失败就吃掉。对全新库（`onCreate` 已建好新结构）来说，每条都以 "no such table / no such column" 失败——
> 那正是预期。

### v5 → v6：删掉记忆卡片的三张表

```dart
if (from < 6) {
```

`IF EXISTS` 让"本来就没这张表"也不报错，所以从任意老版本升上来都安全。

### v8 → v9：删手动标签 + 两个表改名

```dart
if (from < 9) {
  // 1) 删「用户手动标签」整条链路。先删连接表 note_tags，再删主表 tags。
  for (final t in const ['note_tags', 'tags']) {
    await customStatement('DROP TABLE IF EXISTS $t');
  }

  // 2) 两个表改名。不做探测：onUpgrade 里 drift 的 customSelect 返回空，
  //    所以直接执行、失败就吃掉（全新库必然失败，那正是预期）。
  Future<void> trySql(String sql) async {
    try { await customStatement(sql); } catch (_) {}
  }
  await trySql('ALTER TABLE note_ai_summaries RENAME TO ai_note_summaries');
  await trySql('ALTER TABLE settings RENAME TO app_kv');
}
```

**为什么必须先 RENAME 再删类名**：Drift 的表名由类名推导，改类名（`Settings` → `AppKv`、
`NoteAiSummaries` → `AiNoteSummaries`）会让生成器认为"旧表不存在、要建新表"。少了 RENAME，老库升级后这两张表
的数据就直接丢了——`folders` → `notebooks` 那次的做法完全可以照抄。

**顺带改名改了生成代码里的行类名**：`Setting` → `AppKvData`（drift 发现 `AppKv` 会和表类重名，自动加了
`Data` 后缀）、`NoteAiSummary` → `AiNoteSummary`。`app_database.dart` 里的 `_db.settings` /
`SettingsCompanion` / `_db.noteAiSummaries` 等引用全部跟着改。

> `backup_service.dart` 的导入校验必需表清单必须同步：它原先写 `const ['notes', 'settings']`，v9 后要认
> `app_kv`，否则新导出的备份会被自己判定成"不是有效的笔记数据库"（这个坑在 `folders` → `notebooks` 那次踩过
> 一次）。同时按同一先例接受旧名 `settings`，否则老备份全被挡在门外。对应的回归测试是
> `migration_test.dart` 的「v9：删掉手动标签两张表，并把两个表名改掉」——它会断言新名在、老名不在，并且通过新
> 入口 `readSetting()` 读回改名前的数据，确认没丢。

### v9 → v10：新增切片表

```dart
if (from < 10) {
  await m.createTable(noteChunks);
}
```

只建表，不在迁移里回填（理由见第 9 节的「懒回填」）。

### v10 → v11：工作区从"一个笔记库 id"变成"范围"

```dart
if (from < 11) {
  await customStatement(
    'ALTER TABLE ai_conversations '
    "ADD COLUMN workspace_scope TEXT NOT NULL DEFAULT ''",
  );
  await customStatement(
    "UPDATE ai_conversations SET workspace_scope = "
    "'{\"mode\":\"pick\",\"notebookIds\":[\"' || workspace_notebook_id "
    "|| '\"],\"includeUnfiled\":false}' "
    'WHERE workspace_notebook_id IS NOT NULL',
  );
}
```

用 `ALTER TABLE ADD COLUMN`（纯新增、不动数据、不重建表）：这是最不容易出错的一种迁移，而这次改的只是一个
会话级设置。顺手把老值搬过去：原来存的是单个笔记库 id，对应新形状的 `pick` + 一个目录 + 不含轻笔记；
老的空值 = 从没设过 → 留空串，读取时按默认值（全体空间）处理，见 `AgentWorkspace.parse`。

> 空串不等于「不选择」：空串表达"用户没做过这个选择"，与用户显式选的 `{"mode":"none"}` 分得清。把空串读成
> `none` 会让老会话的默认值和新会话的不一样——同一个 App 两套默认，用户只会觉得"有时候看得见有时候看不见"。
> 只有"读不懂的坏 JSON"和"连会话记录都没有"才按 `none` 保守处理。

> 那条 UPDATE 只在 `from < 11` 时跑，也就是老库才有 `workspace_notebook_id` 这一列；全新库的表里已经没有它了，
> 所以不会因为列不存在而报错。老库升级后 `workspace_notebook_id` 这一列仍然留在表里（ADD COLUMN 不删旧列，
> 迁移也没做 DROP COLUMN）。Drift 不再认识它，属于无害的历史残留；删它要走"重建表"，风险远大于收益。

### `_createIndexes()`：全部 8 条显式索引

```
idx_notes_updated          ON notes(updated_at DESC)
idx_notes_inbox            ON notes(is_inbox, updated_at DESC)
idx_notes_notebook         ON notes(notebook_id, updated_at DESC)
idx_notes_deleted          ON notes(deleted_at)
idx_notebooks_order        ON notebooks(sort_order, name)
idx_chunks_used            ON note_chunks(last_used_at)

```

全部写成 `CREATE INDEX IF NOT EXISTS`，所以 `onCreate` 与 `onUpgrade` 末尾各调一次是安全的、可重复执行的。

> 已删除的索引：`idx_feed_due`、`idx_feed_starred`（随 `note_feed_state` 一起，v8）；
> `idx_summaries_note`（随 `note_summaries` 一起，v7）；`idx_folders_parent`（随层级一起，v3）。

### 外键：必须显式打开

`beforeOpen` 里执行 `PRAGMA foreign_keys = ON`——SQLite 默认关闭外键，不开的话 `CASCADE` / `SET NULL`
全都不生效。
