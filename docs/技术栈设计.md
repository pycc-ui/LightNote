# 技术栈设计

这个项目用了哪些技术、每个为什么用、代价是什么。目录结构见 [目录设计](目录设计.md)，表结构见
[数据库设计](数据库设计.md)，开发流程见 [架构和功能开发流程设计](架构和功能开发流程设计.md)。

选型都用两条要义（**轻**、**省 token**，见 [软件理念设计](软件理念设计.md)）过一遍：
「轻」= 依赖越少越好、功能做减法；「省 token」= 不引入会放大或重复消耗 token 的设计。
代价也一并写出来。

---

## 1. 总览

| 维度 | 决定 | 一句话理由 |
|---|---|---|
| 语言 / UI 框架 | Flutter 3.47.6 + Dart 3.13.5，Material 3 | 一套代码出 Android 与 Windows，两个平台工程都已生成 |
| 数据库 | Drift（`NativeDatabase`），不是裸 `sqflite` | 编译期行类型 + `watch()` 响应式查询，两端同一份代码 |
| SQLite 原生库 | 不依赖 `sqlite3_flutter_libs` | drift ≥ 2.32 起由 sqlite3 的 build hooks 自动打包 |
| 状态管理 | `provider`（只做依赖注入）+ drift 的 `watch()` | 全项目只有 drift 一套代码生成器，出错面最小 |
| 网络 | `dio` | 流式响应体、`CancelToken`、超时可分开配置 |
| AI 服务 | DeepSeek OpenAI 兼容接口（`/chat/completions`） | 一个 HTTP 接口同时覆盖流式、JSON Output、Tool Calls |
| 轻量偏好 | 数据库 `app_kv` 表，不用 `shared_preferences` | 少一个依赖，偏好还能进同一个备份包 |
| 密钥 | `flutter_secure_storage` | API Key 只进系统钥匙串，不打进安装包、不进备份 |
| 备份包 | `archive` + `crypto` + `file_selector` | 纯 Dart 读写 zip，Windows 与 Android 行为一致，且不需要存储权限 |
| Markdown 渲染 | `gpt_markdown` | 认 `$…$` / `$$…$$` 数学公式、代码高亮、流式增量渲染；`flutter_markdown` 不认公式且已停止维护 |
| 最低 SDK | `sdk: ^3.10.0` | 被 drift 新一代对 Dart 的要求抬起来的 |

版本以 `pubspec.yaml` 的约束 + `pubspec.lock` 的实际解析结果为准，明细见第 9 节。

## 2. Flutter + Dart

一套代码同时覆盖 Android 手机（目标平台）与 Windows 桌面（日常开发调试）。工程里 `android/`、
`windows/` 两个平台目录都已生成；`ios/`、`linux/`、`macos/`、`web/` 未生成。
技术难点集中在「本地数据模型 + 流式 AI + Markdown 渲染」，这三块 Flutter 侧都有成熟包，
不需要写平台原生代码。

**代价**：包体积大于原生（release 构建含 Flutter 引擎）；Windows 侧构建依赖 Visual Studio Build Tools，
环境要求比纯 Dart 工具链高。

## 3. 数据库：Drift（不是裸 `sqflite`）

| 维度 | 裸 `sqflite` | Drift |
|---|---|---|
| 查询 | 手写 SQL 字符串 | Dart DSL + 可选自定义 SQL |
| 类型 | 运行时 `Map<String, dynamic>` | 编译期生成行类型（`notes` 表 → 行类） |
| UI 刷新 | 自己通知、自己重查 | `watch()` 返回 `Stream`，数据一变 UI 自动重建 |
| 桌面调试 | 需另配 `sqflite_common_ffi` | `NativeDatabase` 直接支持 Windows |
| 迁移 | 手写 `onUpgrade` | `schemaVersion` + 迁移步骤，可导出 schema 回归 |
| 开销 | 无 | 需要跑 `build_runner` |

本项目的查询是「多表关联 + 过滤 + 随机取样」（笔记 ↔ 笔记库 ↔ AI 资产 ↔ 卡片池），
手写 SQL 字符串在这个量级会变成维护负担，所以选 Drift。

**代价**：引入第一套、也是唯一一套代码生成流程——改了 `tables.dart` 必须重跑
`dart run build_runner build`，否则编译不过；生成物 `app_database.g.dart` 体积很大，且 `drift_dev`
依赖 `analyzer`，`build_runner` 生态对 `analyzer` / `build_runner_core` 版本敏感
（`pubspec.yaml` 里留了 `dependency_overrides` 注释段备用）；学习成本高于裸 SQL。

**SQLite 原生库：不依赖 `sqlite3_flutter_libs`。** 自 drift 2.32 / sqlite3 3.x 起，SQLite 原生库由
build hooks 自动打包进应用，`pubspec.yaml` 只需声明 `sqlite3`。当前 `pubspec.lock` 里没有
`sqlite3_flutter_libs`、也没有 `sqlcipher_flutter_libs`——加了只会引入版本冲突。

**Android 临时目录**：部分设备上系统临时目录对 SQLite 不可用，复杂查询会在临时文件上出问题。
`lib/core/db/app_database.dart` 的 `_openConnection` 在 Android 下把 `sqlite3.tempDirectory` 指向
`Directory.systemTemp`，并用 try/catch 包住：拿不到不致命，退回 SQLite 默认值，不让 App 起不来。

## 4. 状态管理：`provider` 只做依赖注入，界面刷新交给 drift 的 `watch()`

全项目 `lib/` 里没有 `ChangeNotifier`，也没有 `notifyListeners`。"数据变了界面跟着变"不是靠
ChangeNotifier 通知，而是靠 drift 查询自带的 Stream。

- `provider` 只承担依赖注入：`main.dart` 用 `MultiProvider` + `ProxyProvider` 把 `AppDatabase` /
  各 repository / `DeepSeekClient` / `PreferencesService` 放进树里，页面用 `context.read<T>()` 取来调方法。
- 需要"库里的数据变了，界面跟着变"的地方，一律是 drift 的 `watch()` 返回 `Stream` + 页面里的
  `StreamBuilder`（笔记列表、笔记库列表、搜索结果、搜索历史、会话消息、累计花费……）。
  写入方不需要通知任何人：那次写会让 drift 重新推流。
- 一次性读取用 `Future`（`repo.byId(id)` 这类），页面自己 `setState` 消费。

**为什么**：只有一份真相——界面显示的就是库里的行，不存在"内存里的副本忘了同步"；
少一层样板——不用为每个页面写 Notifier + `Consumer`，drift 的流天然按表 / 按查询粒度更新；
全项目只保留 drift 一套代码生成器（不引入 `freezed` / `json_serializable` / `riverpod_generator`），
JSON 与状态类全手写，`build_runner` 的出错面小很多；规模匹配——十来个页面、单用户、本地库，够用。

**代价**：不适合"跨页面的临时 UI 状态"（当前选中项、编辑中的草稿留在页面自己的 `State` 里，
页面销毁就没了）；没有乐观更新（写库到界面刷新之间隔着一次 Stream 推送，做不了"先改 UI 再回写"）；
页面里混着"一次性（`Future`）"与"持续（`Stream`）"两种消费方式，读代码时要分清。
将来若要迁移到 Riverpod，替换的是 DI 那几行与 `StreamBuilder`，数据层（Drift）不动。

## 5. 网络：`dio`

- 需要**流式响应体**：DeepSeek 的 SSE 逐块返回，`ResponseType.stream` + `CancelToken` 直接可用。
- 需要**把超时分开配**：连接 20 秒、读取 5 分钟（生成类请求，尤其 pro + 思考模式可能跑很久）。
- 需要**自己判断状态码**：`validateStatus: (_) => true`，才能把 401 / 402 / 429 的错误响应体读出来给用户看
  （而不是被 dio 直接抛成一个没有上下文的异常）。
- 需要**取消**：用户切页 / 关页时中断在途请求，不白烧 token。

**代价**：SSE 要手写解析——逐行读 `data:`、处理 `[DONE]`、跳过心跳与半行、usage 可能只在最后一块、
错误可能藏在流中间。这些都在 `DeepSeekClient._runStream` 里集中实现一次（`streamChat` 与 `streamAgent`
共用）；没有官方 SDK 的类型辅助，请求体是手拼 `Map`，字段名写错只能靠运行时暴露。

## 6. AI 服务：DeepSeek

### 6.1 接口事实

| 项 | 值 |
|---|---|
| Base URL（OpenAI 格式） | `https://api.deepseek.com` |
| 对话端点 | `POST /chat/completions` |
| 模型名 | `deepseek-flash`（App 固定使用这一个）、`deepseek-v4-pro`（官方也有，App 未使用） |
| 上下文 / 最大输出 | 1M / 384K |
| JSON Output、Tool Calls | 两个模型都支持 |
| 思考模式开关 | `{"thinking": {"type": "enabled" \| "disabled"}}` |
| 思考强度 | `reasoning_effort`，官方接受 `minimal/low/medium/high/xhigh/max/ultra` |
| 思维链字段 | `reasoning_content`，与 `content` 同级 |

**为什么用 flash 做默认**：两个模型都支持 JSON Output、Tool Calls 和思考模式，日常的整理、问答、
卡片生成用 flash 就够；flash 价格约为 pro 的 1/3–1/4。pro 只在确实需要更强推理时由用户显式选
（AI 助手页按会话选，卡片流固定 flash）。

**省钱的关键是思考模式默认关闭**：官方写明思考模式默认打开且 effort 默认 `high`，如果不管它，
连"给这篇加个标签"都会走完整推理链，又慢又贵。所以 `DeepSeekClient` 的每个入口都显式传
`thinking: {"type": "disabled"}`，只有用户在 AI 页选了思考强度才打开。

**代价**：轻量任务的输出质量上限低于「默认开思考」，这是刻意的交易；思考模式下 `temperature`、
`presence_penalty`、`frequency_penalty` 不生效（官方行为：设置了不报错也不生效），所以输出稳定性靠
prompt 约束 + JSON Output，代码里在思考模式下干脆不传 `temperature`；JSON Output 有概率返回空
`content`（官方承认），上层必须做降级：重试 → 正则抽 ```json 代码块 → 抛业务异常并保留原文，
不能静默返回空串。

### 6.2 省钱策略

1. **默认 flash，pro 靠用户显式选择。** 代价见上。
2. **批量而非零散。** 标签与卡片素材一次处理整批，减少重复的系统提示词输入。
3. **缓存命中要靠前缀稳定。** 当前价格下，缓存命中的输入价比未命中低一个数量级以上
   （flash 高峰 0.04 vs 2 元/百万 tokens，即 1/50）。所以系统提示词保持稳定，
   且绝不把时间戳、随机 ID 放进 prompt 开头——那会让缓存永远打不中。

此外还省在别处：笔记切片（`note_chunks`）与卡片流预留是持久化资产（存库复用，不是每次重新生成）；
AI 助手的读写不再是"把整篇笔记投喂进去"，而是让模型用命令语言按行号 `grep` / `sed -n` 只取需要的那几行
（见 [命令语言设计](命令语言设计.md)）。

## 7. 本地存储：为什么不用 `shared_preferences`

主题、字号、搜索历史这类轻量偏好走数据库里的 `app_kv` 表（`PreferencesService`）。
理由：少一个依赖、少一套异步初始化；更重要的是偏好随笔记数据进同一个备份 / 导出流程，
备份包恢复后设置不会漂移。

**代价**：每次读偏好都要过一次数据库（可 `watch` 成 Stream，但比内存读取重）；不适合存大对象，
`app_kv` 是 key-value 文本表，只放小配置。

**密钥不走这条路**：API Key 放系统钥匙串（`flutter_secure_storage`；Android Keystore / Windows DPAPI），
不写代码、不写日志、不进备份包。代价：该插件在 Windows 上把数据放在 `%APPDATA%` 下，目录建不出来时抛
`PathAccessException`，所以 `SecureStore` 的每个方法都降级为「没有配置」+ 会话内内存兜底，
绝不把异常抛给 UI；在那种受限环境下用户本次运行能用 AI，但 Key 关掉 App 就没了。

## 8. 备份 / 导入 / Markdown 渲染

**备份包用 `archive` + `crypto` + `file_selector`**

- 备份包就是普通 zip，用任何解压软件能打开检查。用 `archive` 在 Dart 侧读写：不依赖平台压缩库，
  Windows 与 Android 行为完全一致，测试里也能直接跑（`ZipEncoder`）。
- 包内每个文件（当前是数据库快照）算 SHA-256（`crypto`），导入时校验完整性。
- 选文件 / 选目录用 Flutter 官方的 `file_selector`（不是 `file_picker`）：Windows 走 `IFileDialog`、
  Android 走 SAF，两端"选位置"的体验一致，且不需要申请存储权限。

**代价**：放弃 `file_picker` 的额外能力（如多选混合类型），只保留官方插件覆盖的场景；
Android 的 SAF 可能只返回 `content://` URI，`dart:io` 写不了——这种情况下界面提示改用导入 / 导出备份包。

**Markdown 渲染用 `gpt_markdown`（原先用 `flutter_markdown`）**

换掉的三条理由都是硬的：

- `flutter_markdown` 不认 `$…$` / `$$…$$`：笔记与 AI 输出里的数学公式会退化成一堆带美元符号的
  普通文本，而且不报错——只是"看起来不对"，最难查的那种。
- 它已被官方标记 discontinued，总有一天会挡在 Flutter 版本升级上。
- `gpt_markdown` 是面向 AI 输出的渲染器：内置 LaTeX（`\(…\)` / `\[…\]`，外加
  `useDollarSignsForLatex: true` 打开的美元符号写法）、代码高亮与复制按钮、表格对齐、任务列表、
  流式增量渲染（已定稿的段落复用，只重画尾巴那一段），且自带 `val_latex_flutter`，
  不需要额外的 `flutter_math_fork`。

**代价**：多带 4 个传递依赖（`val_highlight`、`val_highlight_flutter`、`val_latex`、`val_latex_flutter`）；
`![说明](url)` 里的 alt 文字拿不到（`imageBuilder` 只给 url 与 `WxH` 尺寸，而图片本来就不渲染，
丢的只是一句说明）；标题字号改用包的默认映射（`h1→headlineLarge`、`h2→headlineMedium`、
`h3→headlineSmall`…），比旧的手写配置大一号——默认样式是包作者按 Material 3 调的，硬搬旧值只会多一处魔法数字。

**渲染入口只有一处**：`lib/core/widgets/markdown_view.dart` 的 `MarkdownView`。三个开关必须每个入口
完全一致，所以不许在页面里直接 new 渲染器：

1. `useDollarSignsForLatex: true`——默认只认 LaTeX 原生分隔符，漏了公式就不显示；
2. 正文图片不加载，只把 URL 当文本显示（渲染 `![](url)` 等于打开笔记就向第三方发请求）；
3. 用户字号倍率与系统字号相乘生效，不能二选一。

**`$` 的误判边界**：`useDollarSignsForLatex` 打开的 `$…$` 用 Pandoc 的判定规则（`DollarMathCloser`）：
单行内成对、且 `$` 内侧不能紧贴空白，所以 `$100` 这类价格不会被当成公式；`\(…\)` 与 `$…$` 可以混在
同一段里。代码围栏里的 `$` 不参与公式解析（改写发生在代码块之外），未闭合的 `$` 按原文显示。
极端写法（一段文字里夹两个价格、`$a$ 和 $b$` 之外又出现落单的 `$`）仍有小概率误判——
对以中文笔记为主的使用场景，这个风险可以接受。
