# 核心功能设计

一句话：**一个本地优先的笔记库，用 AI 帮你整理，也用 AI 从你自己的笔记里长出新的轻笔记。**

四个核心功能见下。每节讲清三件事：是什么、代码在哪、已知限制。表结构、界面细节、AI 协议各有专门文档，这里只给链接。

| 节 | 功能 | 一句话 | 现状 |
|---|---|---|---|
| 1 | 笔记库的平铺设计与增删改查 | 平铺的笔记库 + 未归档的「我的轻笔记」，两者是同一张表的两种视图 | 完成，无回收站 |
| 2 | AI 辅助增删改查 | AI 提交 SQL（1 个 `sql` 工具 + 25 个 UDF），写操作只能走函数 | 完成，无确认层 |
| 3 | 轻笔记「长出笔记」 | AI 从你的笔记取素材生成新卡片，满意就收下成笔记 | 完成，收下只能进"未归档" |
| 4 | 导入和导出 | 只剩整库备份包（`.zip`），Markdown 导出已删除 | 与最初设想差距最大 |

## 1. 笔记库的平铺设计与增删改查

### 是什么

- **笔记库是平铺的**：`notebooks` 只有一层，没有父子、没有子笔记库、没有"删除父目录时子目录上浮"这类边界处理。
- **笔记只属于 0 个或 1 个笔记库**：`notes.notebook_id` 可空。为空 = 「我的轻笔记」（未归档）。
- 「我的轻笔记」和「笔记库」不是两张表，是同一张 `notes` 靠 `is_inbox` / `notebook_id` 区分的两种视图。所以"归档"只是改两个字段，不搬数据。
- **删笔记库不删笔记**：`softDeleteNotebook` 在一个事务里把库内笔记 `notebook_id → NULL`、`is_inbox → true`，笔记回到「我的轻笔记」。
- **删除是逻辑删除**：`deleted_at` 时间戳置位，行还在（为防 bug、为将来的同步留游标），但没有回收站入口。
- **列表顺序是手工能排的**：`notes.sort_order` 升序、同值再按 `updated_at` 降序（`AppDatabase._noteListOrder`，见下方"调整顺序"）。`0 = 没排过`——老库升级后全是 0，所以顺序和升级前一模一样；用户拖过之后那一批从 `1` 起密集编号，而新建的笔记是 0，于是永远落在已排过的那批**前面**。重编号在 `AppDatabase.reorderNotes` / `reorderNotebooks`。
- **笔记的置顶不参与排序**：`notes.pinned` 只做两件事——「挪到最前一次」（`NoteRepository.moveToFront`）与图钉标记；取消置顶只清标记、**位置不动**。理由是笔记已经有手工顺序，再叠一层独立排序会出现"拖上去又被顶回来"的吸附。（AI 会话那边的 `pinned` 是 `pinned DESC`、真钉在最上面，两处语义不同别混。）

### 已知限制

已完成：笔记库的增删改查；笔记的增删改查；归档 / 移出（同一个 `moveNoteToNotebook` 的两个方向）；置顶（笔记是"挪到最前一次"，不参与排序）；拖动排序（两个入口：库详情页顶栏 ⋮「调整顺序」排库里的笔记、笔记库页顶栏 ⋮「调整笔记库顺序」排库本身；形状一致 = 顶部提示条 + 完成按钮 + 行尾 ≡ 手柄，用 `ReorderableListView.builder` 的 `onReorderItem`，因为 `onReorder` 已被 Flutter 3.47 弃用）；库内与全局搜索；软删除 + 一次性撤销。

未做 / 差距：

- **没有回收站。** 删除是逻辑删除（`deleted_at` 置位、行还在），但 `restore()` 只被左滑删除后 SnackBar 上的「撤销」按钮调用（`LogBar(..., actionLabel: '撤销', onAction: () => repo.restore(note.id))`），没有"已删除"列表页。AI 侧的措辞也是「删了就找不回来（没有回收站）」。软删除在这里是给"防 bug、留后路"用的，不是给用户的功能。
- **排序是两套语义共存的**：笔记库列表仍是 `(sort_order, name)`；笔记列表是 `sort_order ASC, updated_at DESC`，而且 `pinned` **不进排序**（只负责"挪到最前一次"）。所以"置顶"在笔记上不是一层排序，用户拖一下就能把它拖走。
- `notes.source` 列的注释预留了 `local` / `import` / `share` / `ai` 四个值，但实际只有默认值 `local` 会被写入——没有任何导入、分享、AI 写入方去写它（[数据库设计](数据库设计.md) §2 已写明）。
- `notes.lastAiAt`：唯一写入方是 `AppDatabase.markNoteAiDone()`，但它零调用方（死代码）；全项目唯一读它的地方是 `tool_executor` 写回笔记时原样带回，没有任何界面展示它。
- `ai_note_summaries`（卡片流素材用的「AI 摘要」，旧名 `note_ai_summaries`）已在 schema v12 整体删除——卡片流的素材现在只有一段截断的原文（见 §3）；更早那张展示型 `note_summaries`（点「AI 整理要点」的产物）已在 schema v7 删除，功能入口一并移除。
- 编辑页正文按 UTF-8 字节分三档横幅（30/40/50 KB），超硬上限拒绝保存并给「裁剪」入口；裁剪不可撤销。
- 同一套上限也管着 AI 的写入（`ai_udfs.dart` 的 `_checkSize` / `safeTruncate`）：UDF 写入的正文到 50 KB 硬上限就失败（原因写给模型看，它会拆成多篇），标题超 200 字截断（`safeTruncate(..., AiLimits.titleHardMax)`）。硬上限**只管增长不管存在**（判定是 `新字节数 ≤ max(原字节数, 50 KB)`），所以老库里 60~90 KB 的笔记不会被锁死，但也不能再变长。早先只有编辑页拦得住，AI 那条路能写出任意长的笔记——同一张表两条写入路径，一条有上限一条没有。（A 类任务的产出走 `result_applier.dart`，那里也先按 `noteHardBytes` 挡一道。）
- `excerpt`（列表预览）与 `wordCount`（字数）只有一处实现（`TextUtils`）：
  先剥 Markdown、预览截 200 字、字数中文按字 + 英文按词。编辑页与 AI 两条路都调它，
  所以"AI 写过"和"人改过"的同一篇笔记，列表里的数字是一致的。

## 2. AI 辅助增删改查

### 是什么

自然语言进，AI 写**一条 SQL**（只有一个工具 `sql`），App 只判断它是不是「一条只读查询」，然后交给 SQLite；SQLite 遇到扩展函数时回调我们注册的 Dart 实现（UDF）。关键分工：**AI 只写 SQL，约束写在函数的实现里** —— 锚点必须唯一、标题截断、正文硬上限、删库不删笔记，模型绕不过去。

**演进：22 个 function-calling 工具 → 1 个命令脚本工具 `run` → 1 个 SQL 工具 `sql`（+ 保留 `askUser` 作挂起载体）**。前两版的失败原因与这一版的取舍见 [AI操作数据库设计](AI操作数据库设计.md)。

| 工具 | 作用 | 安全 |
|---|---|---|
| `sql` | 参数是一条 SQL，可查表、调用 `ai_functions` 里的 25 个函数、用子查询 / CTE / JOIN / 窗口函数 | App 只放行**一条** `SELECT` / `WITH`（`SqlGuard`）；写操作只能走 UDF |
| `askUser` | 信息不足时问用户，会**挂起**，用户回答后继续 | 不碰数据 |

**外加一路「语义检索」（RAG）**：AI 每要回答**一条新的用户消息**时，先在本机拿这条消息检索一遍自己的笔记，把候选素材拼在**那条消息的末尾**一起发出去。它落在这个功能里（而不是搜索页），因为它是"AI 动手之前先给它一点线索"，用户点不到、也看不见：库里那条消息**一个字节都不改**，素材只存在于这一次请求里。

- **两路召回**：**语义**（`note_vectors` 里的向量算余弦）+ **关键词**（就是搜索页那套 `SearchService`，没改），用 **RRF**（`1/(k+名次)`，`k=60`）融合——两边分数不可比（一边是命中次数、一边是 0~1 的余弦），所以只看名次。
- **它只提供候选，不做决定**：注入文案里明说"这是系统猜的、可能不相关、用之前请自己核实"，每条带 `id` 与 `offset`，AI 可以照抄给 `read_note_batch` 接着读；要改笔记照旧走正常工具。
- **不确定就什么都不给**：语义那一路的最高分要过 `RagLimits.injectMinScore`（0.50）才注入；索引还没建好（`isIndexThin`）、没召回、或者任何一步出错，都是"这次没有素材"。AI 手里那些工具照旧可用。

这一版**砍掉了写操作的确认弹层与撤销栈**：安全性来自「写操作只能调用函数」，而不是点击次数 —— 批量函数一次最多 10 条（`SqlLimits.maxBatchSize`）、删除是逻辑删除、`SqlGuard` 只放行单条查询，所以「清空整个库」得反复调用，而轮数上限挡得住。代价是模型在这几轮里删掉一篇笔记 / 一个笔记库是**立即生效**的 —— 取舍与缓解见 [AI操作数据库设计](AI操作数据库设计.md) 第 14 节。

### 代码在哪

- **25 个 UDF（真正的业务约束）**：`lib/core/db/ai_udfs.dart`
  - 读 11 个：`list_notebooks` / `list_notes` / `list_unfiled` / `outline_notes` / `read_note_batch` / `read_around` / `find_in_note` / `search_notes` / `search_in_note` / `count_notes` / `recent_notes`
  - 建 3 个 / 改 8 个 / 删 2 个 / 信号 1 个（`finish`，`meta` 类）：`create_notes_batch`、`update_notes_batch`（锚点必须唯一）、`append_notes_batch`、`move_notes_batch`、`delete_notes_batch`（≤10 条）、`delete_notebook`（库内笔记不删）……**单次也走批量函数**（数组放一个元素），所以没有 `create_note` 这类单次函数；其余几个按类别的函数（`create_notebook` / `duplicate_note` / `insert_after` / `insert_before` / `prepend_to_note` / `rename_note` / `rename_notebook`）没有一一列出，完整清单以 `kAiFunctions` 为准
  - 派生字段（`excerpt` / `word_count`）用 `TextUtils` 算好、与正文同一条 UPDATE 写；触发器只负责清切片
  - 函数清单（给 AI 看的说明书）在 `lib/core/db/ai_functions.dart`（`kAiFunctionsVersion = 5`），开库时灌进 `ai_functions` 表；**函数详情全量常驻 system prompt**，所以没有"按需加载/钉住函数"的机制（`mark_functions` 已删）
- **工具定义**：`lib/features/ai/domain/tool_specs.dart`（`kSqlToolSpec` / `kAskUserToolSpec` / `specsForRequest` / `toolByName`）
- **执行器（App 侧的边界）**：`lib/features/ai/domain/tool_executor.dart`
  - `sql` 分支：`SqlGuard.check` → `customSelect` → 结果按行数 / 字符数截断 → 回灌
  - `sql_guard.dart`：只放行单条 `SELECT` / `WITH`，拒绝写表 / DDL / `PRAGMA` / 多语句；判定前先剥字符串字面量（否则正文里的 `delete` 会误伤正常查询）
  - 结果通知：UDF 的写绕过 drift，所以发现 SQL 里有写函数名就手动 `notifyUpdates`，界面才会刷新
  - 上限：单条 SQL ≤20000 字符、回灌 ≤200 行 / 8000 字符、`read_around` ≤500 字、`read_note_batch` 单条 ≤1500 字 / 整批 ≤15000 字（超了整批拒绝，不是截断）
- **语义检索**：`lib/features/ai/domain/note_retriever.dart`（两路召回 + RRF 融合 + 注入文案 + `autoInjectBlock` 那道线）、`lib/features/ai/data/text_embedder.dart`（ONNX 嵌入，跑在一个**常驻后台 isolate** 里：单条 74ms 的纯 CPU，放主 isolate 会掉帧；顺带保证模型只加载一份）、`lib/features/ai/data/rag_indexer.dart`（补向量：`indexMissing` **先补片、再补向量**，反了会永远挑到空）、`lib/features/ai/data/rag_index_schedule.dart`（后台调度：启动 / 进 AI 页 / 笔记保存后，保存路径**不 await**）；注入的接线在 `ai_chat_repository.dart` 的 `_retrievalFor`（拿最后一条 user 消息去检索，拼在它的末尾）；阈值与预算在 `app_params.dart` 的 `RagLimits`，向量表见 [数据库设计](数据库设计.md) §9
- **A 类任务（整理 / 生成）的产出落地**：`lib/features/ai/domain/result_applier.dart`（`AiResultApplier`）。模型把内容写在回答末尾的 ```json 块里，App 解析 → 校验 → **逐条**调 UDF 落库（不整批回滚：某一条失败不影响其他条，失败项 + 原因 + 已落库的 id 交回模型，最多修 2 轮）。为什么要这条路：让模型把正文塞进 SQL 参数有两个硬伤——单条 SQL 有 2 万字符上限、正文还要先转义成 JSON 再套进 SQL 单引号里。**没有产出块 = 什么都没落库**（B 类问答就是这种情况）；流式过程中产出块也要切掉（`stripForStreaming`），否则模型写笔记那十几秒里，一大坨含笔记全文的原始 JSON 会直播给用户看。
- **对话循环与协议**：`lib/features/ai/domain/agent_loop.dart`、`ai_chat_repository.dart`、`ask_resolver.dart`、`ask_user.dart`、`ai_model.dart`、`prompts.dart`、`tool_types.dart`；模型客户端 `lib/features/ai/data/deepseek_client.dart`、`deepseek_config.dart`。事件里除了正文还有**思维链**（`AgentThinking`，落 `ai_messages.reasoning`，再按轮拼成分段；它不进正文也不进历史）、轮次开始、工具开始（带模型给的参数 JSON）。另外**"这一轮在不在跑"由仓库内存里的 `_running` 决定**（`isRunning` / `runningMessageId` / `runningChanges`），不再用页面局部状态——以前用页面的 `_sending`，用户退出 AI 页时 State 销毁而那一轮还在跑，回来就误报「App 被系统中断」；同一会话重复 `send` 现在直接抛 `StateError`
- **界面**：`lib/features/ai/ui/ai_page.dart`（模型 / 思考强度 / 指令 / 会话历史 / 答题层）、`agent_dialogs.dart`（只剩答题层：确认弹层与撤销入口已随方案更替删除）
- **审计**：`ai_calls` 表（成本可见性 + 故障排查，不存 prompt / 响应全文）、`ai_conversations` / `ai_messages`（消息上的 `pendingAction` 列就是"操作前预览变更"的暂存）

SQL 通道、25 个函数、放行规则与派生字段见 [AI操作数据库设计](AI操作数据库设计.md)；会话与审计三张表的字段见 [数据库设计](数据库设计.md) §6；向量的表结构与"为什么载荷不引原生扩展"见 [数据库设计](数据库设计.md) §9。

### 已知限制

已完成：SQL 通道全链路（放行判定 → SQLite → UDF 回调 → 结果回灌）；25 个函数带业务约束（锚点唯一、标题截断、50KB 拒绝、删库不删笔记）；语义检索全链路（后台补索引 → 两路召回 → RRF 融合 → 过线才注入）；老库能升上来（v13 迁移 + 函数清单对齐 + 触发器 + v15 建空向量表）；`test/ai_sql_test.dart` 覆盖放行规则与函数行为，`test/rag_eval_test.dart` 离线评测检索质量（纯本地、不花 API 钱）。

未做 / 差距：

- **工作区已取消**：AI 能看见用户的**全部**笔记（整个笔记库根目录）。AI 页选工作区的位置改成了**选模型**（flash / pro），卡片流固定 flash。
- **切片不再给 Agent**：Agent 用 `search_notes` / `find_in_note` / `read_around` 自己定位；切片只服务搜索与卡片流。
- **会话历史的 `listHistory` / `readHistory` / `searchHistory` 三个工具已移除**（AI 现在可以自己 `SELECT` `ai_messages`，但只看得见最近 5 轮与更早的摘要）；`HistoryChunker` 类暂留但无调用方。
- **没有 `restoreNote` 命令**（App 没有回收站），也没有任何"打标签"的命令——用户手动标签的两张表（`tags` / `note_tags`）已在 schema v9 删除。
- `ai_calls` 按隐私约束不存 prompt / 响应全文，出问题只能看 `errorCode`（401 / 429 / timeout / json_empty …）。
- **没有确认层**：写操作调用即生效（删除是逻辑删除，但界面上没有回收站入口）。这是这一版明确接受的取舍，理由与代价见 [AI操作数据库设计](AI操作数据库设计.md) 第 14 节。
- **语义检索只是"锦上添花"的一路，而且它是猜的**：及格线 `vectorMinScore = 0.45` 是在 20 篇语料 / 60 条向量 / 20 条查询上**扫出来的**，不是估的——0.35 那版在同样候选里**误报 5/5**，0.50 会漏 5/15，0.45 是"两个错误各犯一次"的点。样本偏小、有过拟合风险，它的作用是"少误报"而不是"消除误报"（全套数据在 `test/rag_eval_test.dart`）。离线评测：15 条有答案的查询，关键词找到 4 条 → 融合后 11 条；5 条"字面必然搜不到"的，关键词 0 → 4 条；5 条本该无结果的误报 1 条。自动注入用更严的 `injectMinScore = 0.50`（宁可少给一条，也不给一条错的）。
- **索引是后台补的，会落后于正文**：嵌一片 74ms 纯 CPU，所以保存笔记**不等索引**；启动、进 AI 页、保存后各补一批（一次最多 10 篇 / 120 片）。索引没建好时检索宁可返回 null，也不拿"索引里仅有的几篇"冒充"最相关的几篇"。
- **向量不算"原生扩展"，相似度在 Dart 里算**：`note_vectors.vec` 存 Float32 小端字节，检索时全表读有效向量、在 Dart 里算点积（实测 2 万条 512 维 = 11ms）。没用 `sqlite-vec`：它在 Android 上要自己 FFI 调 `sqlite3_load_extension`（`package:sqlite3` 没有公开 API），而且必须有真机才能验证。代价是表里会攒下死行（改一次正文攒一批）——它们靠 `content_hash` + `model` 对不上自动失效，不影响结果，攒多了由 `RagIndexer.pruneStale()` 清。
- **`SELECT content` 仍然拿得到全文**：`read_note_batch` 单条 1500 字 / 整批 15000 字、`read_around` 500 字这些上限只是「用函数读」这条路的约束，不是围栏。
- **UDF 的写绕过 drift**：执行器靠「SQL 里出现写函数名」来手动通知界面刷新，属于启发式（假阳性只多刷一次，无害）。

## 3. 轻笔记「长出笔记」

### 是什么

底部导航的「轻笔记」页是一条 AI 卡片流。这里的轻笔记是 AI 从你的笔记素材里长出来的新内容——"野生的"笔记，不是你已有笔记的另一种展示。

链路：**取素材 → 调 AI 生成 → 卡片上屏（只有标题 + 标签 chip）→ 点开看全文（只读，此时还没进库）→ 满意就「加入我的轻笔记」写成一条真笔记**（未归档状态，之后可以在编辑页归档到某个笔记库）。

「轻笔记」这个词在这个 App 里出现两次，指的不是同一批内容：

- 底部导航的**轻笔记页** = AI 生成的新卡片（消费端，看完可以收下也可以直接走掉）；
- 笔记库页的**「我的轻笔记」区块** = 已经收下但还没归档的笔记（`is_inbox = true`）。

所以"随手记一句"的入口在笔记库页，不在轻笔记页——消费流不产出内容。

### 代码在哪

**页面**（`lib/features/note/ui/`）

| 文件 | 是什么 |
|---|---|
| `inbox_page.dart` | 轻笔记页 = AI 卡片流。下拉换一批、点卡片进详情、卡片上「加入 / 移出我的轻笔记」、右上角（`Icons.tune`）选素材来源。首次进入替换列表、下拉刷新前向追加，没有上拉加载 |
| `feed_detail_page.dart` | 轻笔记详情页。只读全文（内容此刻还没落库），顶栏「加入我的轻笔记」→ 变「已加入」 |
| `feed_source_page.dart` | 素材来源页。全屏多选笔记库、「包含我的轻笔记」开关、全选 / 全不选、保存、恢复默认 |
| `widgets/feed_card.dart` | 卡片组件（「加入我的轻笔记」/「从我的轻笔记移出」是同一位置的开关式按钮） |

**数据与生成策略**（数值定义在 `app_params.dart` 的 `FeedLimits`，`lib/features/note/data/feed_repository.dart` 顶部的 `kXxx` 只是它的别名）

| 常量 | 值 | 含义 |
|---|---|---|
| `kGenParallelism` | 3 | 补池的**并发路数**（= 一次最多生成几张，因为每路单卡）；并行单卡比一个请求要一批快得多 |
| `kFeedBatchSize` | 3 | 一屏显示几张（骨架屏用） |
| `kFeedFirstScreenCount` | 3 | 无预留时首屏先只生成几张（先上屏）；有预留时就取预留那一屏 |
| `kFeedPullSize` | 2 | 每次下拉取几张（比一屏少，免得把后台池子抽太快） |
| `kFeedPoolTarget` | 3 | 后台常备几张（是**目标**不是下限：每次只补一批，池子随着下拉逐步涨到这个数） |

**预留（`feed_reserve` 表）**：进入时优先取上次存的那一屏——取到就**零生成**、秒出，这次也不预热池子；没有（比如刚装完）才当场并发生成 `kFeedFirstScreenCount` 张。**写回不在生成侧**：用户看完一屏后由界面调 `stashReserve()` 把这一屏抄进表里，不额外调 AI（旧做法是后台单独生成几张，已改掉）。所以"预留几张"跟着一屏走，不再有自己的常量。

**素材从哪来**

- **来源配置**：`resolveSource()` = 当前全部笔记库 − 用户明确排除的。只存两个 key：`feed_source_excluded`（排除集）+ `feed_include_unfiled`（缺省 true）。所以「默认全选 + 含我的轻笔记」不需要写任何东西，而新建的笔记库自动被包含（构造性成立，不需要"对账"）。`writeSource()` 存排除集，`resetSource()` 清 key 回到默认态。
- **每份素材 = 片内的一小段窗口**（`gatherSources()`；窗口大小见 `FeedWindow.chars`）。素材就是**一段截断的原文**，没有摘要——只发概括的摘要试过，卡片大而空；原文片段里有具体数字、具体说法可以参照。
  - 窗口位置轮换：`feed_window.dart` + `note_chunks.next_window_start`。
  - **素材数不等于笔记数**：一篇笔记有 10 片就能出 10 份素材。笔记少时靠"同一篇取不同的片"把池子补满。**并发单卡是"一路一份素材、只出 1 张"**，所以卡片数就跟着素材数——素材不够就少出几张，不再让模型对着一份素材写多张（那只会换个说法重复）。
  - **素材数有上限**：一次最多 **3 份**（`gatherSources(limit: …)` 的 `limit` = 补池的 `need`，范围 `[kFeedPullSize, kGenParallelism] = [2, 3]`；无预留首屏是 3 份 `kFeedFirstScreenCount`）。所以应用里**不会超过 3 份**。

**怎么避免重复看到同一段**（四层）

| 机制 | 粒度 | 存哪 |
|---|---|---|
| `note_chunks.last_used_at` 排序（越久没用过越优先；排序在 Dart 里做） | 片 | 落库，重启后仍生效 |
| `kRecentChunkKeep = 30`（`noteId:idx`） | 片 | 内存，会话内快速过滤 |
| `kRecentNoteKeep = 15` | 笔记 | 内存（同一篇不在最近 15 张卡里重复出现） |
| `kRecentTitleKeep = 10` | 标题 | 内存：列进 prompt 让模型主动避开 + 生成后过滤掉撞车的卡片 |

落库那一层是必需的：一次最多取 3 份素材，一篇 10 片的笔记等于每批用掉一小半，不记就必然重复（曾抓到过重复卡片）。早先只在内存里记（`_recentChunks`），重启即失效。

**表**：`feed_reserve`（跨启动预留的那一屏，消费即清）、`note_chunks`（`lib/core/db/tables.dart`）

界面细节见 [界面设计](界面设计.md) §3.1–3.3；两张表的字段与"为什么用表而不是 `app_kv` 里的 JSON"见 [数据库设计](数据库设计.md) §7 / §8 / §9。

### 已知限制

已完成：卡片流全链路；跨启动预留（下次打开先把 `feed_reserve` 里那一屏当屏，秒出且**零生成**，不让用户等一次 5~10 秒的生成）；来源配置（含"新建的库自动加入"）；四层重复抑制（最关键的片级记忆已持久化）；收下 / 移出与数据库双向同步——"已加入"由 `watchUnfiled()` 实时推导，不是页面内存里的布尔值（早先存内存，用户跑到笔记库页把它删了，卡片这边还显示「已加入」，是个真 bug）；生成失败与失败降级都有明确空态文案 + 下一步动作。

未做 / 差距：

- **卡片只能「加入我的轻笔记」，不能直接收进某个笔记库。** 详情页顶栏只有这一个动作，没有"收进哪个库"的选择；也没有"从卡片新建笔记到某库"。想归档必须在编辑页或笔记库页再走一步。
- **生成结果不落库**（只有给下次的那一屏进 `feed_reserve` 表）。所以杀掉进程后没收下的那批就没了，下次重新生成、内容不同。这是刻意的取舍（不用新表、不扰动数据），代价就是"看到喜欢的不马上收下就找不回来"。
- **单次生成的张数与输出 token 都有上限**：卡片生成 `max_tokens = 2048`（`AiLimits.feedMaxOutputTokens`，从 16384 收下来只为防"跑飞"，不是省常态成本）；补池一次最多 3 路并行单卡（`kGenParallelism`），无预留首屏一次 3 张。张数越多 JSON 越长越慢，所以用"多补几次"换"单次更快"。
- **卡片上没有正文预览**：只有标题（最多 3 行）+ 一个标签 chip + 「点开看全文」。预览相关的常量还在，卡片已不用；卡片高度自适应（屏高 2/3 只是上限）。
- **没有"不感兴趣 / 我不想看这个"的反馈入口**，也没有收藏。这些随 v8 卡片流改版一并作废（`note_feed_state` 表已删）。
- 需要配好 API Key 才出内容；预热失败会安静降级到按需生成（页面不卡住，只是第一屏要等）。

## 4. 导入和导出

### 是什么

**现在的真实答案：只剩整库备份包（`.zip`）的导出与导入。** 入口在 设置 → 存储与备份。

**Markdown 导出已被整体删除。** 现在 `lib/core/` 下没有 `export/` 目录（只有 `backup/`），
`MarkdownExportService` / `renderSingle` / `exportAll` 在 `lib/` 里也搜不到——功能与符号一起没了。
`docs/数据库设计.md` §3 有同样的记录（它原本还是"用户手动标签"唯一的外部读取方，而标签功能也一起删了）。

保留下来的是编辑页阅读态菜单里的「**复制全文**」（`note_editor_page.dart` → `LogBar.success('已复制全文')`）——那是纯文本复制到剪贴板，不是导出，不落文件。

### 备份包的内容与格式

`lib/core/backup/backup_models.dart` / `backup_service.dart`

- **就是一个普通 zip**，不加密、不私有格式——用资源管理器 / 任何解压软件能打开，里面是标准 SQLite 文件。用户的数据不该被锁在一个只有本 App 能读的盒子里。
- 目录结构：

```
LightNote-20260213-1045.zip
├── backup.json                    清单（版本、统计、校验和）
└── data/
    └── lightnote.sqlite             SQLite 数据库快照
```

- **`formatVersion = 1`**（`kBackupFormatVersion`）。清单字段：`formatVersion` / `appName` / `appVersion` / `schemaVersion` / `createdAt` / `sourcePlatform` / `stats` / `files[{path,size,sha256}]` / 可选 `note`。缺 `formatVersion` 直接拒绝解析——没有版本号的"备份"无法判断兼容性，宁可拒绝也不要猜。
- **`stats` 只有 `notes` 与 `notebooks` 两项**。`cards` / `reviews` / `tags` 的统计已随功能删除一并移除（新备份里没有这几张表，留着字段只会让每次备份在 `SELECT COUNT(*)` 上抛"表不存在"）；老备份包里的这些键会被 `fromJson` 自然忽略。
- **刻意不含 API Key**：它在系统钥匙串里，不属于笔记数据。备份包通常会被放到网盘或聊天记录里，不能顺手把密钥也带出去。

**导出流程**（`BackupService.exportTo`）

1. **用 SQLite 的 `VACUUM INTO` 做一致性快照**（`AppDatabase.snapshotTo`），不是 `File.copy`——App 正在运行，主库随时可能被写到一半，直接拷贝会得到少了最后一次提交、甚至撕裂的库。快照先在私有目录的 staging 里生成（失败不会在用户选的位置留下半截文件）。
2. 组装 zip：数据库条目 + `backup.json`（含数据库的 SHA-256）。
3. 写目标文件先写 `.tmp` 再改名，中途失败不会留下一个"看起来能用"的假备份。
4. **只在用户选定的位置生成一份。** 早先还会在私有目录 `backups/` 再留一份（默认开），已按用户要求去掉——用户没主动要的副本堆在那里既占空间，又让人以为「导出成功 = 系统里有两份」，而其中一份他根本找不到。默认文件名 `LightNote-YYYYMMDD-HHMM.zip`。

**导入流程**（`inspect` → `scheduleImport` → 下次启动换库）

1. **只读校验，不动任何数据**，三层：①zip 能否解开、`backup.json` 是否存在且合法；②数据库条目大小与 SHA-256 是否与清单一致、文件头是不是 `SQLite format 3`；③真开一次库跑 `PRAGMA integrity_check` 并核对必需表。任何失败都抛 `BackupException`，带用户可读的中文原因。
2. **兼容性检查** `compatibilityProblem()`：备份的 `formatVersion` 或 `schemaVersion` 高于本 App → 给可读原因拒绝导入。
3. 校验通过 → 弹确认：备份时间、来源平台、内容摘要，并选**覆盖当前数据**或**保留当前数据**；两种情况旧库都会改名 `before-import-<时间>.sqlite` 留在同目录（不再往 `backups/` 写）。
4. **不在当前进程里换库**：数据库已经打开，Windows 上文件被占用根本换不掉；即使换掉，已打开的连接指向的是旧 inode，后续读写会落到一个"已删除"的文件上。所以只写一个 `PendingImport` 待处理标记，下次启动、连接建立之前才真正换库，然后提示"已从备份恢复"。
5. **老备份包兼容**：`notebooks` / `folders` 两个表名都接受，`app_kv` / `settings` 两个表名都接受，统计里 `notebooks` 键缺失时读旧的 `folders` 键——改名统一由迁移做（唯一改名入口），校验层不自己改。

**换工作目录**用的是同一套快照机制（`snapshotToNewFile`），本质上就是"把库搬到新位置"，所以也不能用文件拷贝。

### 代码在哪

| 路径 | 作用 |
|---|---|
| `lib/core/backup/backup_service.dart` | 导出、导入校验、安排换库、自动留档、统计 |
| `lib/core/backup/backup_models.dart` | 清单 / 格式版本 / 统计 / 导出与导入结果类型 |
| `lib/core/backup/file_dialogs.dart` | 系统选目录 / 选文件（`file_selector`，不需要存储权限），自动补 `.zip` 后缀 |
| `lib/core/backup/pending_import.dart` | 待导入标记（跨启动） |
| `lib/core/backup/app_restart.dart` | 重启以完成导入 |
| `lib/core/db/app_database.dart` | `snapshotTo` —— `VACUUM INTO` 一致性快照 |
| `lib/core/db/database_location.dart` | 数据库位置（私有目录 / 用户工作目录的逐档回退） |
| `lib/features/settings/ui/pages/storage_settings_page.dart` | 界面：导出备份包（.zip）、从备份包导入、更换工作目录、清空 AI 历史 |

细节见 [技术栈设计](技术栈设计.md) 的「备份 / 导入 / Markdown 渲染」一节、[架构和功能开发流程设计](架构和功能开发流程设计.md) 的「数据会不会丢」一节、[界面设计](界面设计.md) 的「设置：首页只做导航」一节。

### 已知限制（四条里与最初设想差距最大）

已完成：整库 `.zip` 导出（一致性快照 + SHA-256 + 失败不留半截文件）；导入的三层校验 + 可回退换库 + 跨启动完成；换工作目录；清空 AI 历史。

未做 / 差距：

- **没有单篇导出。** 单篇导出 Markdown 已删；`docs/目录设计.md` 也明确写了 `backup/` 的边界是"不做单表导出、不做单个 feature 的数据搬运"。
- **没有任何"人能直接读"的导出格式**：Markdown / 纯文本 / PDF / HTML 全都没有。想把笔记拿出去给别人看，只有两条路——单篇「复制全文」手动粘到别处，或者把整个 zip 给对方（对方得有 LightNote，或者会用 SQLite 工具）。
- **没有"导入现成文档"的能力**：不能导入 `.md` / `.txt` / `.docx`，没有从剪贴板或系统分享菜单导入的入口。`notes.source` 预留的 `import` / `share` 两个值至今没有任何写入方（[数据库设计](数据库设计.md) §2 已写明"目前只有默认值 `local` 会被真正写入"）。
- **导入是整库级的**：只有"覆盖"和"并存"两种策略，没有合并导入、不能"只导入某几个笔记库"、不做去重。
- **导入必须重启 App 才生效**（原因见上：已打开的数据库无法安全替换文件，换掉后旧连接还指向旧 inode）。所以导入是"选包 → 确认 → 重启"，不是即时的。
- **备份不加密**：包里是明文 SQLite，任何人都能解开看。这是刻意的取舍（用户数据不该被锁住），但把备份包放网盘 = 把全部笔记明文放上去。
- **不跨设备同步**：手机和桌面是两套独立数据，靠"一端导出、另一端导入"手动搬。文档里也提醒"具体路径以 App 内显示的为准"，不写死绝对路径。
- 部分平台上系统目录选择器给不出可写的文件系统路径（Android SAF 可能只返回 `content://` URI，`dart:io` 写不了）——那时更换工作目录不可用，界面会提示改用导出 / 导入备份包（`FileDialogs.directoryPickerIsReliable` 只在 Windows / macOS / Linux 为 true）。
