# 核心功能设计

一句话：**一个本地优先的笔记库，用 AI 帮你整理，也用 AI 从你自己的笔记里长出新的轻笔记。**

四个核心功能见下。每节讲清三件事：是什么、代码在哪、已知限制。表结构、界面细节、AI 协议各有专门文档，这里只给链接。

| 节 | 功能 | 一句话 | 现状 |
|---|---|---|---|
| 1 | 笔记库的平铺设计与增删改查 | 平铺的笔记库 + 未归档的「我的轻笔记」，两者是同一张表的两种视图 | 完成，无回收站 |
| 2 | AI 辅助增删改查 | 22 个工具分三层发给 AI，写操作由 App 强制确认 | 完成，撤销面窄 |
| 3 | 轻笔记「长出笔记」 | AI 从你的笔记取素材生成新卡片，满意就收下成笔记 | 完成，收下只能进"未归档" |
| 4 | 导入和导出 | 只剩整库备份包（`.zip`），Markdown 导出已删除 | 与最初设想差距最大 |

## 1. 笔记库的平铺设计与增删改查

### 是什么

- **笔记库是平铺的**：`notebooks` 只有一层，没有父子、没有子笔记库、没有"删除父目录时子目录上浮"这类边界处理。
- **笔记只属于 0 个或 1 个笔记库**：`notes.notebook_id` 可空。为空 = 「我的轻笔记」（未归档）。
- 「我的轻笔记」和「笔记库」不是两张表，是同一张 `notes` 靠 `is_inbox` / `notebook_id` 区分的两种视图。所以"归档"只是改两个字段，不搬数据。
- **删笔记库不删笔记**：`softDeleteNotebook` 在一个事务里把库内笔记 `notebook_id → NULL`、`is_inbox → true`，笔记回到「我的轻笔记」。
- **删除是逻辑删除**：`deleted_at` 时间戳置位，行还在（为防 bug、为将来的同步留游标），但没有回收站入口。

### 代码在哪

**表定义**（`lib/core/db/tables.dart`）

| 类 | 表 | 关键字段 |
|---|---|---|
| `Notebooks` | `notebooks` | `id` / `name` / `sortOrder` / `createdAt` / `updatedAt` / `deletedAt`（没有 `parent_id`） |
| `Notes` | `notes` | `notebookId`（可空，FK `ON DELETE SET NULL`）/ `title` / `content` / `excerpt` / `source` / `isInbox` / `pinned` / `wordCount` / `lastAiAt` / `createdAt` / `updatedAt` / `deletedAt` |

**数据访问**：`lib/core/db/app_database.dart`（`watchUnfiledNotes` / `watchNotesInNotebook` / `softDeleteNote` / `restoreNote` / `moveNoteToNotebook` / `setPinned` / `allNotebooks` …）、`lib/features/note/data/note_repository.dart`、`lib/features/note/data/notebook_repository.dart`

**承载操作的页面**（全部在 `lib/features/note/ui/`）

| 页面 | 承载什么 |
|---|---|
| `library_page.dart` | 笔记库页。「笔记库」+「我的轻笔记」两个区块；右下滑两个 FAB（上：AI 助手，下：新建）；`+` 三选项 = 直接记进我的轻笔记 / 新建并归档到某库 / 新建笔记库；长按菜单（重命名、删除笔记库 / 移动到笔记库、移回轻笔记、删除笔记）；左滑删除；顶栏搜索 + 「更多」→ 多选批量移动 / 批量删除 |
| `notebook_detail_page.dart` | 笔记库详情。库内列表、`+` 新建、库内搜索、「更多」（多选 / 重命名笔记库 / 删除笔记库）、左滑删除 |
| `note_editor_page.dart` | 编辑 / 阅读两态，手动保存。「改」的唯一入口；阅读态菜单 = 删除 / 复制全文 / 加入·移动到笔记库 |
| `search_page.dart` | 实时搜索（250ms 防抖）、关键词高亮、搜索历史、结果分「笔记 / 笔记内容」 |
| `widgets/notebook_picker.dart` | 选笔记库的弹层（新建归档、移动、批量移动共用） |
| `widgets/swipe_to_delete.dart` | 左滑删除组件 |

"平铺"这条约束在 `docs/数据库设计.md` §1 与 §10 都有记录（v2→v3 迁移里有
`ALTER TABLE notebooks DROP COLUMN parent_id` 与删索引 `idx_folders_parent`），`tables.dart` 的
`Notebooks` 类注释也写了同一件事。全项目没有任何 `folder_*` 列，也没有任何 `@JsonKey` 列名映射。

细节（字段约束、索引、迁移史）见 [数据库设计](数据库设计.md) §1 / §2 / §10；界面结构见 [界面设计](界面设计.md) §3.4 / §3.5。

### 已知限制

已完成：笔记库的增删改查；笔记的增删改查；归档 / 移出（同一个 `moveNoteToNotebook` 的两个方向）；置顶；库内与全局搜索；软删除 + 一次性撤销。

未做 / 差距：

- **没有回收站。** 删除是逻辑删除（`deleted_at` 置位、行还在），但 `restore()` 只被左滑删除后 SnackBar 上的「撤销」按钮调用（`LogBar(..., actionLabel: '撤销', onAction: () => repo.restore(note.id))`），没有"已删除"列表页。AI 侧的措辞也是「删了就找不回来（没有回收站）」。软删除在这里是给"防 bug、留后路"用的，不是给用户的功能。
- **笔记库有 `sortOrder` 字段，但没有拖拽排序的 UI。** 列表只按 `(sort_order, name)` 排。
- `notes.source` 列的注释预留了 `local` / `import` / `share` / `ai` 四个值，但实际只有默认值 `local` 会被写入——没有任何导入、分享、AI 写入方去写它（[数据库设计](数据库设计.md) §2 已写明）。
- `notes.lastAiAt`：唯一写入方 `streamOrganize()` 自身零调用方（源码注释里写明属于死代码），全项目唯一读它的地方是 `tool_executor` 写回笔记时原样带回，没有任何界面展示它。
- `ai_note_summaries` 表是给卡片流当素材用的，用户看不到；旧的那张展示型 `note_summaries`（点「AI 整理要点」的产物）已在 schema v7 删除，功能入口一并移除。
- 编辑页正文按 UTF-8 字节分三档横幅（80/90/100 KB），超硬上限拒绝保存并给「裁剪」入口；裁剪不可撤销。
- 同一套上限也管着 AI 的写入（`ToolExecutor._fitForSave`）：`createNote` / `updateNote` /
  `appendToNote` 超 100 KB 一律失败（原因写给模型看，它会拆成多篇），标题超 200 字截断。
  早先只有编辑页拦得住，AI 那条路能写出任意长的笔记——同一张表两条写入路径，一条有上限一条没有。
- `excerpt`（列表预览）与 `wordCount`（字数）只有一处实现（`TextUtils`）：
  先剥 Markdown、预览截 200 字、字数中文按字 + 英文按词。编辑页与 AI 两条路都调它，
  所以"AI 写过"和"人改过"的同一篇笔记，列表里的数字是一致的。

## 2. AI 辅助增删改查

### 是什么

自然语言进，AI 挑工具，App 执行。关键分工：AI 只提出调用，要不要真做由 App 判断——写操作一律先弹确认，删类还要二次确认并写明不可恢复。安全不靠模型自觉，靠执行器动手前查风险等级。

**22 个工具，分三层发送（省 token）**：

| 层 | 数量 | 发送方式 | 工具 |
|---|---|---|---|
| `core` 核心 | 7 | 每次请求发完整定义 | `searchNotes`、`listChunks`、`readChunk`、`createNote`、`updateNote`、`askUser`、`requestTools` |
| `common` 常用 | 10 | 只发名称 + 一句话 | `listNotebooks`、`listNotes`、`getNoteMeta`、`appendToNote`、`deleteNote`、`moveNote`、`createNotebook`、`replaceInNote`、`listHistory`、`readHistory` |
| `onDemand` 按需 | 5 | 默认不发，AI 用 `requestTools` 申请后才给定义 | `renameNotebook`、`deleteNotebook`、`batchMoveNotes`、`batchDeleteNotes`、`searchHistory` |

放在按需层本身就是一层额外摩擦：这些工具要么危险、要么很少用，让模型必须先申请一次。

**风险等级（`ToolRisk`）决定确认强度**：

| 等级 | 工具 | 确认 |
|---|---|---|
| `read` | 查询、搜索、读笔记 / 读片 / 读本会话历史 | 直接执行，不弹层 |
| `create` | `createNote` / `createNotebook` | 轻确认 |
| `modify` | `updateNote` / `appendToNote` / `replaceInNote` / `moveNote` / `renameNotebook` / `batchMoveNotes` | 确认 + 可撤销 |
| `delete` | `deleteNote` / `deleteNotebook` / `batchDeleteNotes` | 二次确认，措辞写明不可恢复 |
| `interaction` | `askUser` / `requestTools` | 不碰数据，不进风险表 |

### 代码在哪

- **工具定义 / 风险 / 分层**：`lib/features/ai/domain/tool_specs.dart`（`ToolRisk`、`ToolLayer`、`AgentTool`、`kCoreTools` / `kCommonTools` / `kOnDemandTools` / `kAgentTools`、`specsForRequest`、`toolCatalogText`、`toolByName`）
- **执行器（真正的边界）**：`lib/features/ai/domain/tool_executor.dart`
  - 所有写操作的唯一入口 `_ask()`：①没有确认通道 → 直接拒绝执行（fail closed，不是"默认放行"）；②问用户，被拒 → 返回"用户拒绝了这次操作，不要重试同一个操作"；③同意 → 执行
  - `ToolConfirmRequest`：`title` / `summary` / `before` / `after` / `warning`（UI 拿它渲染 diff 与提醒）
  - 读预算记在轮上：`maxChunksPerTurn = 3`、`maxChunkCharsPerTurn = 1500`；批量工具 `maxBatch = 10`
  - **锚点校验**：`updateNote` 改正文必须给 `expectedText`，App 先确认这段原文还在——不在就返回"锚点失效"，宁可失败也不写到别处
  - **快照粗筛**：AI 读到过的笔记记内容 hash，写之前不一致就往确认层加一句"这条笔记在你读到它之后被改过"（只提醒，不拦）
  - **撤销栈** `maxUndo = 5`，`undoable` / `undoLast()` 给 UI 显示「撤销」
  - **工作区是上限**：`_scope()` 把模型给的 `notebookId` 只做收窄，不能放宽；模型要的库不在工作区里就返回"一条都不命中"，而不是偷偷放宽
- **对话循环与协议**：`lib/features/ai/domain/agent_loop.dart`、`ai_chat_repository.dart`、`ask_resolver.dart`、`ask_user.dart`、`agent_workspace.dart`、`prompts.dart`、`tool_types.dart`；模型客户端 `lib/features/ai/data/deepseek_client.dart`、`deepseek_config.dart`
- **界面**：`lib/features/ai/ui/ai_page.dart`（工作区 / 思考强度 / 指令 / 会话历史 / 工具确认弹层 / 答题层 / 撤销入口）、`agent_dialogs.dart`、`workspace_sheet.dart`
- **审计**：`ai_calls` 表（成本可见性 + 故障排查，不存 prompt / 响应全文）、`ai_conversations` / `ai_messages`（消息上的 `pendingAction` 列就是"操作前预览变更"的暂存）

协议细节、prompt 写法、工作区三态语义见 [AI接入设计](AI接入设计.md)；会话与审计三张表的字段见 [数据库设计](数据库设计.md) §6。

### 已知限制

已完成：22 个工具全部有真实实现（执行器 `execute()` 的 `switch` 完整覆盖 20 个数据类工具，另 2 个交互类由对话流程接管）；写操作强制确认；删类二次确认；没有确认通道时写操作 fail closed；参数宽松接受（模型给错类型也能读出来）并给可读失败原因；工具执行的所有失败都返回 `ToolResult.failure` 而不抛异常（抛异常会打断整轮对话）。

未做 / 差距：

- `askUser` / `requestTools` 不在执行器里执行——走到执行器会返回"由对话流程处理，不该走到这里"。这是刻意的分工，不是缺失。
- **AI 只能读"片"，读不到整篇。** 一轮上限 3 片 / 1500 字（`readChunk` 定义里说"一次最多 3 片"，实际是轮预算，单次调用只能一片）。所以"通读一篇长文再总结"这种任务，AI 做不到。
- **撤销面很窄**：`_rememberUndo` 只在 `updateNote` 与 `replaceInNote` 里调用。移动笔记、新建笔记、删除笔记、新建 / 重命名 / 删除笔记库都不进撤销栈——`readChunk` 之外的动作没有"手滑了救一下"。
- **没有 `restoreNote` 工具**（App 没有回收站），也没有任何"打标签"的工具——用户手动标签的两张表（`tags` / `note_tags`）已在 schema v9 删除。
- `ai_calls` 按隐私约束不存 prompt / 响应全文，出问题只能看 `errorCode`（401 / 429 / timeout / json_empty …）。
- 工具风险级别是工具定义的一部分，加新工具必须显式声明——漏了编译器会提醒；但这也意味着风险等级只有 5 档，"某个参数才危险"这种细粒度区分表达不了。

## 3. 轻笔记「长出笔记」

### 是什么

底部导航的「轻笔记」页是一条 AI 卡片流。这里的轻笔记是 AI 从你的笔记素材里长出来的新内容——"野生的"笔记，不是你已有笔记的另一种展示。

链路：**取素材 → 调 AI 生成 → 卡片上屏（只有标题 + 标签 chip）→ 点开看全文（只读，此时还没进库）→ 满意就「加入我的轻笔记」写成一条真笔记**（未归档状态，之后可以在编辑页归档到某个笔记库）。

「轻笔记」这个词在这个 App 里出现两次，指的不是同一批内容：

- 底部导航的**轻笔记页** = AI 生成的新卡片（消费端，看完可以收下也可以直接走掉）；
- 笔记库页的**「我的轻笔记」区块** = 已经收下但还没归档的笔记（`is_inbox = true`）。

所以"随手记一句"的入口在笔记库页，不在轻笔记页——消费流不产出内容。

### 代码在哪

**页面**（`lib/features/note/ui/`）

| 文件 | 是什么 |
|---|---|
| `inbox_page.dart` | 轻笔记页 = AI 卡片流。下拉换一批、点卡片进详情、卡片上「加入 / 移出我的轻笔记」、右上角（`Icons.tune`）选素材来源。首次进入替换列表、下拉刷新前向追加，没有上拉加载 |
| `feed_detail_page.dart` | 轻笔记详情页。只读全文（内容此刻还没落库），顶栏「加入我的轻笔记」→ 变「已加入」 |
| `feed_source_page.dart` | 素材来源页。全屏多选笔记库、「包含我的轻笔记」开关、全选 / 全不选、保存、恢复默认 |
| `widgets/feed_card.dart` | 卡片组件（「加入我的轻笔记」/「从我的轻笔记移出」是同一位置的开关式按钮） |

**数据与生成策略**（`lib/features/note/data/feed_repository.dart` 顶部常量）

| 常量 | 值 | 含义 |
|---|---|---|
| `kGenParallelism` | 6 | 补池的**并发路数**（= 一次最多生成几张，因为每路单卡）；并行单卡比一个请求要一批快得多 |
| `kFeedBatchSize` | 3 | 一屏显示几张（骨架屏用） |
| `kFeedFirstScreenCount` | 3 | 无预留时首屏先只生成几张（先上屏，其余后台补） |
| `kFeedPullSize` | 2 | 每次下拉取几张（比一屏少，免得把后台池子抽太快） |
| `kFeedPoolTarget` | 15 | 后台常备几张（≈ 7 屏余量） |
| `kFeedReserveSize` | 6 | 每次启动给下次预留几张，存进 `feed_reserve` 表（**单独生成**，不从池子搬） |

**素材从哪来**

- **来源配置**：`resolveSource()` = 当前全部笔记库 − 用户明确排除的。只存两个 key：`feed_source_excluded`（排除集）+ `feed_include_unfiled`（缺省 true）。所以「默认全选 + 含我的轻笔记」不需要写任何东西，而新建的笔记库自动被包含（构造性成立，不需要"对账"）。`writeSource()` 存排除集，`resetSource()` 清 key 回到默认态。
- **每份素材 = 一篇笔记的「AI 摘要 + 片内 400 字窗口」**（`gatherSources()`）。只发摘要是试过的，结果是卡片大而空——摘要天生概括。切片是原文，里面才有具体数字、具体说法可以参照。
  - 摘要来自 `ai_note_summaries` 表（`note_ai_asset_repository.dart`），一篇一行、长期复用、按内容字节数 20% 阈值判断失效；生成失败会退回正文截断（摘要只是省钱的优化，不该成为"生成不出卡片"的单点故障）。
  - 窗口位置轮换：`feed_window.dart` + `note_chunks.next_window_start`。
  - **素材数不等于笔记数**：一篇笔记有 10 片就能出 10 份素材。笔记少时靠"同一篇取不同的片"把池子补满，只有所有片都不够时才少于目标张数，那时由提示词让模型"从不同角度补足"。
  - **素材数有上限**：一次最多 **6 份**（`gatherSources(limit: …)` 的 `limit` = 补池的 `need`，范围 `[kFeedPullSize, kGenParallelism] = [2, 6]`；无预留首屏是 3 份 `kFeedFirstScreenCount`）。所以应用里**不会超过 6 份**。

**怎么避免重复看到同一段**（四层）

| 机制 | 粒度 | 存哪 |
|---|---|---|
| `note_chunks.last_used_at` 排序（越久没用过越优先；排序在 Dart 里做） | 片 | 落库，重启后仍生效 |
| `kRecentChunkKeep = 60`（`noteId:idx`） | 片 | 内存，会话内快速过滤 |
| `kRecentNoteKeep = 15` | 笔记 | 内存（同一篇不在最近 15 张卡里重复出现） |
| `kRecentTitleKeep = 40` | 标题 | 内存：列进 prompt 让模型主动避开 + 生成后过滤掉撞车的卡片 |

落库那一层是必需的：一次最多取 5 份素材，一篇 10 片的笔记等于每批用掉一半，不记就必然重复（曾抓到过重复卡片）。早先只在内存里记（`_recentChunks`），重启即失效。

**表**：`feed_reserve`（跨启动预留的 6 张，消费即清）、`ai_note_summaries`、`note_chunks`（`lib/core/db/tables.dart`）

界面细节见 [界面设计](界面设计.md) §3.1–3.3；三张表的字段与"为什么用表而不是 `app_kv` 里的 JSON"见 [数据库设计](数据库设计.md) §4 / §7 / §8。

### 已知限制

已完成：卡片流全链路；跨启动预留（下次打开先把 `feed_reserve` 里的 6 张当屏，秒出，不让用户等一次 5~10 秒的生成）；来源配置（含"新建的库自动加入"）；四层重复抑制（最关键的片级记忆已持久化）；收下 / 移出与数据库双向同步——"已加入"由 `watchUnfiled()` 实时推导，不是页面内存里的布尔值（早先存内存，用户跑到笔记库页把它删了，卡片这边还显示「已加入」，是个真 bug）；生成失败与失败降级都有明确空态文案 + 下一步动作。

未做 / 差距：

- **卡片只能「加入我的轻笔记」，不能直接收进某个笔记库。** 详情页顶栏只有这一个动作，没有"收进哪个库"的选择；也没有"从卡片新建笔记到某库"。想归档必须在编辑页或笔记库页再走一步。
- **生成结果不落库**（只有给下次的 6 张进 `feed_reserve` 表）。所以杀掉进程后没收下的那批就没了，下次重新生成、内容不同。这是刻意的取舍（不用新表、不扰动数据），代价就是"看到喜欢的不马上收下就找不回来"。
- **一次生成张数有上限**（默认 5）：张数越多，JSON 输出越长、越慢，逼近 8192 token 输出上限后会被截断、JSON 解析失败、整批白烧。所以用"多补几次"换"单次更快"。
- **卡片上没有正文预览**：只有标题（最多 3 行）+ 一个标签 chip + 「点开看全文」。预览相关的常量还在，卡片已不用；卡片高度自适应（屏高 2/3 只是上限）。
- **没有"不感兴趣 / 我不想看这个"的反馈入口**，也没有收藏。这些随 v8 卡片流改版一并作废（`note_feed_state` 表已删）。
- 需要配好 API Key 才出内容；预热失败会安静降级到按需生成（页面不卡住，只是第一屏要等）。

## 4. 导入和导出

### 是什么

**现在的真实答案：只剩整库备份包（`.zip`）的导出与导入。** 入口在 设置 → 存储与备份。

**Markdown 导出已被整体删除。** 现在 `lib/core/` 下没有 `export/` 目录（只有 `backup/`），
`MarkdownExportService` / `renderSingle` / `exportAll` 在 `lib/` 里也搜不到——功能与符号一起没了。
`docs/数据库设计.md` §3 有同样的记录（它原本还是"用户手动标签"唯一的外部读取方，而标签功能也一起删了）。

保留下来的是编辑页阅读态菜单里的「**复制全文**」（`note_editor_page.dart` → `LogBar.success('已复制全文')`）——那是纯文本复制到剪贴板，不是导出，不落文件。

### 备份包的内容与格式

`lib/core/backup/backup_models.dart` / `backup_service.dart`

- **就是一个普通 zip**，不加密、不私有格式——用资源管理器 / 任何解压软件能打开，里面是标准 SQLite 文件。用户的数据不该被锁在一个只有本 App 能读的盒子里。
- 目录结构：

```
LightNote-20260213-1045.zip
├── backup.json                    清单（版本、统计、校验和）
└── data/
    └── lightnote.sqlite             SQLite 数据库快照
```

- **`formatVersion = 1`**（`kBackupFormatVersion`）。清单字段：`formatVersion` / `appName` / `appVersion` / `schemaVersion` / `createdAt` / `sourcePlatform` / `stats` / `files[{path,size,sha256}]` / 可选 `note`。缺 `formatVersion` 直接拒绝解析——没有版本号的"备份"无法判断兼容性，宁可拒绝也不要猜。
- **`stats` 只有 `notes` 与 `notebooks` 两项**。`cards` / `reviews` / `tags` 的统计已随功能删除一并移除（新备份里没有这几张表，留着字段只会让每次备份在 `SELECT COUNT(*)` 上抛"表不存在"）；老备份包里的这些键会被 `fromJson` 自然忽略。
- **刻意不含 API Key**：它在系统钥匙串里，不属于笔记数据。备份包通常会被放到网盘或聊天记录里，不能顺手把密钥也带出去。

**导出流程**（`BackupService.exportTo`）

1. **用 SQLite 的 `VACUUM INTO` 做一致性快照**（`AppDatabase.snapshotTo`），不是 `File.copy`——App 正在运行，主库随时可能被写到一半，直接拷贝会得到少了最后一次提交、甚至撕裂的库。快照先在私有目录的 staging 里生成（失败不会在用户选的位置留下半截文件）。
2. 组装 zip：数据库条目 + `backup.json`（含数据库的 SHA-256）。
3. 写目标文件先写 `.tmp` 再改名，中途失败不会留下一个"看起来能用"的假备份。
4. **只在用户选定的位置生成一份。** 早先还会在私有目录 `backups/` 再留一份（默认开），已按用户要求去掉——用户没主动要的副本堆在那里既占空间，又让人以为「导出成功 = 系统里有两份」，而其中一份他根本找不到。默认文件名 `LightNote-YYYYMMDD-HHMM.zip`。

**导入流程**（`inspect` → `scheduleImport` → 下次启动换库）

1. **只读校验，不动任何数据**，三层：①zip 能否解开、`backup.json` 是否存在且合法；②数据库条目大小与 SHA-256 是否与清单一致、文件头是不是 `SQLite format 3`；③真开一次库跑 `PRAGMA integrity_check` 并核对必需表。任何失败都抛 `BackupException`，带用户可读的中文原因。
2. **兼容性检查** `compatibilityProblem()`：备份的 `formatVersion` 或 `schemaVersion` 高于本 App → 给可读原因拒绝导入。
3. 校验通过 → 弹确认：备份时间、来源平台、内容摘要，并选**覆盖当前数据**或**保留当前数据**；两种情况旧库都会改名 `before-import-<时间>.sqlite` 留在同目录（不再往 `backups/` 写）。
4. **不在当前进程里换库**：数据库已经打开，Windows 上文件被占用根本换不掉；即使换掉，已打开的连接指向的是旧 inode，后续读写会落到一个"已删除"的文件上。所以只写一个 `PendingImport` 待处理标记，下次启动、连接建立之前才真正换库，然后提示"已从备份恢复"。
5. **老备份包兼容**：`notebooks` / `folders` 两个表名都接受，`app_kv` / `settings` 两个表名都接受，统计里 `notebooks` 键缺失时读旧的 `folders` 键——改名统一由迁移做（唯一改名入口），校验层不自己改。

**换工作目录**用的是同一套快照机制（`snapshotToNewFile`），本质上就是"把库搬到新位置"，所以也不能用文件拷贝。

### 已知限制（四条里与最初设想差距最大）

已完成：整库 `.zip` 导出（一致性快照 + SHA-256 + 失败不留半截文件）；导入的三层校验 + 可回退换库 + 跨启动完成；换工作目录；清空 AI 历史。

未做 / 差距：

- **没有单篇导出。** 单篇导出 Markdown 已删；`docs/目录设计.md` 也明确写了 `backup/` 的边界是"不做单表导出、不做单个 feature 的数据搬运"。
- **没有任何"人能直接读"的导出格式**：Markdown / 纯文本 / PDF / HTML 全都没有。想把笔记拿出去给别人看，只有两条路——单篇「复制全文」手动粘到别处，或者把整个 zip 给对方（对方得有 LightNote，或者会用 SQLite 工具）。
- **没有"导入现成文档"的能力**：不能导入 `.md` / `.txt` / `.docx`，没有从剪贴板或系统分享菜单导入的入口。`notes.source` 预留的 `import` / `share` 两个值至今没有任何写入方（[数据库设计](数据库设计.md) §2 已写明"目前只有默认值 `local` 会被真正写入"）。
- **导入是整库级的**：只有"覆盖"和"并存"两种策略，没有合并导入、不能"只导入某几个笔记库"、不做去重。
- **导入必须重启 App 才生效**（原因见上：已打开的数据库无法安全替换文件，换掉后旧连接还指向旧 inode）。所以导入是"选包 → 确认 → 重启"，不是即时的。
- **备份不加密**：包里是明文 SQLite，任何人都能解开看。这是刻意的取舍（用户数据不该被锁住），但把备份包放网盘 = 把全部笔记明文放上去。
- **不跨设备同步**：手机和桌面是两套独立数据，靠"一端导出、另一端导入"手动搬。文档里也提醒"具体路径以 App 内显示的为准"，不写死绝对路径。
- 部分平台上系统目录选择器给不出可写的文件系统路径（Android SAF 可能只返回 `content://` URI，`dart:io` 写不了）——那时更换工作目录不可用，界面会提示改用导出 / 导入备份包（`FileDialogs.directoryPickerIsReliable` 只在 Windows / macOS / Linux 为 true）。
